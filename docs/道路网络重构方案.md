# 道路网络重构方案 —— 从「成对寻路」到「共享路网」

> 状态: 方案评审稿 v1（2026-09-13）。本文档是**计划**，未实施。
> 触发问题: 同一条谷地走廊里，矿15→粮11 与 矿15→灵2 两条路**全程平行、互不合并**（见 2026-09-13 截图）。

---

## 一、问题定义

### 1.1 现象

两聚落 (A=矿15, B=粮11, C=灵2) 分布为"A 在谷顶，B/C 在谷口两侧"。期望: A 向下修**一条**干道，
到分叉点后分成两支到 B、C（用户蓝线所绘）。实际: A→B 与 A→C 两条路在共享的谷地段**平行双线**。

### 1.2 根因（成对寻路框架的结构性缺陷）

当前算法 = 对每个聚落对独立跑 A*，"合并"靠**给已建路格打折**，且折扣只对
「本对两端点直线走廊 ±3 格」内的路格生效（`ROAD_REUSE_CORRIDOR`）。三个致命限制:

| # | 限制 | 后果 |
|---|------|------|
| 1 | **折扣按对的直线走廊限定** | A→B 与 A→C 的直线在分叉后夹角张开，中段彼此距离 >3 格 → 互在对方走廊外 → 谁也骑不了谁 → 平行双线 |
| 2 | **道路是成对私有的折线** | 同一段谷地被两条线路各修一遍；没有"这段路属于路网、被多条线路共用"的表示 |
| 3 | **合并与直线不可兼得（成对框架内）** | 放开折扣（不限走廊）→ 上一轮的"垂直绕出去骑远干道"问题；限定走廊 → 本轮的"不合并"问题。**三角张力: 直线度 / 并线度 / 代价最优，成对框架只能三选二** |

### 1.3 结论

打补丁已到边界。需要把"路"从**成对折线的集合**重构为**共享 tile 路网**，把"哪两点该连"
从**邻域全对**重构为**稀疏需求图**，把"绕行容忍"从**隐式（权重隐含）**重构为**显式绕行系数闸**。

## 二、迭代史与经验教训（此前想法盘点）

| 版本 | 机制 | 解决了什么 | 暴露了什么 | 去留 |
|------|------|-----------|-----------|------|
| v0 近邻连接 | 每聚落只连最近 1/2 个 | 简单 | 路网碎裂成孤岛链 | ✗ |
| v1 邻域全对 | 3x3 池内全部聚落逐对 A* | 不再孤岛 | 平行冗余路爆炸 | 需求图取代 |
| v2 跳板剪枝 | ∃m 严格介于两端且直线绕行 ≤30% ⇒ 不建直达 | 消灭三角捆绑 | 只管"建不建"，不管"合不合并" | 并入需求图稀疏性 |
| v3 地形权重表 | 水8/沙4/林4/沙5/山8 vs 草3 | 路避山/水/沙漠 | 权重对比越大绕行越夸张（需绕行闸兜底） | ✓ 保留 |
| v4 走廊限定复用 | 已建路格在两端直线 ±3 胶囊内 2 费 | 消灭"垂直绕出去骑远干道" | **本问题: 分叉对不合并** | 升级为全局折扣+绕行闸 |
| v5 步数透镜自适应 | 复用模式步数上限 = COST_MAX÷ROAD_W_ROAD=60 | 假不可达/次优（独立 Dijkstra 对拍抓出） | — | ✓ 保留 |
| v6 cartDist/isqrt | 笛卡尔实际距离整数化 | 距离语义精确、无浮点 | — | ✓ 保留 |

**核心教训**: 每个补丁都在"直线度 / 并线度 / 代价最优"三角里挪动支点。合并问题（本方案）
在成对框架里无解，必须换框架。

## 三、调研结论（外部做法）

| 来源 | 做法 | 可借鉴点 |
|------|------|---------|
| [Rahix: Procedural Road Networks](https://blog.rahix.de/003-road-networks/) | 格网每条边初始高通行成本；选两端点 A*；**沿路径把边的成本降低**，后续路径自然重合 → 合并是**涌现效果**；降到最低价后**反涨一大截**防止单路无限吸流 | ① 全局边折扣（不限走廊）是主流做法；② 折扣要有"防独大"机制 |

| [林道规划绕行系数 (Detour Index)](https://www.sciencedirect.com/science/article/pii/S2352186426000623) / [PlanningTank](https://planningtank.com/transportation/network-connectivity-indices) | **DI = 实际路长 ÷ 直线距离**，衡量绕行程度；林道工程常用上限 **≈1.4**，超过视为低效迂回 | 给"绕远路"一个工业标准量化闸门，替代拍脑袋 |
| [Procedural Modeling of Cities — Parish & Müller 2001](https://cgl.ethz.ch/Downloads/Publications/Papers/2001/p_Par01.pdf) / [tmwhere 城市生成](https://www.tmwhere.com/city_generation.html) / [martindevans 道路生成系列](https://martindevans.me/game-development/2015/12/11/Procedural-Generation-For-Dummies-Roads/) | 先定**连接图**（ population 驱动的稀疏边集），再逐边最短路 | "先定该连谁，再修路"的分层顺序 |
| [r/proceduralgeneration: 路网生成讨论](https://www.reddit.com/r/proceduralgeneration/comments/qepohc/creating_a_road_network_between_pois_on_a_map/) / [gamedev.SE: 城市街道网络](https://gamedev.stackexchange.com/questions/122015/how-to-generate-a-city-street-network) | 社区共识: **找路 → 认领边 → 折扣** 循环，重叠段自然成为交叉口 | 与 Rahix 同源，验证方向 |

**一句话归纳**: 业界标准 = `稀疏需求图 → 按序逐边 A* → 已建边全局折扣 → 合并涌现 → 绕行上限兜底`。
我们已有的 A* 核心、cartDist、权重表全部可复用；缺的是**需求图层**和**全局折扣 + DI 闸**。

## 四、新算法设计：「路网优先」(Network-First)

### 4.0 与现状的结构对比

```
现状:  for 每区域格 { for 每聚落 a { for 每候选 b { A*(a,b) → 私有折线 } } }      // 拓扑=邻域全对
重构:  需求图 E = 稀疏边集(聚落骨架) → for 边 in 全局规范序(E) { A* (代价场含全局折扣) → 网络认领 tile }  // 拓扑=需求图
```

### 4.1 第一层: 需求图 (Demand Graph) —— 决定"哪两点该连"

- **终点集**: 全部聚落（非 poi）。
- **边集 = 相对邻域图 (RNG)**: 边 (a,b) 保留 ⟺ 不存在第三点 m 使
  `max(d(a,m), d(m,b)) < d(a,b)`（d 用 cartDist）。
  - RNG ⊇ MST → **骨架必连通**（MST 的任何边都不被支配）→ 现有"最近邻对永不被剪"的
    连通性保证自动继承；
  - RNG 天然稀疏（平面点集平均度 ≈ 2.5）→ **跳板剪枝不再需要**（被支配的冗余边根本不入图）；
  - 实现用 3x3 区域格窗口内的近似 RNG（窗口外的点距离远，几乎不可能支配窗内边；边界误差可接受）。
- **可选增强**: 每 hub 追加最近 k=1 个跨窗邻居（弥补窗口边界），默认关。
- 每条需求边携带: 端点对、`hubBefore` 优先级、六边距。

### 4.2 第二层: 建网序 (Construction Order) —— 决定"先修谁"

全局规范序，与会话访问顺序无关:

```
排序键: (min(hubBefore(a,b)) 的端点等级 降序,  需求边六边距 升序)
```

- 等价于"大城市之间的干线先修，小聚落的支线后接"（延续 v2 以来的 hub 优先原则）。
- **断点续建**: 记录已建边数 `builtEdges`；重启/续建时按同一规范序重放跳过已建边。
  因序是全局规范序（只依赖种子与聚落集合），懒生成下仍是"会话内确定"。
- **性能护栏**: 建网为一次性/分批预算制（沿用现 `maxNew` 机制），单次调用有预算上限。

### 4.3 第三层: 代价场 (Cost Field) —— 决定"怎么走"

对需求边 (a,b) 跑 A*（现 `bfsRoad` 核心 + cartDist 启发 + Dial 桶，全部保留），代价:

```
进入格 t 的代价 =  地形权重 ROAD_W[biome(t)]
                 × 0.5    若 t 是已建路格（全局折扣, 不限走廊）→ 即 ROAD_W_ROAD=2
```

- **取消 `ROAD_REUSE_CORRIDOR` 走廊限制**——绕行问题改由 4.4 的显式闸门兜底，
  不再靠"折扣只在直线上"这种隐式约束（三角张力的解扣）。

### 4.4 第四层: 反绕行闸 (Detour Gate) —— 决定"合并的边界"

对每条建成的边计算 **绕行系数 DI = 路径步数 ÷ 六边距**（[林道标准](https://planningtank.com/transportation/network-connectivity-indices)）:

```
DI ≤ DI_SOFT (1.25): 接受，正常入网
DI ≤ DI_HARD (1.40): 接受，但标记"迂回边"（渲染可用虚线/窄带，视觉提示）
DI > DI_HARD:        该需求边**不建**（无折扣重寻一次，仍超限则放弃）
                     —— 骨架(MST⊂RNG)边例外: 必建，超限也接受（连通优先）
```

- 这是"绕远路"问题的工业标准答案：**合并允许，但每条边的绕行度有硬上限**。
- 比现在的直线走廊优雅：走廊是"空间约束"（会误杀分叉合并），DI 是"质量约束"（只砍真迂回）。
- DI 用整数运算：`步数×10 ≤ 14×六边距` 即 DI ≤ 1.4，无浮点。

### 4.5 表示层: 共享路网 (Shared Network) —— "这段路属于路网"

```
RoadNet:  Map<"q,r",  { routeCount, firstRoute }>     // tile 级: 被几条线路共用（渲染/折扣合一, 取代 roadTileIdx）
Route:    { a, b, tiles: [ [q,r]... ] }               // 线路级: 端点对 + 认领的 tile 序列 (存档/派生用)
```

- **渲染**: 按 RoadNet 的 tile 集画（共享段天然只有一条线），`routeCount ≥ 2` 的段可加宽/加深表达"干线"。
- **存档**: 线路仍按对下发（兼容现有 `regionJson` 协议与客户端按 key 去重渲染），底层 tiles 共享。
- **折扣索引**: `roadTileIdx` 与 `road.tiles` 合并为 RoadNet，消除现在"索引 add-only 与缓存淘汰不一致"的隐患。

### 4.6 第五层: 平滑 (可选, P2)

- tile 级跳点捷径: 若 path[i] 与 path[j] 之间直线逐格代价 ≤ 实际子路径代价，删除中间点
  （等价 line-of-sight 简化）；渲染抖动系数可调 0~4px。
- 动机: 消除均匀地形上的残余细锯齿（六边格几何必然 + 伪随机抖动）。

### 4.7 确定性与性能

| 项 | 策略 |
|----|------|
| 确定性 | 需求图 (种子派生) + 全局规范序 + 全整数代价 ⇒ 会话内严格确定；跨会话因懒生成访问序不同，共享段归属可能不同（与现状同等，文档已标注） |
| 性能 | 需求边数 O(n)（n=聚落, ≈1300/全域）比现在"全对"少一个量级；A* 代价场多一次 RoadNet 查表 O(1)；预算制分批不变 |
| 严格模式 (可选) | 首次触网时按规范序一次性建完全部需求边（全局确定），代价 = 一次性 ~数秒，适合服务端权威预生成 |

## 五、迁移路径

| 阶段 | 内容 | 涉及 |
|------|------|------|
| P0 | 需求图生成器（近似 RNG）+ 建网规范序 + 全局折扣（删 ROAD_REUSE_CORRIDOR）+ DI 闸 | `roadsNear` 拓扑层重写为 `demandEdges()` + `buildNetwork()`；`bfsRoad` 签名不变 |
| P1 | RoadNet 表示合并（roadTileIdx + road.tiles → 一处）；干线渲染（routeCount≥2 加宽） | `mapgen.js` 存储层 + 渲染器 |
| P2 | 平滑 + 折扣防独大（routeCount>K 恢复原价）+ 严格全局成网模式 | 可选增强 |

**保留不动**: `bfsRoad` A* 核心（Dial 桶 + cartDist 启发 + isqrt + 三重剪枝）、`ROAD_W` 权重表、
`hubBefore`、`roadFail`、预算制、`regionJson` 协议、客户端渲染去重。

**删除/取代**: `ROAD_REUSE_CORRIDOR`（被 DI 闸取代）、跳板剪枝 `hopPrune`（被 RNG 需求图取代）、
邻域全对循环（被需求图取代）。

## 六、验收标准

1. **截图场景**: 矿15/粮11/灵2 三角 → 谷中单干道 + 分叉，平行段为 0（人工目检 + 共享率统计: 干线路段 routeCount≥2 占比显著上升）。
2. **直线度**: 均匀地形上 DI ≤ 1.15；整体 DI 分布 p90 ≤ 1.4（脚本统计）。
3. **无迂回合并**: 不存在"骑路导致 DI > 1.4 的线路"（闸门保证, 脚本断言）。
4. **连通性**: 每聚落 ≥1 路；骨架连通（RNG⊇MST 保证, 脚本断言）。
5. **确定性**: 同进程双跑逐键一致；w3 回归 12 项全过（纯函数部分不动）。
6. **性能**: 单 region 冷建 ≤ 250ms；±20 格全域建网 ≤ 现水平 ×1.5。
7. **协议兼容**: 客户端与 C# 存档层零改动。

## 七、风险与备选

| 风险 | 缓解 |
|------|------|
| 全局折扣 + 懒生成 → 跨会话形状漂移比现在更大（折扣不再有走廊封顶） | 规范序近似 + 严格模式可选；现状已有同类标注 |
| 近似 RNG 的窗口边界漏边 → 个别聚落少连 | 每 hub 追加 k 近邻补边（4.1 可选项） |
| DI 闸砍掉的需求边造成"看得见但没路" | 骨架边强制建；非骨架边不建时客户端本就无此路预期 |
| 路复用的路径依赖导致跨配置路数波动（±2%） | 属已知特性, 统计时固定会话序 |
