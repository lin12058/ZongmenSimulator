# 玩家信息表设计（SQLite · JSON 存储）

> 状态：**设计稿 v1**（2026-09-23）。只做设计，未实施业务代码。
> 上游：`docs/玩家宗门放置与城市迭代方案.md` §4.3 —— 那里设计的是**列式 + protobuf BLOB**。
> 本文按你 09-23 的要求改为 **JSON 存储**（「字段可能会频繁改动，不用 protobuf 了」），
> 并把字段清单一次性摊开。

## 〇 一页纸结论

| 项 | 结论 |
|----|------|
| 表名 | `PlayerSect` |
| 粒度 | **一个账号 × 一世 = 一行**（方案 §六 第 6 项已定：P0 一世 1 个宗门）|
| 主键 | `(Account, Round)` |
| 存储 | **混合式** —— 主键与热查询列**提到列上**，其余全部进 `Json TEXT` |
| P0 字段数 | **25 个**（3 身份列 + 11 渲染必需 + 5 玩家特有 + 6 元数据），其中 `resources` 是否落库待定（§3.3）|
| 新增文件 | `Server/Zongmen/Storage/PlayerSectStore.cs`（同步短连接，与 `WorldLedger` 同风格）|
| 必须独立表 | ✅ 与 `World` 表同理 —— 写进 `Data(Key,Value)` 会被 `PruneExcept` 每 2 分钟静默删除 |

### 为什么不能「全部塞进一个 JSON 列」

这是本设计唯一的硬约束，值得先说清：

引擎生成**每个区域包**时都要问一句「这一区域格里有没有玩家宗门」（`GetTileBlock` →
settle 包 → 叠加玩家实体）。这是**热查询**，一个会话内会跑成千上万次。

- **全 JSON**：每区域包要 `SELECT Json FROM PlayerSect WHERE Round=?` 全表读回 + 逐行
  `JSON.parse` ⇒ 解析成本摊在每个区域包上，且**无法用索引**。玩家一多就线性劣化。
- **全列式**：每加一个玩法字段就要 `ALTER TABLE`。SQLite 虽支持，但**你明确说了字段会频繁改** ——
  那这张「玩家资产表」的 schema 就会变成历史包袱，且每次改动都要写迁移。

⇒ **混合式**：把「进 `WHERE` / 进 `ORDER BY` / 做唯一约束」的字段提成列；其余一律进 `JSON`。
判据很简单：**一个字段什么时候该从 JSON 提成列？当它第一次出现在查询条件里。**

## 一 先分家：这张表**不是**什么

三样东西都容易被叫成"玩家信息"，但生命周期完全不同，混在一张表里会立刻出问题：

| 东西 | 生命周期 | 进不进这张表 | 理由 |
|------|---------|-------------|------|
| 玩家**账号档案**（道号、总游玩时长、跨世声望/成就）| **跨世** | ❌ | P0 没有任何玩法承载它。真要做时另开一行（`Round = 0`）或另开表 `PlayerProfile`，别混进来污染"世内资产"的语义 |
| 玩家**在世界里的宗门**（位置 / 等级 / 建筑 / 资源）| **一世** | ✅ **本文的表** |
| 玩家 **UI 偏好**（面板开关、显示项、小地图倍率）| 跨世跨设备 | ❌ | 前端 `web/js/store.js`（localStorage，键 `zongmen.settings.v1`）已经在管。要让它在多设备同步是**另一个需求**，与宗门数据无关 |

**为什么要写这一节**：如果不先分家，最容易发生的错是「玩家换世后宗门没了，但道号还在」
—— 于是有人把道号塞进同一行，结果 `Round` 一变，道号也跟着被「新一行」丢掉。分开就永远不会遇到。

## 二 字段清单

### 2.1 身份与归属（**提为列**）

| 字段 | SQL 类型 | 说明 |
|------|---------|------|
| `Account` | TEXT | = `WsSession.Account`。来源 `MapWsHandler.cs:104` `session.Account = req.Account.Trim()`。⚠ **主键之一**，也是 `PlaceEntity.owner` 的值 |
| `Round` | INTEGER | 对齐 `World.Round`。⚠ **主键之一**，也是唯一的索引键 |
| `Seed` | TEXT | 冗余存。**理由**：区域包生成路径拿到的是 **seed**（`GetTileBlock(seed, i, j)`）而不是 round，存下来省一次 `World` 表的 join，且允许「在旧世界上查看自己的旧宗门」 |

> `Account` 目前是**明文、无 Token 校验**（`LoginRequest{Account, Token}`，`Token` 未使用，
> 只要非空就放行）。⚠ ⇒ **在接真鉴权之前，这张表只能当"本地/局域网可信环境"用**；
> 一旦上公网，任何人都能用别人的 Account 认领/覆盖其宗门。这是**安全问题不是设计问题**，先记在这。

### 2.2 地图实体（JSON 内 —— **必须与 `PlaceEntity` 同名同义**）

这一组字段存在的唯一理由：**让玩家宗门能被当成普通 `sect` 实体画在地图上**。

⚠ **两条通路要分清**（2026-09-23 起）：

| 通路 | 数据源 | 用途 |
|------|--------|------|
| **地图渲染** | `PlayerSect` → `EntityGroup` → `PlaceEntity` → `settleCells` | 把宗门画在图上、算归属势力（与 NPC 聚落**同一条**通路，零改动复用） |
| **本宗面板** | 直接读 `PlayerSect` 表 | 左上角显示**你自己的**宗门 —— 本宗是持久资产，**不在视野内时也要能显示** ⇒ 不读实体层 |

⚠ 旧版的「宗门录」面板（读 `settleCells` 里 `type==='sect'` 的实体）已于 2026-09-23 下线：
面板从「浏览/择宗（从别人的宗门里挑一个）」改成「本宗」。
「查看**其他**宗门/聚落的详情」已抽为独立模块 `web/js/infocard.js`（另一套 UI 体系），
数据源仍是实体层 —— 所以上面这条「同一条通路」对**它**依然成立。

⇒ 玩家宗门落库后，地图渲染与「他人详情卡」都零改动复用；只有本宗面板走表。

| 字段 | 类型 | 必需 | 说明 |
|------|------|:----:|------|
| `id` | string | ✅ | 格式见 **§五**（⚠ 上游写的格式是错的，必须改）|
| `type` | string | ✅ | 恒 `"sect"` |
| `q`, `r` | int | ✅ | 格坐标 —— 位置的**唯一真相** |
| `name` | string | ✅ | 宗门名（玩家输入，需服务端做长度/字符白名单）|
| `owner` | string | ✅ | = `Account`。NPC 聚落此字段恒空 ⇒ 前端可据此区分「我的宗门」|
| `tier` | int | ✅ | 1~3（与 NPC 的 `tier` 同口径：`village=1 / town=2 / city=3`，宗门 1~3）|
| `pop` | int | ✅ | 人口 |
| `state` | int | ✅ | 0 活跃 / 1 被毁 / 2 刷新中 / 3 事件态（与 `PlaceEntity.State` 同义）|
| `style` | string | ✅ | 风格键（`spirit`/`river`/`farm`/… 见引擎 `STYLE_NAME`）|
| `buildings` | array | ✅ | `[{q, r, kind, terrain, tier}]` —— 与 `BuildingDto` **逐字段对齐** |
| `resources` | array | ⚠ | `[{resource, amount}]` —— **存不存见 §三.3** |

### 2.3 玩家特有（JSON 内）

| 字段 | 类型 | 必需 | 说明 |
|------|------|:----:|------|
| `domainR` | int | ✅ | **领地半径**。方案已定**存档而非重算** —— 因为宗门会升阶（`tier` 变），若按当前 tier 重算，会导致「同一座宗门在不同时刻的领地不同」，历史落点合法性无法复现 |
| `stock` | object | ✅ | 库存 `{"粮":1200,"木":340,…}`，键取引擎 `RES_ORDER` 的 8 种（粮/木/矿/渔/炭/灵/丹/器）。⚠ **建议 8 个键全部写全**（缺的写 0），避免"缺失 = 0 还是 = 未知"的歧义 |
| `disciples` | int | ⭕ | 弟子数（P0 可只存一个整数，不存名单）|
| `queue` | array | ⭕ | 建造队列 `[{kind, terrain, q, r, doneAt}]`（P0 可空数组）|
| `chronicle` | array | ⭕ | 编年（开宗 / 升阶 / 被袭…）。**P0 建议留字段但只 append 少量**，因为它是"玩家资产"里最容易被要求加的一个 |

### 2.4 工程元数据（**前三个为列**）

| 字段 | 位置 | 说明 |
|------|------|------|
| `Ver` | 列 | 乐观锁。客户端提交带 `Ver`，服务端 `UPDATE … WHERE Ver = ?` ⇒ 防多标签页互相覆盖 |
| `UpdatedAt` | 列 | 毫秒时间戳。要按时间排序/做清理，所以提列 |
| `IdemKey` | 列 | 幂等键，**唯一索引（部分索引，允许 NULL）** ⇒ 网络重发不会落两个宗门 |
| `BornAt` | JSON | 落定时刻（展示用，不参与查询）|
| `tickAt` | JSON | 上次结算时刻。⚠ **只有做"离线收益"时才需要**，见 §八 |
| `v` | JSON | **JSON 结构版本号**（整数，从 1 起）。字段结构变化时读路径按 `v` 分支迁移 ⇒ 比 SQL 迁移好写得多。**P0 就要有** —— 后补的代价是"已落库的旧行没有 `v`，不知道该按哪版解"|

## 三 关键纪律：**不存派生量**

这条在本工程已被反复验证过（`roadFail` 的注释写着「派生量而非状态」）。玩家表同样适用：

### 3.1 ✗ 不存 `x` / `y`

`PlaceEntity.X/Y` 是 `Q/R` 经 `tileToWorld(q,r)` 的**派生量**（引擎 `mapgen.js:236`）。
服务端每次下包现算即可。存了就有**两处真相**，一旦有人改了 Q/R 忘了改 X/Y，地图上就会出现
「数据说在东边、画在西边」—— 而且不崩溃。

### 3.2 ✗ 不存 `styleName`

`STYLE_NAME[style]` 查表的派生量（引擎 `mapgen.js:685`）。同理。

### 3.3 ⚠ `resources` 与 `stock` 的关系 —— **必须想清楚，否则会有一致性 bug**

NPC 聚落的 `resources` 是**从建筑聚合派生**的（`townNet()`：遍历 `plan.resources` 求和）。
若玩家宗门 100% 照搬，那么：

- **甲案**：**不存** `resources`，每次按 `townNet` 口径从 `buildings` 现算。
  - 红利：与 NPC 100% 同构，**零一致性风险**；前端拿到的形状天然一致。
  - 代价：玩家**不能有消耗**（建造花资源、被掠夺、上缴），因为一旦有消耗，"当前值"就不再是建筑的纯函数。
- **乙案**：**存** `stock`（净库存），`resources` 变成 `stock` 的投影。

**我的判断：走乙案。** 理由：宗门经营模拟里资源**必然有消耗**（这是玩法本身），
甲案在第一次"建造要花灵石"时就会被迫加字段。但**要把纪律写死**：

> `buildings` 是**真相**，`stock` 是**当前值**。产出速率仍由 `buildings` 派生（不存速率），
> 只有"当前存量"落库。任何"产出速率"字段都不许进 JSON —— 那是派生量。

### 3.4 ✗ 不存"自动生成聚落"的任何东西

按 seed 可复现（`mapgen.js` 是纯函数）。玩家的存在**不改变**自动聚落 —— 这正是方案
§2.4 的决策（玩家实体不进 `settlementsFor` 的抑制逻辑），也正因为如此，
「附近城市**不需要**重算」（见方案 §3.6）。

## 四 表结构

```sql
CREATE TABLE IF NOT EXISTS PlayerSect (
    Account   TEXT    NOT NULL,              -- 玩家身份 (WsSession.Account)
    Round     INTEGER NOT NULL,              -- 第几世 (对齐 World.Round)
    Ver       INTEGER NOT NULL DEFAULT 1,    -- 乐观锁
    UpdatedAt INTEGER NOT NULL,              -- 毫秒时间戳 (排序 / 清理用)
    IdemKey   TEXT,                          -- 幂等键 (可空)
    Json      TEXT    NOT NULL,              -- §2.2 + §2.3 + BornAt/tickAt 全在这里
    PRIMARY KEY (Account, Round)
);

/* 「取某一世的所有玩家宗门」是区域包生成路径上的热查询 ⇒ 必须有 */
CREATE INDEX IF NOT EXISTS IX_PlayerSect_Round ON PlayerSect(Round);

/* 幂等: 只约束非空值 (SQLite 的部分索引) */
CREATE UNIQUE INDEX IF NOT EXISTS IX_PlayerSect_Idem
    ON PlayerSect(IdemKey) WHERE IdemKey IS NOT NULL;
```

### 为什么这几列**不**提出来（而不是"懒得提"）

| 候选字段 | 为什么留在 JSON |
|---------|----------------|
| `q` / `r` | 查询是「**这一区域格**里有没有玩家宗门」，而**区域格 ≠ 瓦片格**（`REGION_M=18`）。用 `q/r` 做索引要写 `BETWEEN` 区间且与区域格边界错位。**正确做法是内存镜像 + 按区域格建索引**（§六），根本不用查库 |
| `tier` / `state` | 同理 —— 读路径不查库，写路径只按主键。等它们真的进 `WHERE` 再提 |
| `domainR` | 只有落点校验用，且校验发生在**内存镜像**上 |

## 五 ⚠ 必须修正上游的一处错误：`EntId` 的格式

上游 `docs/玩家宗门放置与城市迭代方案.md` §4.3 写的是：

```sql
EntId TEXT PRIMARY KEY,   -- p_{round}_{n}      ← ❌ 错
```

**这个格式会让引擎静默失效。** 证据（`Server/Zongmen/Engine/js/mapgen.js`）：

```
:1209   id: i + '_' + j + '_' + k,                    // NPC 聚落: {区域i}_{区域j}_{序号}
:1221   id: i + '_' + j + '_p',                       // 秘境 poi: {区域i}_{区域j}_p
:1651   var pAp = pA.id.split('_'), spk = pAp[0] + ',' + pAp[1];
        var sk = skels[spk] || (skels[spk] = skeletonEdgesFor(+pAp[0], +pAp[1]));
```

即**引擎会反解 id 的前两段为区域格坐标**（`+pAp[0]` / `+pAp[1]`），用它去取骨架边。

若 `id = "p_3_1"`（上游写法），则 `+pAp[0]` = **`NaN`** ⇒ `skeletonEdgesFor(NaN, 3)`
⇒ **不抛异常、不报错、静默扫出空池**。这类 bug 的表现是"路网莫名其妙连不上"，
排查成本极高。这是本工程已经栽过一次的坑型（"注入静默无效"，方案 §3.2 坑 E）。

**正确格式**：

```
{区域i}_{区域j}_{后缀}
```

- 前两段**必须是区域格坐标的数字串**（负数带 `-` 无妨，`Number()` 能转）；
- 后缀**不能是纯数字**（会与 NPC 聚落的序号 `k` 撞）；
- 后缀**不能是 `p`**（已被 poi 占用，且 `i_j_p` 有"同格唯一秘境"的语义）；
- 建议后缀 `u{序号}`（`u` = user）：`12_-3_u1`。同格多宗门时靠序号区分。

> ⚠ 一并在实现里加一条**守卫**：`PlayerSectStore` 落库前断言
> `Number.isFinite(+id.split('_')[0]) && Number.isFinite(+id.split('_')[1])`，
> 不满足就拒绝写入并报错。这比事后在路网里找幽灵便宜得多。

## 六 接口：与引擎 / 前端的对接

### 6.1 读路径：**内存镜像**（不可省）

`MapWorldService` 生成区域包时**绝不能查库** —— 每区域包一次 SQLite 往返会把方案 §3.6
实测的 405 ms 同步重算直接毁掉。

做法照 `WorldLedger`：**惰性全量加载进内存镜像**（`List<PlayerSectEntry>`），
按 `Seed` + **区域格**建索引。量级：一个账号一世一行，几百到几千行，一次读尽最省心。

```
落定 / 升阶 / 拆除  ⇒  写库 + 同步更新内存镜像（同一把锁内，保证读到的立即是新值）
```

> ⚠ 为什么必须同步更新镜像而不是"下次加载时刷新"：`MapWorldService` 的区域包缓存是
> **二级缓存（内存 LRU + SQLite）**。若镜像滞后，会出现「落定成功 → 立刻重拉 → 拿到不含
> 自己宗门的包」的竞态。这与 `WorldLedger` 头注释里「走写队列会让『点确定 → 立刻刷新』
> 出现读到旧库的竞态」是同一条教训。

### 6.2 传引擎：形状必须能被 `settlementsFor` 的消费方直接吃

`MG.setExternalSettlements(list)`（方案 §2.4 新增出口）吃的是**聚落对象数组**。
本表 JSON 的形状已与之对齐（`id/type/q/r/name/pop/owner/tier/state` + 足迹）。
⚠ `x`/`y` 由**引擎侧现算**（`tileToWorld`），不要从 C# 传 —— 见 §3.1。

### 6.3 下前端：并进 settle 包

玩家宗门以 `PlaceEntity` 形态并入 `EntityGroup`（与 NPC 聚落同一个数组），
由 `GetTileBlock` 从内存镜像合并。这样：

- 前端**零改动**就能画它（`settleCells` 里 `type==='sect'` 的实体）—— 地图渲染与
  归属势力两处都自动带上；
- ⚠ 左上角「本宗」面板**不走这条路**：它的数据源就是本文的 `PlayerSect` 表
  （本宗不在视野内也要能显示）⇒ 两条独立通路，别指望"进了 settle 包面板就有了"；
- `owner` 非空 ⇒ 前端可加"这是我的宗门"的视觉区分（P2）。

## 七 生命周期

| 事件 | 动作 | 镜像 / 缓存 |
|------|------|------------|
| **落定** | `INSERT`（带 `IdemKey`）；随后走方案 §3.3 的同步重算 | 更新镜像 ⇒ 区域包失效 + `BumpBlockRev` + `roadVer++` |
| **升阶**（tier 变）| `UPDATE` + **显式更新 `domainR`** 并**重新校验周围是否已被侵入**（方案 §2.5 所述）| 同上 |
| **改名 / 换风格** | `UPDATE`，`Ver++` | 只需 Settle 位失效（道路无关）|
| **拆除** | `UPDATE state=1`（**软删**，不 `DELETE`）| 按边清 `roadCache`/`roadFail` + `roadVer++` |
| **换世**（`Round+1`）| **不动历史行** —— 旧世的宗门留在旧 `Round` 上 | 新世从零开始 |
| **清库** | ⚠ 后台 `PruneExcept` **够不着本表**（它只 `DELETE FROM Data`）。⇒ 历史 `Round` 的行会**永久累积**，需要一个显式的保留策略（见 §八）|

## 附：本设计**没做**的事（避免后续被当漏项）

- ✗ 玩家账号档案表（跨世）—— §一 已分家，P0 不需要
- ✗ 玩家 UI 偏好的服务端同步 —— 前端 `store.js` 已管
- ✗ 多宗门（P0 一世 1 个）
- ✗ 宗门间的外交 / 战争 / 弟子名单

> ⚠ 一处**曾经想省、但决定不能省**的：JSON 结构版本号 `v`。
> 初稿把它列进"没做的事"，理由是"P0 字段还少"。这是错的 ——
> 它的价值**只在于先有**：一旦库里有了一行没带 `v` 的 JSON，之后任何结构变化都只能靠
> "猜它是不是旧结构"。加一个整数几乎零成本，所以已提到 §2.4。参见 `Res_ORDER`/`STYLE_NAME`
> 这类"版本化常量"在本工程历来都要留后路。
