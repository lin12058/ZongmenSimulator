## 一、顶层就两棵树

```
squad                     小队 —— 有哪些人, 每个人在干什么
├── id / name / capacity
└── members[]
    ├── 身份   id name role gender age realm exp mood
    ├── 天赋   root{order,v,main}  talents{v,total}  traits[{n}]
    ├── 携带   equip{weapon,offhand,body,head,talisman}  queue[]  queueFrom
    ├── 能力   arts{slots[{n,rank,cost}],cap,from}
    ├── 状态   vit{hp,mp}
    ├── 在干什么 activity{kind,jobId,taskName,progress,done,since,note}
    └── 派活   prio{jobId: 1..4|0}

bag                       背包 —— 有哪些东西 (全队共用一套)
├── capacity / cols / rows
└── items[]
    ├── id (全局唯一)  cell (整数=第N格 / null=穿戴中)  wornBy (只读输出)
    └── name kind ch q w atk def acc hp mp heal qty qtyMax
```

## 二、四条硬约定

| # | 约定 | 违反的后果 |
|---|---|---|
| 1 | **只传源数据，不传派生值**。气血/攻击/防御/命中/闪避/负重全部由前端 `attrs()` 现算 | 传了会被静默覆盖，白改 |
| 2 | `realm` / `role` / `age` / `gender` 是**纯展示文本**，不参与任何公式 | 改境界不会变强 |
| 3 | **装备用 itemId 引用**，物品本体只在 `bag.items` 出现一次 | 对象搬运式的旧写法会产生产生"同一件东西两份" |
| 4 | **id 全局唯一且由服务端生成**（建议前缀 `srv-`） | 与前端调试自增 `i1/i2` 撞车 ⇒ 两件不同东西被当成同一件 |

## 三、`activity` 是"在干什么"的全部

```json
{ "kind": "work", "jobId": "gather", "taskName": "采灵草",
  "progress": 43, "done": 12, "since": 1732470000000, "note": "" }
```

| 字段 | 说明 |
|---|---|
| `kind` | `work` 干活 / `idle` 空闲 / `rest` 静养 / `combat` 交手 / `away` 外出。**空闲也必须给 `kind:"idle"`** |
| `jobId` | 对应工种表 id；`kind != work` 时应为 `null` |
| `taskName` | 给玩家看的具体动作（不是工种名） |
| `progress` | 0~100 |
| `done` | 累计完成件数 |
| `since` | 开始时间 Unix ms，0 = 未知 |
| `note` | 卡住原因（灵草不足 / 伤势未愈），面板直接显示 |

## 四、物种表 / 槽位 / 品类

- 六道 key：`body` `qi` `mind` `gear` `pill` `array`（体/气/神/器/丹/阵），每道 6 项，单项 ≤60，总量 90~180。
- 装备槽：`weapon` `offhand` `body` `head` `talisman`；`equip.talisman` 必须等于 `queue[0]`，`queue` 长度 1~4。
- 物品 `kind`：`weapon` `offhand` `body` `head` `talisman`（可穿戴）/ `pill` `material` `book`（不可穿戴）。
- 品阶 `q`：1~6（一至六品）。

## 五、HTTP 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/crew` | 取当前小队契约。没有数据 → **404** `{error:"no squad"}` |
| PUT | `/api/crew` | 全量覆盖（导入存档 / 演示初始化）。**严格校验**：成员空、id 重复、格位越界/冲突 → 400 |
| POST | `/api/crew/patch` | 增量。**宽松**：允许两次请求间的瞬时格位冲突 |
| DELETE | `/api/crew` | 清空（调试） |
| GET | `/api/crew/schema` | 字段说明（联调用，不含业务数据） |

### patch 的形状

```json
{
  "squad":   { "name": "外门三队", "capacity": 9 },
  "members": [ { "id": "srv-p-1", "activity": { "kind": "work", "jobId": "gather",
                 "taskName": "采灵草", "progress": 43 } } ],
  "removeMembers": ["srv-p-9"],
  "items":   [ { "id": "srv-i-1", "cell": 12 } ],
  "removeItems":   ["srv-i-9"],
  "jobs":    [ "…整表替换…" ]
}
```

语义：`members` / `items` 按 id 做**字段级合并**（对象递归、数组整体替换），id 不存在则新增；`remove*` 按 id 删除。

**为什么服务端不用 DTO 接 patch**：只有"键是否存在"才能区分「没传这个字段」与「显式传 0 / null」。先反序列化成 C# 类，缺失的 int 会变 0，合并就会把原值抹掉。

`removeItems` 会**自动清掉**成员身上对它的引用（`equip.* = null`、从 `queue` 里移除），避免前端报"引用不存在的物品"。

## 六、校验分级

| 级别 | 触发 | 处理 |
|---|---|---|
| **error** | 缺 `squad`/`bag`/`members`/`root.v`/`talents.v`；id 重复；装备或队列引用了不存在的物品；特质正反同现 | **拒绝装载**（`hydrate` 返回 `state:null`） |
| **warning** | 灵根合计 ≠100（按比例归一）；`talents.total` 与各道合计不符（以实际为准）；特质条数越界；天赋总量越界；`cell` 越界或格位冲突（后到者自动找空格）；缺 `activity`/`vit`；`exp=0` | 修正后**照装**，返回 `warnings[]` |

⚠ `validate()` 会**就地修正**越界/冲突的 `cell` 改成 `null`（这样 `hydrate` 能接着用同一份对象）。要保留原值请先深拷贝。

⚠ **格位冲突只能是 warning**：后端两次 patch 之间必然存在瞬时冲突（把 A 挪到 B 的格子，再让 B 走开），判 error 会让整份存档都装不进去。

## 七、前端怎么用

```js
// 1) 全量装载
const res = CrewBridge.mount(contract);          // { ok, errors, warnings, state }
CrewBridge.mount(contract, { localTick: false }); // 接后台数据时必须关本地推进

// 2) 增量
CrewBridge.patch({ members: [{ id: 'srv-p-1', activity: { kind: 'work', jobId: 'gather', progress: 43 } }] });

// 3) 玩家改了数据 → **只发事件**，不发整份契约（第十四节）
CrewBridge.onEvent(ev => {
  // ev: { v, id, seq, base, at, type, data }  —— data 里只有 id 和目标值
  fetch('/api/crew/events', { method: 'POST', headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ base: ev.base, events: [ev] }) });
});

// 4) URL 开关：?crewapi=1 → GET /api/crew 并装载；?crewapi=/自定义路径 也行
```

⚠ **2026-11-25 起上面的旧写法作废**：`onChange` 曾带 `ev.contract`（整份契约）并 `PUT /api/crew`，
等于把业务结果搬到后端、还会覆盖服务端正在跑的 `activity`。现在只有事件，见**第十四节**。
`PUT /api/crew` 降级为「导入存档 / 调试」专用。

包装手法不变：`CrewBridge` **替换 `CrewModel` 上的写函数**来截获（面板持有的是对象引用，属性被替换后自然走包装版），
所以 UI 代码可以零改动。区别是现在包装的是 **9 个**写函数、发的是**单条事件**（清单见 §14.9）。

## 八、⚠ 接后台数据必须关本地推进

`crew-panel.js` 的 tick 每 500ms 调 `M.step()`，它会**给空闲的人自动派活**，把后端下发的 `activity` 覆盖成前端编的。

- `CrewBridge.autoMount()` 已自动 `setLocalTick(false)`；
- 手动装载请写 `CrewBridge.mount(c, { localTick: false })`；
- URL 带 `?crewapi=` 时面板在 init 阶段就关掉（不等 fetch 回来，避免启动那几百毫秒派活）。

验证方法：看头行「在役 N」是否等于后端 `activity.kind === 'work'` 的人数。

## 十二、多小队（前端已实现 · 2026-11-24 第六轮）

### 前端现在的形态

- `state.pawns` **仍是全量弟子**，小队只存 id 引用与顺序：
  `state.squads = [{ id, name, members: ['p3','p1',…] }]` + `state.curSquad = 'sq1'`。
  好处：`attrs / step / teamWeight / probe` 一行都不用改，队伍页只负责"按 id 取人 + 按 members 排"。
- 队名 ≤ **4 字**（`M.SQUAD_NAME_MAX`，写入口一律过 `M.squadName()`），默认 `小队 / 二队 / 三队…`，最多 6 支。
- 入口 = **每支小队一条独立纸签**，从上到下堆叠在右缘（原单条复制成多份），每条尾跟本队人数；
  当前队那条**放大成 tab**（scale 1.12 + 朱砂字 + 更亮纸面）；点哪条 ⇒ 打开面板并滚到那一段。
  **点某一个队名 ⇒ 打开面板并滚到该小队那一段**（该段闪一下朱砂高亮）。
- 队伍页 = **各小队纵向分段**（用户 23:54 口径：不是横条切换，是从上到下排开、点名字跳过去）：
  - 每段一个队头（`≡` 拖动把手 + 队名 + 人数 + 负重 + `×`）＋ 该队弟子行；
  - 队头**上下拖动**改小队顺序，弟子行**上下拖动**改队内站位（两互不干扰，靠 handle 区分）；
  - 双击队头就地改名；`×` 二次确认解散（人回第一队）；底部 `＋ 新建小队`；
  - 空队显示 `.rp-empty.sm` 提示块，不留白。
- 兜底：`M.normalizeSquads(state)` 幂等 —— 补队、修名、成员去重、把"没归队"的弟子塞回第一队，每次渲染前都能安全调。
- 持久化：`ZMStore` 键 `crew` 里多了 `squads[]` 与 `curSquad`；`?squads=N` 是演示参数且**优先于存档**。
- 判据：`verify/_crew_harness.html?test=1` 里 I 段（入口条横排 / 队名截断 / 分段渲染 / 移队 / 队头拖动 / 队内拖动 / 点击跳转 / 二次确认 / 落盘）。

### 接后台要改的三处（当前**没做**）

1. 契约从单 `squad` 升为 `squads[]`：`squads: [{ id, name, members: [memberId…] }]`；`curSquad` 属前端本地偏好，不必上服务器。
2. `crew-bridge.js` 的 `toInner / toWire / applyPatch` 要按数组映射；服务端 `CrewEndpoints` 目前固定 `squad-1`，需把 id 提到 URL 或 body。
3. ⚠ `setSquad(data)` 会整体替换 `state` ⇒ 服务端每次 patch 都会冲掉前端拖出来的顺序。接后台时**服务端必须保存 members 数组顺序**（数组序即站位），否则拖完一刷新就回原样。

## 十三、弟子归属 / 位置标记 / 空队与背包合并（2026-11-25）

### 数据里到底有没有「这个人在哪队、第几位」

- **不存字段**：弟子对象上没有 `squadId`，也没有 `pos`。唯一真源是 `state.squads[i].members` 的**数组顺序** ——
  下标就是站位（0 = 队首）。
- 读法统一走两个派生接口，别自己再写一套遍历：
  - `M.locatePawn(state, pawnId)` → `{ id, squad, name, pos, size }`（找不到返回 `null`）
  - `M.probe(state).assign` → `[{ id, squad, pos } …]`，覆盖全员，供验收/联调直接读
- 写操作只有 `M.movePawn(state, pawnId, toSquadId, toPos)`：
  - `toPos` 缺省 = 插到目标队末尾；目标队**为空也照样能收**（`toWasEmpty` 标记）
  - 返回 `{ ok, same, from, to, pos, fromEmpty, toWasEmpty }`
  - ⚠ 不要另存一份 position —— 两份数据一定会漂，拖一次就错位

### 接口现状（`crew-bridge.js`，**还没升级**）

- 仍是**单个** `squad`：`{ id, name, capacity, members: [member…] }`，`members` 顺序即站位；
  **没有** `squads[]`，也**没有** `position / squadId` 字段。
- 要多队必须升级契约（§12 的三处）：`squads: [{ id, name, members: [memberId…] }]`；
  服务端按数组顺序原样保存。若日后想给每条 member 加显式位置，只能由数组下标**派生**输出，不许入库双写。

### 空小队 / 移空 / 背包合并（用户 2026-11-25 明确要求）

- **空队不是死路**：空小队也渲染一个真的 `.rp-list.empty` 落点（高度 ≥40px），
  拖弟子行进去、或走行尾「移」都能进人。新建的空队立刻可用。
- 空队不会被自动删除；只有队头 `×` 二次确认才解散（人回第一队）。
- **移空之后背包合并**：`M.movePawn` 返回 `fromEmpty=true` 时，面板提示
  「『X』已空 · 负重 0（物品都在宗门背包，不会丢）」。
  ⚠ 当前全宗**只有一份背包**（`state.stash`，6×8=48 格），所以没有分队背包要搬；
  这条规则的实质是「队伍空了，物品和负重不许跟着蒸发」。将来若改成分队背包，
  移空时必须把该队的 bag 全量并入主背包（件数守恒、负重守恒），并保证不丢件。
- 判据（`verify/_crew_harness.html?test=1` 的 J 段）：标记覆盖全员 / 标记=下标 /
  跨队拖动人数守恒 / 空队接人 / 空列表高度 / 移空后队伍仍在 / 负重 0 /
  背包件数不变 / 总负重不变 / 每段行数=该队人数。

## 十四、事件流（Event-only · 2026-11-25 定案）

### 14.0 为什么改成"只发事件"

旧写法（第七节 step 3）：`onChange` 回调里塞 `ev.contract`（**改完的整份契约**）→ `PUT /api/crew`。
问题有三个：

1. 前端把"结果"发给后端，后端只能照抄，**业务规则被复制到两端**，一改就漂。
2. 整份契约里含着当前 `activity / vit`，一次装备会把服务端正在跑的模拟结果覆盖回去。
3. 冲突无法定位——两份全量数据谁对？只能整份覆盖。

新口径：**一次用户交互 = 一条事件**，事件只说"谁对什么做了什么"，服务端算结果、自己推进 `rev`。
前端不推导、不搬运状态，只发意图。

### 14.1 编码：事件走 JSON，不走 protobuf

| | 用什么 | 理由 |
|---|---|---|
| 地图 WS 帧 | **protobuf**（`[1B type][payload]`） | 每帧多次/秒、字段热、几十 KB |
| 小队事件 | **JSON**（`application/json; charset=utf-8`） | 单条 150~400 B、低频（人手点一下）、要能直接读日志与回放 |

- **不为事件新增 `.proto`**：多一套 schema 就多一套版本协商，收益为零；`v` 字段已够做兼容。
- 不 gzip（< 1 KB，压了反而多耗 CPU）；一次批量 > 20 条再考虑。
- 契约本体（`/api/crew` 的 GET 返回、导入存档）沿用现有 JSON，**不要求**改成 protobuf。

### 14.2 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/crew/events` | 提交 1~N 条事件，返回新 `rev` 与逐条结果。**日常唯一写通道** |
| GET | `/api/crew?since=<rev>` | 增量拉取（重连补差）；不带 `since` 返回整份契约 |
| PUT | `/api/crew` | ⚠ 降级为**导入存档 / 调试**专用，前端日常不调用（否则两套冲突规则并存） |

请求：

```json
{ "base": 118,
  "events": [
    { "v":1, "id":"evt_01H8X3", "seq":42, "at":1732500000000,
      "type":"member.move", "data":{ "pawnId":"srv-p-3", "toSquadId":"sq2", "toPos":0 } }
  ] }
```

成功：

```json
{ "ok": true, "rev": 119,
  "results": [ { "id":"evt_01H8X3", "ok": true, "code": null, "data": null } ] }
```

冲突（`base` 落后）：

```json
{ "ok": false, "rev": 121, "resync": true,
  "results": [ { "id":"evt_01H8X3", "ok": false, "code":"conflict" } ],
  "state": { "…整份契约，字段同第二节…" } }
```

### 14.3 信封字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `v` | int | ✔ | 信封版本，当前 `1`；未知版本整条拒绝 `bad-version` |
| `id` | string | ✔ | **幂等键**，客户端生成（ULID/`evt_` + 随机），服务端保留 5 分钟 |
| `seq` | int | ✔ | 客户端单调序号（每次 +1）；有缺口 = 客户端丢包，重连走 `GET ?since=` |
| `base` | int | ✔ | 客户端看到的 `rev`；与当前不符 ⇒ `conflict` + `resync` |
| `at` | int | ✔ | 客户端时间 Unix ms（**只作审计**，排序/超时一律用服务端时间） |
| `type` | string | ✔ | 见 14.4 |
| `data` | object | ✔ | 只放 **id + 目标值**。⚠ 禁放派生值（负重/攻防/百分比/人数） |

⚠ 命名对照：事件里的 `pawnId` 就是契约里的 `members[].id`（前端内部沿用 `pawn` 这个词，进出契约一律叫 member）。
`itemId` 就是 `bag.items[].id`。**事件里不允许出现 `cell` 下标以外的位置描述**——背包格用 `cell`，队伍站位用 `toPos`。

### 14.6 一次手势 = 一条事件

| 交互 | 事件数 | 何时发 |
|---|---|---|
| 拖队头到新位置（过程中跨过 N 个段） | **1** | 松手（`pointerup`） |
| 拖弟子行到队内新位置 / 拖到别队 / 拖进空队 | **1** | 松手 |
| 行尾「移」→ 点目标队 | **1** | 点目标队那一下 |
| 双击队头改名 | **1** | 回车 / 失焦提交（Esc 不提交 = 0 条） |
| 点队头 `×` → 再点「确认」 | **1**（第一次那下 0 条） | 第二次点击才发 |
| 点任务矩阵格（连点 4 次） | **4** | 每次点击各一条，`value` 是算好的目标值 |

拖动过程**零事件**——不要在每个"越过中线"的时刻发，那是给自己造流量和竞态。

### 14.7 幂等 / 顺序 / 事务

- **去重表**：`CrewEvent(Id TEXT PRIMARY KEY, At INT)`，写入前查、成功后落，后台定期删 5 分钟前的行。
  ⚠ 必须是**独立表**（塞 `Data(Key,Value)` 会被 `PruneExcept` 清空，同 `Crew` / `WorldLedger` 的坑）。
- **重复 `id`**：直接返回 `results[].ok = true` 并**跳过执行**（不报错，让重试无脑重发）。
- **顺序**：同一批按数组顺序在**一个事务**里跑；单条失败只回滚该条，其余照常，`ok` 为整体是否全成功。
- **`seq` 缺口**：服务端记录每客户端最大 `seq`；发现跳号 ⇒ 响应里带 `"gap": true`，前端下次先 `GET ?since=rev` 补差再发。
- **`rev`**：存 `Crew` 表新列 `Rev INT`，每成功一批 +1；`GET` 一并返回。

### 14.8 冲突策略（已定：乐观 + 服务端权威）

1. 前端点下/松手 → **立刻改本地**并渲染（不等网络）。
2. 攒 300 ms 合并窗口 → 发 `POST /api/crew/events`（带 `base = 本地 rev`）。
3. 服务端 `base != rev` → `conflict` + `resync: true` + 整份 `state`。
4. 前端**整份重装**（覆盖本地），toast「已被别处改动，已同步」，本地 `rev` 跟上。
5. 单条业务拒绝（如 `bag-full`）→ 不回滚本地渲染，按 `code` 提示 + 强制重装该队。

**唯一不强求乐观的**：`squad.create`。等一个往返拿真实 `squadId`（否则要给临时 id 做映射，
后续 `member.move` 还得等建队完成，复杂度不划算）。其余 8 条全乐观。
