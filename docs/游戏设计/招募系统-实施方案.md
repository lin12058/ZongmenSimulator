## 〇、一页纸结论

**玩家在聚集地打探候选弟子**：花「招募值」刷新候选池、花「招募值」把人招进小队。
招募值随**游戏年份**累计（每年按**宗门影响力**结算，当前影响力固定 10 ⇒ 每年 +10），余额 **30 年产量封顶**（当前 = 300 点），花掉后可再随时间攒回来。
池子由**确定性随机**生成、状态**落库** ⇒ 刷新网页 / 断线重连看到的都是**同一批人**；
想换一批只能**花点数刷新** —— 这就是「防刷」的全部机制。
招募入队：**选一支现有小队合并进入**；**没有小队时自动新建一支**。
**一旦有队伍，招募点就被锁在队伍驻地**：只能在队伍所在的聚落招人，跑到别的城镇招不了（没有队伍时才不限地点）。

| 项 | 定案 |
|---|---|
| 招募值速率 | **每年 = 当前宗门影响力**（当前影响力 10 ⇒ 每年 +10；每 360 tick 结算一次，现实 1 游戏年 ≈ 6 分钟） |
| 余额上限 | **30 年产量**（当前 = 10 × 30 = **300 点**；影响力变化时上限同步 = 产量 × 30） |
| 刷新成本 | **-30 点 / 次**（换一整批候选人，剩余的旧候选作废） |
| 招募成本 | **-50 点 / 人**（堵住「跑图到多个聚落免费看池挑苗子」的口子） |
| 初始值 | **50 点**（首次建档赠送，进游戏即可招 1 人） |
| 可招募地点 | **所有聚落实体**（村落 / 渔村 / 坊市 / 仙城 / 他人宗门 / 自家宗门），野外不可；**已有队伍时仅限该队驻地所在聚落** |
| 池量 | 按聚落类型：村落 3~4 / 坊市 4~6 / 仙城 6~9 / 宗门 2~5 / 渔村 3~5（`CFG.POOL`） |
| 出身 | **按聚落类型偏置**（渔村多渔家、仙城多书生…，见 §4.2） |
| 防刷 | 种子 = `f(worldSeed, settleId, rollNo)`；`rollNo` + 池子快照**落库**；刷新页复现同池 |
| 入队 | 合并进入现有小队 / 无队自动新建（队上限 6 支、队容 9 人）；**队员入哪支队，就必须在哪支队的驻地招募** |
| 队伍驻地 | 每支小队记一个 `settleId` 驻地：**建队时自动绑定当次招募聚落**；有队伍 ⇒ 只能在驻地招募（`wrong-settle`） |
| 弟子数 | **= 所有小队人数合计**（不另存计数，由 Crew 契约派生） |
| 落库 | 新表 `RecruitPoint`（点数，全宗一份）+ `RecruitPool`（池子，每聚落一份）—— 均独立表 |
| 接口 | 4 个端点：`state` / `pool` / `roll` / `hire`（专用端点，**不走**事件流） |

## 一、玩法闭环

```
① 打探（免费·幂等）        ② 刷新（-30 点）           ③ 招募（-50 点/人）
点聚落 → 打开招募面板   →   换一整批候选人        →   选人 → 选小队 → 入队
  首次自动生成 rollNo=0       rollNo+1，旧池作废         标记 taken，写入 Crew 契约
  池子落库（此后固定）        点不够 → 拒绝               无队员 → 建队（驻地=此地）
                                                           有队伍但在别处 → 拒绝
```

- 招募值在**游戏时间**里自然累积 —— 挂机也在涨（世界时钟服务端持续走），速率 = 宗门影响力。
- 玩家只有两个消耗途径：**刷新**（换样本）与**招募**（要人）。不花不扣。
- 同一批池子里的人可以连招多个（每个各扣 50 点）；招走后该位置灰「已入宗门」，**不重排**（对齐 `Chargen` §九）。
- **打探免费但招募受限**：没有队伍时随便哪个聚落都能招（招了就在当地建队）；一旦有队伍，
  只能回到**那支队伍的驻地**招人 —— 想换地方招，得先把队伍挪过去（队伍移动是后续功能，见 §十三）。

## 二、招募值

### 2.1 惰性结算（Lazy Settlement）

不挂 TickJob。四个入口（`state` / `pool` / `roll` / `hire`）在服务端**先结算再算账**：

```
deltaTicks = nowTick - lastTick                 // nowTick 取 WorldClockStore（当前 seed+round）
years      = floor(deltaTicks / 360)            // 整年才计息，不足 1 年的余数保留
perYear    = Influence(account, round)          // 每年产量 = 宗门影响力（当前恒 10）
cap        = perYear * 30                       // 30 年产量封顶（当前 10 × 30 = 300）
gain       = years * perYear
points     = min(cap, points + gain)
lastTick  += years * 360                        // ⚠ 只推进整年，余数留在 lastTick 上
```

| 纪律 | 原因 |
|---|---|
| 余数必须留在 `lastTick` | `lastTick = nowTick` 会吞掉不足一年的零头，每年都少算 |
| 只用整数 tick 运算 | 不引入浮点；`gain` 由 `floor` 出，天然无小数 |
| **`perYear` 与 `cap` 必须同源** | 都是 `Influence()` 算出来的：影响力变了，产量和上限一起变，否则「30 年量」的语义会漂 |
| 影响力**不建历史曲线** | 整段 `deltaTicks` 一律按**当前**影响力算：入口调用频繁 ⇒ delta 通常不足 1 年，误差可忽略；只有长期离线跨了影响力变化才会略偏（P0 接受，不引入事件表）。下调导致 `points > cap` ⇒ 夹断到 cap，不补不退 |
| `Influence()` 保底 1 | 影响力为 0 会让招募值永久冻结、玩家卡死；下限 1 / 年 |
| 封顶只夹 `points`，**不停表** | 「余额上限」语义：花掉后靠新时间回血（用户 2026-11-25 定案） |
| 结算先于一切校验 | roll/hire 都要用结算后的最新余额判断 |

### 2.2 常量表（建议初值，集中一处便于调）

| 常量 | 值 | 说明 |
|---|---|---|
| `INFLUENCE_DEFAULT` | **10** | 影响力缺省值（影响力系统未上线前的固定取值） |
| `POINTS_PER_YEAR` | **= Influence(account, round)** | 每游戏年产量；当前影响力 10 ⇒ 每年 +10 |
| `POINT_CAP_YEARS` | **30** | 上限年数（用户定案：30 年产量） |
| `POINT_CAP` | **= perYear × 30** | 派生（当前 300），不单独配置；影响力变化时同步 |
| `INITIAL_POINTS` | **50** | 首次建档赠送（成本上调后同步上调，保证开局能招 1 人） |
| `ROLL_COST` | **30** | 刷新一次（= 3 年产量） |
| `HIRE_COST` | **50** | 招一人（= 5 年产量） |
| `ENTER_COST` | **0** | 打探费（默认免；见 §3.5 攻击面清单，可调成 30 强堵） |

现实时间换算：1 tick = 1 秒；1 年 = 360 tick = 6 分钟；攒满 300 点 = 30 年 = 3 小时现实。

> **数值后果（试玩时照这张表核对手感）**：每年 10 点 ⇒ 招 1 人攒 5 年、刷新 1 次攒 3 年；
> 满余额 300 点 = 最多 6 人 或 10 次刷新。一个 3~9 人的满池全招 = 150~450 点 = 15~45 年，
> ⇒ **单池必然招不满**，玩家必须取舍。若觉得太慢，只调 §2.2 的 `INFLUENCE_DEFAULT` 与成本，
> 上限和百分比判据会跟着走，不需要改代码别处。
数值全部是**游戏内点数**，与灵石/库存无关（P0 不混货币）。

### 2.3 为什么不用 TickJob

每个账号挂一个「每年按影响力加点」的定时任务，要处理**离线补算 / 换世重挂 / 重启恢复**三套边界，收益为零。
`WorldClock` 已经提供权威时间 ⇒ 用 `(nowTick, lastTick)` 两个数就能随时算出正确答案 ——
与地图侧「读时生成 + 缓存」同一条纪律（`GetTileBlock` 先例）。
影响力同理不缓存：每次结算现问 `Influence()`（当前是常量 10，接了影响力系统后读宗门影响力）。

## 三、防刷：确定性池子 + 状态落库

### 3.1 池子 = 纯函数

直接复用 `Chargen.genPool(opts)` 现成的口径（**生成器零改动**）：

```
seed = fnv1a([worldSeed, settleId, rollNo, 'pool'].join('\u0001'))
候选人 = genCandidate({ worldSeed, settleId, round: rollNo, slot: i, salt: 'cN' })
```

- `chargen.js` 的 `genPool` 里那个 `round` 参数，招募系统传入 **`rollNo`（刷新轮次，0 起）** —— 语义对齐，不改生成器。
- 同 `(worldSeed, settleId, rollNo)` 两次生成逐字段一致 ⇒ 「刷新网页还是同一个」在**算法层**已经成立。

### 3.2 「当前随机数」落库 —— 快照为真源

用户口径：「当前随机数保存到数据库」。落库内容 **两层**：

| 层 | 存什么 | 作用 |
|---|---|---|
| 随机数（轻） | `rollNo`（当前轮次）+ `taken[]`（已招走的下标） | 审计 / 重建 / 显示 |
| 快照（重） | `genPool` 的**完整输出 JSON**（9 人 × ~2KB ≈ 18KB） | **展示与招募的唯一真源** |

**为什么快照也要落库**（只存 `rollNo` 不够）：

1. `chargen.js` 是活代码 —— 日后改分布/改特质，同一 `rollNo` 重算会**换人**。快照一落，
   已打探的池子**永久固定**（对齐「招走的人不重排」的精神）。
2. `hire` 直接从快照取人装配进契约，**不重跑生成器** ⇒ 显示的人和入队的人 100% 一致。
3. 快照带 `v`（生成器版本号），将来生成器升级可按版本兼容读旧池。

首次进入某聚落面板：**自动生成 `rollNo=0` 并落库（免费）**。
⇒ 性质是「幂等的读时生成缓存」，与 `GetTileBlock` 读时生成区域包同类，不算破坏只读纪律。

### 3.3 刷新语义（整池换新）

- `POST /roll`：`rollNo + 1` → 生成新池 → **覆盖快照**（旧池未招走的人作废）→ `taken` 清空。
- 前端刷新前二次确认：「当前池中还有 N 人未招募，刷新将换一批（-30）」。
- 余额 < `ROLL_COST`(30) ⇒ 拒绝 `insufficient-points`，`rollNo` 不动。

### 3.4 招走占位

- `taken[]` 记录已招走的下标；展示时该卡置灰「已入宗门」。
- 重复招募同一位 ⇒ 幂等返回既有成员（`duplicated: true`），**不重复扣点、不重复加人**（见 §7.4）。

### 3.5 攻击面清单（这条要写进判据）

| 攻击 | 防线 |
|---|---|
| 反复刷浏览器/重开会话 | 状态落库 ⇒ 同池；换一批必须花点 |
| 刷新请求连发 | `rollNo +1` + 扣点在同一把锁内原子完成；余额不足拒绝 |
| 重复 hire 同一位 | `taken` 幂等 + 确定性成员 id |
| 伪造 `settle` 参数（改 type/pop 骗好苗子） | 服务端**只认 `settleId`**，`type/pop/element/q/r` 全部自己从 `citySettlementsJson` 查回（§9.3） |
| 跑图到多个聚落免费看池 | **招募本身收 50 点**（用户定案）；看信息免费但招人要钱。若要强堵再开 `ENTER_COST` |
| 跑图到远处聚落挖人（跨地图刷好苗子） | **队伍驻地约束**：有队伍后 `/hire` 只接受「队伍驻地 == 请求聚落」，其余一律 `wrong-settle`（§4.1.1）；打探仍免费，但招不了 |
| 多标签页同时操作 | 点数与 taken 全部服务端权威；前端操作后以响应里的余额/rev 重绘 |
| 换世重开卡池 | 状态按 `(Account, Round, SettleId)` 隔离，新世从零；旧世行保留（同 `PlayerSect` 策略） |

## 四、聚集地与出身

### 4.1 可招募地点 = 所有聚落实体（打探层）

- 类型：村落 `village` / 渔村 `fishing` / 坊市 `town` / 仙城 `city` / 宗门 `sect`（含他人宗门、自家宗门）。
- 判据：该格上确实存在聚落实体（经 `citySettlementsJson` 服务端复核）。秘境 `poi` 池量 0，不招。
- 池量沿用 `CFG.POOL`（村落 3~4 / 坊市 4~6 / 仙城 6~9 / 宗门 2~5 / 渔村 3~5），`pop` 只做放大参考（≥ 每人 50 人）。
- **打探不受驻地限制**：任何聚落都能点开面板看池子（免费）；能不能招人见 4.1.1。

### 4.1.1 队伍驻地约束（招募层，2026-11-26 新增）

口径一句话：**没队伍 ⇒ 哪都能招；有队伍 ⇒ 只能回队伍驻地招。**

> 术语对齐：用户口语的「城镇」= 本档的**聚落**（村落 / 渔村 / 坊市 / 仙城 / 宗门都算），野外与秘境不算。
> 「队伍驻地」= 该队 `Settle` 字段记的**聚落 id**（`i_j_k`），不是「宗门所在地」。

| 情形 | `/hire` 行为 |
|---|---|
| **没有任何队员**（`squads` 全部 `members` 为空，且老契约 `Squad.Members` 也为空） | 允许，任意合法聚落；招完优先塞进已存在的**空队**（顺手绑定驻地 = 当前聚落），没有空队才新建。⚠ 判据是「**有没有人**」，不是「有没有 `squad` 对象」—— 空队在前端仍会渲染，不代表有队伍 |
| 有队伍，`squadId` 省略 | 服务端自动选队：优先**本镇且有队员**的队 → 再退「第一支有队员的队」→ 再退「第一支空队」（详见 §9.6 ①）。⚠ 前端建议**总是显式传 `squadId`**，否则可能进到玩家没预期的那支队 |
| 有队伍，传了 `squadId` | 校验**该队**驻地 == 请求聚落 |
| 目标队驻地 ≠ 请求聚落 | 拒绝 `wrong-settle`（HTTP 200 + ok:false），`points` 原样返回不扣 |
| 目标队驻地为空（老存档 / 迁移前） | **兼容补绑**：首次 hire 时把驻地写成请求聚落，继续流程 |
| 目标队驻地已存在但该聚落已不在引擎里（聚落被毁） | 视为无效驻地 ⇒ `wrong-settle`，提示「驻地已不存，需重新安顿队伍」（队伍迁移功能见 §十三.3） |

- **驻地存在哪**：`CrewContract.Squads[i]` 新增字段 `Settle`（settleId 字符串，空 = 未绑定）。
  与 `Members` 同一份契约一起走 `CrewStore.Mutate`，不另建表 —— 队伍位置天然属于队伍属性。
- **为什么不用「宗门所在地」代替**：宗门是玩家聚落（`PlayerSect`），与小队活动位置会分离（未来队伍会外出）；
  小队自己记驻地才经得起「队伍移动」这个后续功能，且不用改 `PlayerSect` 表。
- **多队各自在不同镇**：只要当前聚落里有**一支**队的驻地匹配，就能招进那支队；前端入队浮层
  把「不在本镇」的队置灰并标「驻地：临川坊」。
- **为什么这么限**：① 语义自洽 —— 人要入队，队得在场；② 顺手堵掉「跨地图扫池挑好苗子」这个刷法；
  ③ 成本已经从 10 提到 50，若还允许隔空招，跑图成本远低于招募成本，限地点才是真正的门槛。

### 4.2 出身偏置（本次新增，改 `chargen.js`）

现状 `bgOf(rng)` 只按全局权重抽出身（农户 26 / 流民 18 / 猎户 16 / 渔家 12 / 铁匠 12 / 游医 9 / 书生 7）。
按「不同聚落出身不同」新增**按聚落类型的权重系数**：

| 聚落 | 农户 | 猎户 | 渔家 | 铁匠 | 游医 | 流民 | 落第书生 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 村落 village | ×2.0 | ×1.6 | ×0.8 | ×0.8 | ×0.6 | ×1.2 | ×0.3 |
| 渔村 fishing | ×1.0 | ×0.9 | **×3.0** | ×0.6 | ×0.7 | ×0.8 | ×0.3 |
| 坊市 town | ×0.8 | ×0.9 | ×0.8 | **×2.2** | ×1.6 | ×1.0 | ×1.4 |
| 仙城 city | ×0.5 | ×0.6 | ×0.8 | ×1.2 | ×1.4 | ×0.9 | **×2.2** |
| 宗门 sect | ×0.9 | ×1.0 | ×0.9 | ×1.0 | **×1.5** | ×0.8 | **×1.5** |

> 表里的数字是**乘在基础权重上的系数**（`weight × bias`），实现时作为 `BG_BIAS[type]` 常量表放 `chargen.js` 的 `CFG` 旁边。
> ⚠ 系数只影响**抽取概率**，不改单个出身的字段（bias 道 / mood 区间照旧）。

改法（两处小改，`genPool` 透传即可）：

1. `bgOf(rng, settleType)` 加第二个参数；内部 `acc += BACKGROUNDS[i].weight * (BG_BIAS[settleType]?.[k] ?? 1)`。
2. `genPool` 里把 `st.type` 传给每个 `genCandidate`（`genCandidate` 的 opts 里加 `settleType`，只在抽出身时用）。
3. ⚠ 改完跑一遍 `selfTest()` + `stats()`，确认分布断言不破（出身不在硬约束里，理论上不破）。

## 五、招募与入队

### 5.1 队选择（合并进入 / 无队新建）

`POST /hire` 的 body 带 `squadId`（可选）。**先过 §4.1.1 的驻地闸，再看下表**：

| 情形 | 行为 |
|---|---|
| 传了 `squadId` 且队存在且未满 | 成员**追加到该队队尾**（`squads[i].members` push） |
| 传了 `squadId` 但队满（9 人） | 拒绝 `squad-full`（前端应把满队置灰） |
| 传了 `squadId` 但队不存在 | 拒绝 `no-squad` |
| **目标队驻地 ≠ 请求聚落** | 拒绝 `wrong-settle`（**先于队满判断**，否则「满队」会盖住「不在本镇」的真实原因） |
| 没传 `squadId`，有队员的队存在 | 自动选队（§9.6 ①：本镇有队员的队 → 第一支有队员的队 → 第一支空队），同样过驻地闸 |
| 没传 `squadId`，**没有任何队员**（全是空队或空契约） | 优先复用**已存在的空队**（绑定 `Settle` = 请求聚落），没有空队才新建一支（服务端按序号起名「小队」） |
| 队数已达上限（6 支）且要求新建 | 拒绝 `squad-limit` |

「合并进入」= 追加到队尾；**队内再拖站位是入队后的事**（`member.move` / 面板拖动，不在本系统内）。
校验顺序（实现照抄）：`bad-settle` → `no-pool` → `bad-slot`（含已 taken 幂等返回）→ `points` → `wrong-settle` → `squad-full` / `squad-limit` → 扣点写入。

### 5.2 成员与装备落点

- `pawn`（Chargen 输出）→ 契约 `MemberDto`：字段一一对应（`id/name/role/gender/age/realm/exp/mood/root/talents/traits/equip/queue/arts/vit/activity/prio`），**不换算任何派生值**。
- `items[]`（5 件起步装备 + 1 件法宝）→ 并入 `bag.items`；全部 `cell: null`（穿戴态 / 队列态）。
  - ⚠ 穿戴态**不占背包格** ⇒ 招募不受背包容量限制（P0 无需校验）。
- `role` 恒 `凡人`（出身在 `meta.background` 里展示），入宗转职司是后续功能。
- ⚠ `root.v` 是**份数口径**（0/20，合计 20k），不是 100 —— 与 `crew-bridge` 的归一逻辑一致（`hydrate` 会按比例缩放成纯度，不算 error）。契约 `schema` 的注释要同步改一句。

### 5.3 幂等与可重放

- 成员 id 与物品 id 都是**确定性派生**：`srv-c-<hash8>` / `srv-c-<hash8>-weapon`。
  同 `(settleId, rollNo, slot)` 恒同一 id ⇒ **重复请求天然幂等**。
- `hire` 流程：校验（点数 / slot / 队）→ 写 Crew → 标记 `taken`。若第二步前进程崩溃，
  重试时成员 id 相同 ⇒ 不会重复加人；`taken` 补记成功即收尾。**无需跨 store 分布式事务**。
- 重复 hire：返回 `{ ok: true, duplicated: true, member: {…}, points: {…} }`（对齐接口档 §14.7「重复直接 ok，让重试无脑重发」）。

### 5.4 并发纪律（⚠ 一个必须做的服务端小改）

`CrewStore.Save` 是**全量覆盖**。若 `hire` 走「锁外读契约 → 加人 → Save」，
会吞掉前端 300ms 窗口内刚发的 `patch`（拖动/派活）。做法：

- 给 `CrewStore` 加一个**锁内原子变换**方法，例如
  `CrewContract? Mutate(Action<CrewContract> f, string id = DefaultId)`：
  在 `_gate` 锁内完成「读 → 改 → Revision+1 → 落库」，`hire` 只传一个「加成员 / 入队 / 加物品」的闭包。
- ⚠ **禁止**在 `RecruitEndpoints` 里读-改-写 `squads` —— `squads` 在 `Patch` 里是整表替换，
  两个并发 hire 各自构造数组会互相覆盖（丢人）。

### 5.5 驻地字段的静默丢失（必看，不报错那种坑）

`squads` 是**整表替换**：前端每次拖动站位 / 改队名都会重发整个 `squads` 数组。
若前端构造数组时**没带 `settle`**，服务端按「空 = 未绑定」处理 ⇒ 下次 hire 补绑到当时的聚落
⇒ **驻地被悄悄改到别处**，玩家还以为队伍在原地。

三道防线（缺一不可）：

1. **前端透传**：`normalizeSquads` 保留未知字段，`settle` 显式带出来（`crew-model.js` / `crew-bridge.js`）。
2. **服务端兜底**：`Patch` 合并时，传入 squad 的 `settle` 为空而**旧值非空** ⇒ **保留旧值**，绝不当作解绑。
3. **解绑只能显式**：P0 不提供解绑/换驻地接口；队伍迁移是后续功能（§十三.3）。

> 与「块级 rev 不 Bump ⇒ 客户端永久陈旧」同类：不报错、不崩、只是数据慢慢变错，难查。

## 六、数据模型

### 6.1 两张新表（独立表，⚠ 不进 `Data(Key,Value)`）

```sql
/* 招募值：全宗一份（Account × Round） */
CREATE TABLE IF NOT EXISTS RecruitPoint (
    Account   TEXT    NOT NULL,
    Round     INTEGER NOT NULL,
    Points    INTEGER NOT NULL DEFAULT 0,   -- 当前余额（⚠ 上限不落库：结算时按 influence×30 现算）
    LastTick  INTEGER NOT NULL DEFAULT 0,   -- 上次结算的世界 tick
    Ver       INTEGER NOT NULL DEFAULT 1,
    UpdatedAt INTEGER NOT NULL,
    PRIMARY KEY (Account, Round)
);

/* 候选池：每个打探过的聚落一份（Account × Round × SettleId） */
CREATE TABLE IF NOT EXISTS RecruitPool (
    Account   TEXT    NOT NULL,
    Round     INTEGER NOT NULL,
    SettleId  TEXT    NOT NULL,             -- 格式 i_j_k（区域坐标_序号），同 PlayerSect 的 id 口径
    RollNo    INTEGER NOT NULL DEFAULT 0,   -- 已刷新次数（种子输入）
    Taken     TEXT    NOT NULL DEFAULT '[]',-- JSON: [0,3,…] 已招走的下标
    SettleJson TEXT   NOT NULL DEFAULT '',  -- 聚落上下文快照 {type,pop,element,q,r,name}
    PoolJson  TEXT    NOT NULL DEFAULT '',  -- 池子快照（genPool 完整输出，v 字段在内部）
    Ver       INTEGER NOT NULL DEFAULT 1,
    UpdatedAt INTEGER NOT NULL,
    PRIMARY KEY (Account, Round, SettleId)
);
```

| 纪律 | 说明 |
|---|---|
| **必须独立表** | `Data` 表会被后台 `PruneExcept` 定期 DELETE —— 对齐 `Crew` / `PlayerSect` / `WorldLedger` 同一个坑 |
| `SettleJson` 单独存 | 聚落上下文（type/pop/element/q/r）只查一次、快照固定；避免每次重建时重查引擎 |
| `PoolJson` 是展示与 hire 的真源 | 见 §3.2 |
| 换世 | 主键含 `Round` ⇒ 新世天然从零；旧行保留（是否清理见 §十三.6） |
| `PruneExcept` 够不着 | 需要时另加显式清理（debug 端点或后台任务），P0 不做 |

### 6.2 与既有表的关系

```
WorldLedger(Current) → seed + Round ─┐
WorldClockStore      → nowTick ──────┤
                                     ├→ RecruitEndpoints（结算/生成/校验）
citySettlementsJson  → 聚落上下文 ────┤
                                     ↓
        RecruitPoint（点数）      RecruitPool（池子快照）
                                     ↓ hire
        CrewStore.Mutate → Crew 契约（squad.members / squads[] / bag.items）
```

- 弟子数**不落库**：所有小队人数合计即宗门弟子总数（用户 2026-11-25 定案），
  `PlayerSect.disciples` 字段标注「派生/停用」，由 Crew 契约现算。
- 招募值**不塞 `PlayerSect` JSON**：未立宗也要能攒（招募不要求先立宗），
  且点数写频高，独立表归属 `RecruitStore` 统一管理。
- **队伍驻地不另建表**：跟着 Crew 契约的 `squads[].settle` 走（§4.1.1），与成员同一份存档、同一把 `Mutate` 锁；
  好处是「招人 + 绑定驻地」天然一个事务，不会出现「人进去了但驻地没写」的半截状态。
- `Influence()` 不入库：影响力是外部系统的当前值，验算即可（§9.5）；落一份反而会和真源漂。

## 七、HTTP 接口（4 个端点）

统一风格对齐 `CrewEndpoints`：JSON + camelCase + `{ ok, error, code }`；写操作一律 POST（防预取缓存）。

### 7.1 `GET /api/recruit/state`

无参数（点数全宗共享）。**先结算**再返回：

```json
{ "ok": true,
  "points": { "value": 42, "cap": 300, "perYear": 10, "influence": 10,
              "rollCost": 30, "hireCost": 50, "initial": 50 },
  "clock": { "tick": 123456, "year": 343 } }
```

⚠ `rollCost / hireCost / cap / perYear / influence` 由服务端下发 —— **前端不许硬编码、不许自己推影响力公式**
（对齐「词表不许 UI 再抄一份」）。`perYear` 就是服务端结算用的那个数，前端只显示。

### 7.3 `POST /api/recruit/roll`

```json
// 请求
{ "settle": "12_-3_1" }
// 成功
{ "ok": true, "rollNo": 3, "candidates": [ … ], "points": { … } }
// 余额不足
{ "ok": false, "code": "insufficient-points", "error": "招募值不足（25/30）", "points": { … } }
```

语义：结算 → 校验余额 ≥ `ROLL_COST`(30) → 扣点 → `rollNo+1` → 新池 → 覆盖快照 → `taken` 清空。
⚠ 刷新不改变 `SettleJson`（聚落上下文不变）。⚠ 刷新**不受驻地限制**（在哪都能刷，只扣点）。

### 7.4 `POST /api/recruit/hire`

```json
// 请求
{ "settle": "12_-3_1", "slot": 2, "squadId": "sq2" }   // squadId 可省；省略 = 第一支队
// 成功
{ "ok": true, "duplicated": false,
  "member": { "id": "srv-c-77aa01ce", "name": "陆听澜", "…": "…" },
  "squadId": "sq2", "rev": 347, "points": { … }, "hireGate": { … } }
// 队伍不在本镇
{ "ok": false, "code": "wrong-settle",
  "error": "队伍驻地在青石村，需回到驻地才能招募",
  "hireGate": { "allowed": false, "reason": "wrong-settle", "squads": [ … ] },
  "points": { … } }
```

语义（顺序即实现顺序）：

1. 结算（`points` 已是最新）
2. 校验 `settle` 合法（引擎复核，`bad-settle`）；取 `RecruitPool` 行（没有 ⇒ `no-pool`，前端应先 GET pool）
3. 校验 `slot` 在快照范围内 ⇒ 否则 `bad-slot`；已 `taken` ⇒ **幂等返回**（§5.3，不扣点、**也不查驻地**）
4. 校验余额 ≥ `HIRE_COST`(50) ⇒ 否则 `insufficient-points`
5. **驻地闸**：按 §9.6 ① 定目标队（显式 `squadId` → 本镇有队员的队 → 第一支有队员的队 → 第一支空队 → 新建）
   → 校验 `Settle == 请求聚落`；空队/驻地为空则**补绑**当前聚落继续；不等 ⇒ `wrong-settle`（返回 `hireGate` 供前端跳转提示）
6. 校验目标队未满（`squad-full`）/ 要新建但已 6 支（`squad-limit`）
7. 从**快照**取该候选人 → 构造 `MemberDto` + `items[]`
8. `CrewStore.Mutate`：加成员（队尾）+ 入队（`squads`；无队则新建并写 `Settle`）+ 并入 `bag.items`
   - ⚠ `Crew` 表为空（首招）⇒ 服务端**内部新建契约**（不走 `PUT` 的「members 不能为空」校验）
9. 扣点 + 标记 `taken` → 落库 → 返回

### 7.5 错误码总表

| code | HTTP | 场景 |
|---|---|---|
| `insufficient-points` | 200 + ok:false | 余额不够（roll 或 hire） |
| `bad-settle` | 400 | settleId 解析失败 / 引擎查不到该聚落 / `poi` 类型 |
| `no-pool` | 404 | hire 时池子还没生成（先 GET pool） |
| `bad-slot` | 400 | slot 越界 |
| `wrong-settle` | 200 + ok:false | **目标队伍驻地 ≠ 请求聚落**（§4.1.1；带 `hireGate` 供前端提示「回驻地」） |
| `squad-full` | 200 + ok:false | 目标队已满 9 人（`code` 区分，前端置灰提示） |
| `no-squad` | 200 + ok:false | 传了不存在的 `squadId` |
| `squad-limit` | 200 + ok:false | 要新建但已有 6 支 |

### 7.6 为什么不走事件流（对照接口档 §14）

- 招募是**强校验 + 跨表原子写**（点数 / taken / Crew 三处），乐观事件流会把它拆成三段可竞态的操作。
- 事件流的价值在「低保真频操」（拖动/派活）；招募是低频、必须服务端权威的动作 ⇒ **专用端点**。
- `member.recruit` 事件**不定义**（接口档 §14.4 它本来就标着「暂不定义」）——
  由本系统的 `hire` 端点取而代之；前端招募成功后重装契约即可。

- 面板首次打开 = `GET /api/recruit/pool?settle=…`；刷新 = `POST /roll`；招募 = `POST /hire`。
- **能不能招以 `hireGate` 为唯一判据**（`allowed` / `reason` / `squads[].here`），前端不自己算「队伍在哪」。
- 招募成功后：候选卡置灰 + `CrewBridge` 重装契约（`GET /api/crew` → `mount(c, { localTick: false })`）→
  队伍面板立刻能看到新人。
- 招募值显示：面板打开时取一次 + 每次操作响应里带最新值；**长期开着按 `/api/clock` 本地插值**（可选，P0 可省）。
  插值速率用响应里的 `points.perYear`，**不要写死 10**（影响力会变）。
- ⚠ 多月台/多标签页：以服务端响应为准重绘（不本地乐观扣点）。

## 九、服务端要点（实现时必看）

### 9.1 结算与余额的三处写口

| 入口 | 结算 | 写 RecruitPoint | 写 RecruitPool |
|---|---|---|---|
| `state` | ✔ | 有新增长才写 | — |
| `pool` | ✔ | 有新增长才写 | 首次生成时写 |
| `roll` | ✔ | 扣点后写 | 覆盖快照 |
| `hire` | ✔ | 扣点后写 | 标记 taken |

⚠ 结算写库统一走 `RecruitStore.Settle(account, round, nowTick)`（一把锁内读-算-写），端点不各写一份。
⚠ `Settle` 内部**自己取影响力**（`Influence(account, round)`），不接受调用方传参 —— 否则前端/其它端点能伪造产量。

### 9.2 世界上下文取法

- `seed + round`：`MapWorldService.CurrentSeed() / CurrentRound()`（内部走 `WorldLedger.Current()`）。
- `nowTick`：`WorldClockStore.GetOrCreate(seed, round, initialTick)` 或 `TickPump.Snapshot()` —— **以 (seed, round) 键**，换世自动是新时钟行。

### 9.3 聚落校验（防伪造）

```
settleId "i_j_k" → 解析出 (i, j)
→ lease = MapWorldService.LeaseWorld(seed)
→ json = lease.Vm.Call("citySettlementsJson", i, j)      // ext 感知：含玩家宗门
→ 按 id 找到条目 → 取 { type, pop, element, q, r }
```

- 找不到 ⇒ `bad-settle`；`type == 'poi'` ⇒ `bad-settle`。
- **客户端只能给 `settleId`**；type/pop/element 一律服务端查回（防「改 pop 骗池量」的刷法）。
- ⚠ 首次生成时把这份上下文存进 `SettleJson`，后续不重查（聚落数据随演化变动时，池子固定不动——这是特性不是 bug）。

### 9.4 chargen 接线（照 `角色生成器-实施方案.md` §十三）

1. `JsvmModule.BuildBundle` 的 bundle 数组加 `Engine/js/chargen.js`；
2. `WorldModule.Invoke` 加 case（建议一个出口吃一个 JSON 字符串，省参数）：

```csharp

```

   JS 侧 `genPoolJson(optsJson)` = `JSON.parse` → `genPool` → `JSON.stringify`（薄封装，不碰生成逻辑）。
   ⚠ 可达性已确认：bundle 头部三行别名（`var window = globalThis; var global = window;`，`JsvmModule.cs:67`）
   先于所有脚本执行，而 `chargen.js` 结尾导出 `global.Chargen = api` ⇒ VM 内 `root.Chargen` 直接可用。
3. `ComputeEngineHash / EngineScriptOrder` **不纳入**（它不是地图引擎的一部分，纳入后每次改生成器都要清世界库）；
4. 重启服务端后生效；若载荷指纹没变**不需要**清 `db/zongmen.sqlite*`（接线时实测确认一次）。

### 9.5 影响力取值（当前是桩，别把 10 写死）

```csharp
// Server/Zongmen/Services/InfluenceProvider.cs（新增，约 20 行）
public interface IInfluence { int Of(string account, int round); }
public sealed class InfluenceProvider : IInfluence
{
    public const int DEFAULT = 10;          // §2.2 INFLUENCE_DEFAULT
    public int Of(string account, int round) => Math.Max(1, DEFAULT);   // 保底 1
}
```

- P0 注册 `AddSingleton<IInfluence, InfluenceProvider>()`；以后接影响力系统只换实现，`RecruitStore` 一行不改。
- `Math.Max(1, …)` 是硬约束：影响力 0 ⇒ 招募值永久冻结、玩家卡死。
- 影响力是**当前值**，只影响「这一段时间的产量」，不建历史曲线（§2.1 纪律表）。
- 未立宗 / 影响力系统还没上线的账号，`Of()` 直接返回 `DEFAULT`（10），不会因为没宗门就冻结。
- 上限同源：`cap = perYear * 30`；影响力上调不会瞬间送点，只让后续年份攒得更快。

### 9.6 队伍驻地校验（§4.1.1 的服务端实现）

```text
// 必须在 CrewStore.Mutate 的锁内执行（锁外读到的 Settle 可能已被 patch 改掉）

// ① 定目标队
if (squadId 有值) {
    目标队 = squads.Find(id);  if (目标队 == null) → no-squad
} else {
    目标队 = squads.FirstOrDefault(s => s.Members.Count > 0 && s.Settle == settleId)  // 本镇有人的队
          ?? squads.FirstOrDefault(s => s.Members.Count > 0)                          // 退而求其次：第一支有人的队
          ?? squads.FirstOrDefault()                                                  // 再退：第一支空队
          ?? 新建队
}

// ② 驻地闸（空队不算"有驻地"，可直接启用）
if (目标队.Members.Count == 0)        目标队.Settle = settleId        // 空队/新建队：绑定当前聚落
else if (目标队.Settle == "")         目标队.Settle = settleId        // 老存档补绑
else if (目标队.Settle != settleId)   → wrong-settle（返回 hireGate）

// ③ 容量
if (目标队.Members.Count >= 9)        → squad-full
```

> 「没有任何队员 ⇒ 任意聚落可招」是上面规则的**自然结果**：全是空队时 ① 会选到空队、
> ② 会把它重绑到当前聚落，不需要额外分支。⚠ 别写成 `if (squads.Count == 0)` ——
> 前端可能留着空队对象（`.rp-list.empty` 仍渲染），那样判会误拒。

- `squads` 为空但 `Squad.Members` 有人（老契约「单队」形态）⇒ 视作一支隐含队：
  补建 `Squads[0]` 并绑定驻地（与前端 `normalizeSquads` 的补队口径一致）。
- ⚠ 驻地在**队伍**上（`Squads[i].Settle`），不在成员上；队员换队不改驻地。
- ⚠ 不要用前端传来的队伍列表做判断 —— 服务端只读自己的 `CrewContract`。

## 十一、验收判据

### 11.1 离线（`verify/_recruit_probe.mjs`，Node 直跑，不碰服务端）

1. **结算公式**：给定 `(points, lastTick, nowTick, influence)` 组合表 —— 含跨年、余数月、cap 夹断、cap 后花掉回血，
   全部与公式手算一致（相对判据，不写死随机值；`cap` 由 `influence×30` 推出，不在用例里写死 300）。
2. **余数不丢**：连续 5 次不同余数的结算，累计 gain 与一次性结算相同。
3. **确定性**：同 `(worldSeed, settleId, rollNo)` 两次 `genPool` 的 `JSON.stringify` 完全相同。
4. **出身偏置**：`stats` 口径下渔村池的渔家占比 ≈ 权重表推算值（容差 ±5pp，相对判据）。
5. **快照往返**：`PoolJson` 序列化 → 反序列化 → hire 取人字段一致。
6. **影响力同源**：`Influence` 返回 10 / 20 / 0 三档跑同一组 tick ⇒ `perYear` 与 `cap` 同步变化
   （0 被保底成 1，不冻结）；影响力下调导致 `points > cap` ⇒ 夹断到 cap，不补不退。
7. **驻地判定**（纯函数层）：给定 `(squads[], settleId)` 组合表 —— 无队 / 驻地为空 / 驻地相同 / 驻地不同 / 老契约隐含队，
   返回的 `hireGate.allowed` 与预期一致（不依赖服务端）。

### 11.2 端到端（`verify/_recruit_api_probe.mjs http://127.0.0.1:8155`）

1. **首探落库**：`GET pool` 首次返回 `rollNo:0` 且响应两次完全相同（**刷新网页等价性**）。
2. **重启持久化**：重启服务端 → 同账号 `GET pool` 仍是同一批（`JSON.stringify` 相等）。
3. **roll**：余额 **-30**、`rollNo+1`、新池与旧池不同；余额清 0 后再 roll ⇒ `insufficient-points` 且 `rollNo` 不动。
4. **hire**：余额 **-50**、`taken` 含该 slot、`/api/crew` 里出现新成员且 `equip/queue` 指向的 itemId 全部存在。
5. **入队**：指定 `squadId` ⇒ 成员在该队队尾；**没有任何队员**时首招 ⇒ 独立成队（已有空队则复用并绑驻地，无空队才新建）；队满 9 人 ⇒ `squad-full`；6 队后再新建 ⇒ `squad-limit`。
6. **幂等**：同 `(settle, slot)` 连发 2 次 hire ⇒ 第二次 `duplicated:true`、**只扣一次点、只加一人**。
7. **服务端复核**：伪造 `settle`（乱 id / 不存在）⇒ `bad-settle`；伪造 pop/type 参数**不被采纳**（池量仍按服务端值）。
8. **换世隔离**：`POST /api/world/next` 后同 settle 的池子从 `rollNo:0` 重新开始，点数行按新 Round 独立。
9. **驻地闸**：无队时在 A 聚落招 ⇒ 成功且新队 `settle = A`；再去 B 聚落 hire ⇒ `wrong-settle` 且
   **余额不减、`taken` 不变**；回 A 聚落 ⇒ 成功；`GET pool` 在 B 聚落仍能正常打探/刷新（刷新只扣点不查驻地）。
10. **驻地不漂移**：入住后从队伍面板拖动站位 / 改队名 ⇒ `GET /api/crew` 里 `squads[i].settle` **保持 A**（§5.5 三道防线）。

> 判据四防（工程纪律）：不得用绝对值阈值判随机分布（用相对/分布形状）；
> 参照系取服务端自查结果或公式手算；同容差语义统一；源码守卫先剥注释。
