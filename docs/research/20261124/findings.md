# 发现与取舍：背包与装备系统调研

> 类型 `research` ｜ 日期 `20261124` ｜ 配套 `task_plan.md`（计划）、`progress.md`（日志）

**一句话结论**：成熟解法已收敛成两条路线——「定长格子数组」做背包、「属性驱动配额」做装备上限。修仙题材正好各挂一个世界观壳：**储物戒品阶 → 背包格数，神识容量 → 每人装备件数**。真正难的不是格子数，而是「扩容时的索引稳定性」和「换装回包」这两件事，80% 的实现都在这里翻车。

只记三件事：

1. 背包模型选**定长 slot 数组 + 配置表/实例双表**，不要选列表字典（后面拖动、整理、占多格全靠数组）。
2. 装备上限选**属性驱动**（境界/神识 → 件数），不要选纯固定部位数。修仙题材固定部位数会浪费"法宝越炼越强"的空间。
3. 100 格不要一屏铺 10×10。一屏 4×5=20 格可读性最好，100 格做成「分页 + 滚动」。

## 一、调研发现：参考产品扫描（能直接抄的 + 明确别抄的）

| 产品 | 背包模型 | 装备模型 | 可抄的点 | 别抄的点 |
| --- | --- | --- | --- | --- |
| 《我要当老祖》 | **6×7 棋盘（42 格），背包即战场** | 无独立装备栏，法宝直接摆棋盘 | 物品**占位关系产生效果**（相邻共鸣、灵宠站位、魂石叠加）——把"格子"从容器变成策略面 | 42 格太小，后期必爆仓；纯棋盘不适合"储物戒"叙事 |
| 《了不起的修仙模拟器》 | 无限仓库 + 携带重量 | **固定部位 12 件（衣2+武器1+符咒3生效+道具6），法宝栏 3→6 靠功法/丹药解锁，满配 18 件** | 「基础部位 + 可解锁附加栏」的**两段式扩容**，比单纯加部位数优雅 | 符咒"戴 6 张只激活 3 张"这种隐性规则，玩家必须查攻略才懂 |
| 《鬼谷八荒》 | 列表背包 + 7 个页签（全部/丹药/秘籍/装备/法宝/材料/其他） | **装备栏 3 格（戒指/坐骑/符箓）+ 战斗道具栏 5 格（只能放丹药法宝）**；法宝共 8 种，**念力够才装得到 5 个** | **属性门槛限制装备件数**（念力→法宝数），最贴合"境界养成"的限额模型 | 页签过多；"能装但装不上"的反馈很隐蔽 |
| 《我是掌门》 | 背包即塔防战场 | 无 | 同一格**多层叠加**（聚灵阵底层 + 符塔中层 + 护盾顶层），整排平移补防 | 与"储物戒"叙事冲突，纯玩法缝合 |
| 《剑与魔法王国》 | — | **105 格装备栏：武器 5 / 防具 2 / 饰品 3 / 辅助 90**，辅助栏只按稀有度折算属性（25%/20%/15%/10%），技能无效 | 「辅助栏」概念：**同一件装备放主栏吃 100%，放辅栏吃 10~25%**，天然造出"堆量 vs 精品"两条流派 | 105 格是页游时代的数值膨胀产物，不是设计 |
| 《Darkest Dungeon》 | **全队通用 16 格**，一种物品 1 格，堆叠上限极严，金币也占格 | 无 | 通用槽省掉了"谁带什么"的决策成本 | 16 格 + 单格制 = 纯靠稀缺制造的假难度，玩家公认最差体验之一 |
| 《Pillars of Eternity》 | 每人小包 + **无限共享 stash** | 固定部位 | stash 的正确理由：**"背包满了就在地牢里做捡哪个"是无趣取舍，不是有策略的取舍** | stash 无限会抹掉携带压力，要加"只能回城取"的限制 |
| 《Morrowind》/《KC:D》 | 重量制 | 18 槽 / 16 层叠 + 4 武器 | 分层穿甲（内衬→锁甲→板甲）的可视化层次 | 纯重量制在 2D 里毫无手感 |

### 从这些产品里提炼出的四条规律

1. **格子数决定"决策密度"，堆叠上限决定"整理成本"。** 两者要一起调：格子多 + 堆叠高 = 无压力；格子少 + 堆叠低 = 烦躁（Darkest Dungeon）；格子少 + 堆叠高 = 有压迫感但不烦（推荐区间）。
2. **装备件数用"属性门槛"限制，比用"固定部位"限制更耐玩。** 固定部位数在开局就定死，玩家只能换不能成长；属性门槛让"提升境界"直接等于"多带一件法宝"，成长反馈立刻可见。
3. **扩容必须"只增不减、只追加不重排"。** 所有做崩的实现都是扩容时重排了原有格子索引，客户端缓存的 slot 号全错。
4. **共享背包比个人背包更适合"小队养成"。** 核心循环是"培养一队人"，让玩家逐个算谁带什么会稀释养成爽感。个人负担靠"装备队列"承担就够了。

### 独立游戏的经验区间（可作为数值锚点）

| 参数 | 建议区间 | 说明 |
| --- | --- | --- |
| 装备槽位数 | 4（武器/防具/饰品/特殊） | 超 6 玩家算不过来 |
| 同阶段同类可选装备 | 3~5 件 | 超 6 出现纯垃圾件 |
| 全流程装备总数 | 40~80 | 超 150 必须砍"纯数值件" |
| 词条池 | 8~15 条 | 超 25 条互相打架 |
| 单件装备词条 | 1~3 条 | 超 4 条玩家放弃阅读 |
| 材料种类 | 15~30 种 | 超 50 种背包变考古现场，用"材料家族 + 品质"压缩 |
| 装备淘汰周期 | ≥5 小时 / 3 场 Boss | 短于 3 小时，整套搭配设计作废 |
| 合成成功率 | 100%，或仅正向浮动 | 低于 90% 的纯随机失败会激怒玩家 |

| 项目 | 技术栈 | 模型 | 对项目的价值 |
| --- | --- | --- | --- |

## 二、技术取舍

### 2.1 背包模型四选一

| 模型 | 数据结构 | 优点 | 缺点 | 适配判断 |
| --- | --- | --- | --- | --- |
| **定长格子数组** | `Slot[capacity]`，槽内存 itemId+count | 支持位置、拖动、整理、占多格、排序；UI 与数据一一对应 | 需处理碎片、扩容、满包 | **采用** |
| 列表背包（字典） | `dict<defId,count>` + `dict<instId,inst>` | 实现最简单，查数量 O(1) | 无位置概念，做不了拖动和"占 2 格的大件" | 否掉：后期无法补 |
| 重量制 | 累加 weight ≤ 上限 | 数值直观 | 2D 里没手感，玩家算不过来 | 否掉：2D 无手感 |
| 棋盘共鸣制 | 格子 + 邻接关系图 | 生成策略深度（《我要当老祖》） | 整理算法从 O(n) 变 O(n×邻接)，玩家被"摆位"绑架 | 降级为后期玩法层，不做基础层 |

**结论**：基础层用定长数组；若以后要做"法宝相邻共鸣"，在数组之上加一层"邻接效果计算"，不要改数组本身。

### 2.2 装备队列限额四选一

| 模型 | 机制 | 代表 | 修仙映射 |
| --- | --- | --- | --- |
| 固定部位 | 武器/衣/鞋/戒…各 1 格 | 多数 RPG、Morrowind | 基础层必须有，玩家一看就懂（武器、护体法衣、靴、本命法宝、储物戒本身） |
| **属性驱动上限** | 总件数 = f(某属性) | 鬼谷八荒（念力→法宝 5 个） | **神识容量**：炼气 2 → 筑基 3 → 金丹 5 → 元婴 7。境界提升直接多带法宝，成长感最强 |
| 分组配额 | 每类各有独立格数 | 剑与魔法王国（武器5/防具2/饰品3/辅助90） | 法衣 2 / 法宝 N / 符箓 3 / 丹丸 5，N 由神识决定 |
| 可解锁附加栏 | 基础部位 + 靠功法/丹药解锁 | 了不起的修仙模拟器（法宝 3→6） | 功法修满解锁"法宝栏 +1"，或吃"三神兽丹"开满 |

**采用组合（三层叠加，各管一件事）**：

```
每人装备队列 =
  固定部位 5 格（武器 / 法衣 / 靴 / 本命法宝 / 储物戒）   ← 给确定感
+ 灵宝位 N 格（N = 神识容量档位，境界驱动 1→6）           ← 给成长感
+ 符箓位 3 格（可被特定功法 +1）                          ← 给 Build 感
```

### 2.3 落到本项目的技术选型（.NET 8 + protobuf + Canvas 前端）

**数据模型：配置表 / 实例表分离**

```
ItemDef（静态配置，走 JSON 下发，同 /api/map/meta 的路子）
  id, name, 类型(丹药/法器/符箓/材料/功法残页), 品质(白绿蓝紫橙),
  stackMax, cellW, cellH（占格，MVP 恒 1×1）, icon, 描述, 使用效果

ItemInst（动态实例，落 SQLite）
  instId(唯一), defId, count, 耐久/强化等级/词条(仅装备类), bindFlag, expireTs
  —— 可堆叠物品只需 defId+count；独立物品必须 instId（每件都可能不同）
```

关键判断：丹药/材料走"配置 ID → 数量"，法器/符箓走"实例 ID → 实例数据"。混用是后期最大的债。

**容器抽象（背包与装备队列共用同一个类）**

```
Container
  ownerType: Squad | Character
  ownerId
  capacity: int          // 100 起步，储物戒品阶扩容
  slots: Slot[capacity]  // 定长数组
  Slot { instId?, defId?, count }
```

背包和小队装备队列共用 `Container`，只是 `capacity` 与"允许放入的类型集合"不同。这样"拖拽、整理、堆叠、拆分"四套逻辑只写一份。

**服务端权威 + 增量同步**

- 客户端只做**乐观 UI**（先画出来），所有增删改由 WS 请求 → 服务端校验 → 返回 `slotDiff[]`（`{containerId, slotIndex, instId, defId, count}` 数组）
- 驳回时回滚本地并提示
- 每次变更挂 `BumpBlockRev` 同款版本号，客户端版本落后就要求全量重拉

## 三、踩过的坑（实现级，可直接变判据）

| 现象 | 根因 | 规则（照这个写） |
| --- | --- | --- |
| 升级储物戒后，背包里物品图标错位/消失 | 扩容时重排了原有格子索引，而客户端缓存的是绝对 slot 号 | **只在尾部追加空槽，绝不动已有 0~(capacity-1) 号内容** |
| 背包满时换装备，旧装备凭空消失（刷物品漏洞源头） | 卸下→装上的三动作里，卸下那步没有落脚点，半成功 | **换装前先预占一个背包空槽**；成功则提交，失败整体回滚，不允许半成功 |
| 服务端与前端算出不同剩余数量，出现"幽灵物品" | 同种丹药散在 3 格，"用掉 5 颗"扣减顺序不确定 | **按 slotIndex 升序扣，扣到 0 才清槽**；写进协议注释，前端照抄 |
| 背包满时拾取，物品静默消失 | 添加接口没有返回"未放下数量" | 添加返回值必须携带 overflow 数量，非 0 就报满并拒绝 |
| 卸下储物戒后容量回落，物品超容 | 只改了 capacity，没检查已用槽数 | 当前已用槽数 > 新容量时**禁止卸下/降阶**，而不是丢弃溢出物品 |

### 边界处理清单（必须显式设计）

| 边界 | 处理 |
| --- | --- |
| 背包满时拾取 | **拒绝 + 提示**，不要静默丢弃；或落到"驿站/暂存处"（修仙叙事天然有：宗门库房） |
| 堆叠溢出 | 先填未满的同种格 → 再占新格 → 剩下数量返回调用方 |
| 移除数量不足 | **整个操作失败**，绝不扣一半 |
| 装备被替换下来 | 回背包；若满则换装失败（见上表第 2 行） |
| 物品过期 | 用 `expireTs`，读档时懒清理，不要后台定时扫全表 |

## 四、MVP 拆分建议（转实施用）

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| **P0** | `Container` 抽象 + 定长数组 + 堆叠/拆分/交换/整理 + 单测（含满包、溢出、扣减顺序） | 纯逻辑层无 UI 可跑通全流程；满包不丢物品 |
| **P1** | 储物戒 100 格 UI（分页 5×4，可滚动）+ 拖拽 + 页签筛选 + 使用/丢弃 + 容量升级（只追加） | 升级后索引不错位；拖拽与服务端一致 |
| **P2** | 每人装备队列（固定 5 部位 + 神识驱动 N + 符箓 3）+ 换装原子事务 + 属性汇总 | 满包换装失败可回滚，物品增减为零 |
| **P3** | 占多格物品（1×2/2×2）、词条、法宝相邻共鸣、宗门库房 | — |

**为什么占多格放 P3**：一旦有 1×2 物品，UI 要写碰撞检测，整理算法要写成二维装箱（近似 NP），成本是单体物品的 3~5 倍。除非"大件占大格"是核心卖点，否则 demo 阶段别做。
