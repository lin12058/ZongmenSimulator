## 关键问题（待用户拍板，决定 P0 的数据结构）

1. **100 格是硬上限还是当前上限？** 建议：基础 100，储物戒 4 阶（100/200/500/1000）。
2. **背包是小队共享还是每人一个？** 建议：小队共享（`ownerType=Squad`），个人只保留装备队列。
3. **装备件数由什么驱动？** 建议：神识容量（境界驱动），不是纯固定部位数。
4. **物品要不要占多格（1×2 / 2×2）？** 建议：P0~P2 一律 1 格，P3 再开。
5. **堆叠上限给多少？** 建议：材料 999 / 丹药 99 / 符箓 10 / 法器功法 1。
6. **背包满了走"拒绝"还是"溢出到宗门库房"？** 建议：拒绝 + 提示，库房作为独立容器 P3 再做。

## 决策记录

| 决策 | 理由 |
|------|------|
| 背包用定长 slot 数组，不用列表/字典 | 拖动、整理、占多格、排序全靠数组；列表模型后期做不了"大件占大格" |
| 装备上限用属性驱动，不用纯固定部位 | 固定部位数开局定死，玩家只能换不能成长；属性门槛让"升境界 = 多带法宝"立刻可见（对齐《鬼谷八荒》念力→法宝 5 个） |
| 开源框架只参考结构，不引 NuGet 包 | 它们都是单机容器抽象，缺「网络增量同步 + 服务端权威校验 + 存档版本迁移」，这三样要自己写 |
| 占多格物品延后到 P3 | 有 1×2 后整理算法退化为二维装箱（近似 NP），UI 要写碰撞检测，成本 3~5 倍 |
| 文档从 `docs/` 根目录迁到 `docs/research/20261124/` | 遵循 `plan-with-file`：`docs/<类型>/YYYYMMDD/` 是唯一允许位置，三件套文件名固定 |
