# Server 目录代码构成分析

> 分析对象：`D:/codes/宗门模拟器demo/Server/`（不含 `bin/`、`obj/`）
> 分析日期：2026-11-24

## 一句话结论

Server 是**单进程 ASP.NET Core 8 宿主**，全部复杂度集中在两层：
一层是 **C# 编排层**（2788 行，其中单个 God service 占该层 34%），
另一层是 **内嵌 JS 世界引擎**（2488 行，`mapgen.js` 一个文件占该层 78%）。
C# 不生成任何地形，只做「调 JS → 拼 protobuf → gzip → 三级缓存 → 下发」。

依赖方向严格单向：`Web → Services → (Engine, Storage, Protocol, Domain)`。
`Domain` 只依赖 protobuf-net，`Protocol` 不依赖业务，两者是前后端唯一共享契约。

### 3.3 编排层（1 个文件，952 行）

`MapWorldService.cs` 一个类承担 7 项职责：

1. **构建编排**：`BuildChunk/BuildRegion/BuildComm/BuildSettle` —— 调 `vm.Call(...)` 拿 JSON，逐字段搬进 DTO
2. **协议组装**：`GetTileBlock` 按 mask 位把 5 个图层拼进一个 `TileResponse`
3. **多级缓存**：7 个 `LruCache` + 2 个 `ConcurrentDictionary`（详见第五节）
4. **并发控制**：`BuildOnce` per-key 门闩（同 key miss 只建一次）
5. **新鲜度**：`_roadVerCache` 单调取大，比 V8 门闩便宜
6. **世界台账出口**：`WorldCurrentJson/WorldNextJson/WorldListJson`
7. **后台维护**：`MaintenanceLoopAsync` 每 2 分钟 Flush + `PruneExcept` + 裁 `_blockRev`

## 四、一条 WS 请求的完整链路

以「客户端申请一个块 `(i,j)`，mask=All」为例：

1. `MapWsHandler.Map` 读满一帧 → `type=2` → `HandleTileAsync`
2. 反序列化 `TileRequest`，校验 seed 非空
3. `mask = mask==0 ? All : mask & All`；未登录则剔掉 Settle/Poi/Comm 位，并把被剔位记进 `DeniedMask`
4. `Task.Run(() => svc.GetTileBlock(...)).WaitAsync(ct)` —— 全同步管线丢线程池，客户端断开可提前放弃等待
5. `GetTileBlock`：读 5 个 rev，用 `Need(bit)` 判断「mask 命中 且 客户端未持有或 rev 已变」；全不变则直接返回最小响应
6. `World(seed)` 借出 VM（`_inFlight++`，LRU 期间不会 Dispose）
7. `needChunk` → `GetChunkBytes` → `_mem` → SQLite 回填 → 否则 `BuildOnce` 内 `vm.Call("chunkJson")` → JSON 解析 → 逐段切定宽 buf → `ProtoCodec` → gzip → `Store`
8. `GetBlockLayers(vm, seed, i, j)` → `blockLayersJson` → 得到本块覆盖的 region/comm 格（走 `_blockLayersCache`）
9. `needRegion/Settle/Poi` → `RegionPackOf` / `SettlePackOf`（解压+反序列化结果也缓存）→ 聚落按 `Type=="poi"` 拆到两个图层
10. `needComm` → `GetCommBytes` → `UnwrapCached` 解压成原始 protobuf 嵌进 `TileResponse.Comms`
11. `SendFrameAsync(gzip: true)` → 帧 `[2][gzip(protobuf)]`

## 五、缓存与持久化骨架

| 缓存 | 容量 | 内容 | 落库 |
|---|---|---|---|
| `_tileCache` | 1024 | 单格详情 gzip + 生成时 roadVer | 否 |
| `_gridCache` | 64 | 小地图字段网格 JSON | 否 |
| `_regionHot` | 512 | 区域包 gzip | **否**（T2：只写不读，纯写放大） |
| `_rawCache` | 2048 | chunk/comm 解压后 protobuf | — |
| `_blockLayersCache` | 1024 | 块→region/comm 归属映射 | — |
| `_regionPackCache` | 512 | 区域包反序列化对象 | — |
| `_settlePackCache` | 512 | 足迹包反序列化对象 | — |
| `_mem` | 8192 | chunk/settle/comm gzip | **是**（异步批量） |
| `_blockRev` | 无上限 | 块级 5 图层 rev | 否（按活跃 seed 裁） |

键空间（`WorldKeys`，seed 先 SHA1 取前 16 位十六进制）：

```
w:<16hex>:chunk:<ca>:<cb>     落库
w:<16hex>:comm:<ci>:<cj>      落库
w:<16hex>:settle:<i>:<j>      落库（建筑足迹会演化）
w:<16hex>:region:<i>:<j>      只在内存/会话内
Data(Key,Value) 之外的独立表：World(Round, Seed, BornAt)
```

## 六、并发模型

| 机制 | 位置 | 保护对象 |
|---|---|---|
| `SemaphoreSlim _gate` | `JsWorldVm` | 单个 V8 引擎不可重入 |
| `_inFlight` 计数 | `JsWorldVm` | 在跑的引擎不被 LRU Dispose（Dispose 会崩进程） |
| `_buildGates` per-key 锁 | `MapWorldService.BuildOnce` | 同 key 并发 miss 只建一次 |
| `_roadVerLock` + 单调取大 | `MapWorldService` | 旧采样不覆盖新版本 |
| `_flushLock` | `SqliteVirtualContext.Flush/PruneExcept` | 批量写与 DELETE 不交错 |
| `lock(_metaLock)` / `lock(_gate)` | meta 缓存 / WorldLedger | 首次构建与台账追加 |

## 七、结构性问题（按优先级）

### P1 限流保护在现状下基本落空

`ApiRateLimitMiddleware.cs:30-31` 只拦 `/api/map/tile` 与 `/api/map/fields`，
但图数据主通道已经是 `/ws/map`（`MapWsHandler.cs:30`）。
R6 的设计目标是「保护 V8 门闩不被高频请求钉死」，而 WS 侧**没有任何 per-IP 限流**，
一个客户端可以无限发 `TileRequest` 让 V8 全速跑。
HTTP 那两个端点反而只是信息面板与小地图轮询。修法：把限流抽成可复用的计数方法，在 `HandleTileAsync` 入口按连接 IP 也计一次。

### P1 `MaxSeeds` 双默认值漂移

`Options.cs:14` 是 `4`（注释 T13 明确「默认由 3 提到 4」），
但 `appsettings.json:14` 写死 `3`，配置覆盖代码 → **实际生效 3**。
这台机器上跑验证时「按默认 3 建实例，第 4 个 seed 立刻被淘汰」的坑就来自这里。
修法：二选一对齐，或在启动日志里打印「配置值 vs 代码默认」不一致告警（`Program.cs:52` 已经打印 MaxSeeds，可加一行来源标注）。

### P2 `MapWorldService` 职责过载

952 行、7 类职责（见 3.3）。任何一层要改（缓存策略 / 协议字段 / 世界台账 / 维护任务）都要动同一个 900 行的类。
拆分建议按依赖顺序：`BlockAssembler`（第 5、6、7、8、9、10 步的组装逻辑）→ `CacheSet`（7 个 LRU + roadVer 观测）→ `MaintenanceService`（后台任务）。三者都不改协议，可独立验证。

### P2 死代码与「该删未删」

| 位置 | 情况 |
|---|---|
| `MapEndpoints.cs:16` `MapGet("/")` | 永远不执行 —— `StaticWebMiddleware.cs:62-63` 已把 `/` 映射到 `index.html` 并直接返回 |
| `MapMessages.cs:91-92` `SettlementDto.Buildings/Resources` | `mapgen-server.js:89-94` 已不再下发这两个字段，`MapWorldService.cs:247-256` 的读取逻辑只在「旧持久化区域包」上生效，注释已自认是冗余 |
| `MapWorldService.cs:252-256` | 同上，`GetProperty` 链读不到东西恒为空 |

### P3 `BuildOnce` 的双检与实际主缓存不一致

`BuildOnce`（第 426 行）只 double-check `_mem`，但区域包的主缓存是 `_regionHot`（第 194 行）。
当 `_mem` 被 8192 上限淘汰、`_regionHot` 仍有值时，同一 key 的并发等待者会重复 `BuildRegion`（包含一次完整 A*，实测首请求 ~196ms）。
影响是「偶尔多算一次」，不是错误，但属于缓存分层没对齐。

### P3 `mapgen.js` 是单文件 God module

1932 行 / 约 60 个函数 / 11 个区段，且 `settlementsFor → growTownFootprint → roadsNear → bfsRoad` 之间存在跨区段调用。
任何参数调试都必须整文件加载（这也是 `verify/` 必须严格按 `[noise, mapgen-config, mapgen, mapgen-server]` 顺序拼接的原因）。
短期不建议拆（拆了会破坏「引擎脚本经 WS 单包下发」与 S4 引擎指纹的 SHA256 口径），
长期若要拆，必须先让 `EngineScriptOrder` 支持列表化 + 指纹算法同步改。

### P3 内存只有条数上限，没有字节上限

7 个 LRU + `_mem` + `_blockRev` 全部按**条数**限容。
单块 gzip 实测 10~40KB，`_mem` 8192 条最坏可达数百 MB；chunk 尺寸随精灵数增长。
`MaxSeeds` 调大 + 多客户端漫游时这是唯一无明显上限的维度。

### P4 `Program.cs:28` 硬编码 `http` 与 `0.0.0.0`

`UseUrls` 固定 http、固定全网卡，没有从配置读 scheme/绑定地址的入口。
局域网调试方便，但无法上 HTTPS，也不能只绑 `127.0.0.1`。
