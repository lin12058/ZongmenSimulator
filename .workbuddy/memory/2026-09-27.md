## ⚠⚠ 后端启动永久挂死 —— DI 循环依赖（2026-09-27 上午；用户报「卡在正在生成」）

### 现象 → 定位手法（可复用）
用户报 `dotnet run --project .\Server\Zongmen\` 一直卡住、后端打不开。前端那行
「正在生成」实际是 `#fatal` 面板的标题 **「山河未成」**（`web/index.html` line 484）。

排查链（每步排除一批可能）：
1. `netstat -ano | grep 8140` = **无监听**；进程**活着** ⇒ 不是崩溃，是**挂起**。
2. `curl` 返回 **502** ⇒ 是**本机代理**（`HTTP_PROXY=127.0.0.1:9105`）回的，不是后端。
   ⚠ 判后端死活必须 `NO_PROXY='*' HTTP_PROXY= HTTPS_PROXY= ALL_PROXY= curl …`。
   绕开后得 `HTTP 000` / rc=7 = 连接被拒，才是真相。
3. `dotnet build` = 0 警告 0 错误 ⇒ **不是编译问题**。
4. `timeout 60 dotnet run > log` ⇒ log **0 字节**、rc=124 ⇒ 连 ASP.NET hosting 日志都没有
   ⇒ 卡在 **Kestrel 之前**。
5. ⚠ `/tmp` 在本机映射到 `D:\tmp`（`node /tmp/x.mjs` → `MODULE_NOT_FOUND D:\tmp\x.mjs`）
   ⇒ 临时脚本一律写 **`verify/_tmp/`**，用完删。
6. Bash 重定向会吞输出（与 MEMORY 里「PowerShell 输出被吞」同源）⇒ 改**用 Node `spawn` 抓流**，
   确认 **25s 零输出、进程不退出**。
7. **在 `Program.cs` 顶部插 `Console.Error.WriteLine($"[boot +{sw.ElapsedMilliseconds}ms] …")` 计时桩**，
   逐段打点 ⇒ 一次夹出区间；再在区间内**逐个 `GetRequiredService` 打点** ⇒ 一次精确定位。

### 根因（一行）
```
TickPump → ITickExecutor → TickPump        ← DI 循环
```
`Program.cs` 的 factory lambda 写了 `new TickVmPoolExecutor(…, sp.GetRequiredService<TickPump>(), …)`，
而 `TickPump` 自身依赖 `ITickExecutor`。
⚠⚠ **因为走手写 factory lambda，绕过了 .NET DI 的循环检测** ⇒ **不抛异常**，
而是**永久静默挂死**（进程活着 / 不监听端口 / 零日志）。
⇒ 这正是 MEMORY 里「world⇄pump 循环引用 ⇒ 必须用委托倒置」的**同一条坑，漏了 pump 这一侧**：
   当时只给 `MapWorldService` 包了 accessor，却把 `TickPump` 直接注入了执行器。

### 决定性证据 + 修法
`grep -n "_pump" TickVmPoolExecutor.cs` ⇒ **只有声明行 + 赋值行，全文从未使用**。
那个 `TickPump` 参数是「以后可能要用」的空引用，却把整个后端钉死。
修法（**零功能损失**）：删 `_pump` 字段 + 删构造参数 + 删 `Program.cs` 里那一半实参。

### 教训
1. **手写 factory lambda 注册的 DI 会绕过循环检测** ⇒ 环变成**静默死锁**；
   声明式 `AddSingleton<A>()` 会抛 `InvalidOperationException`，反而不容易踩。
2. **注入而未使用的依赖 = 定时炸弹**。宁可删掉，真需要时再委托/accessor 倒置。
3. **裸构造期（DI 之前）无日志** ⇒ 这类挂起只能靠**手动计时桩**定位。
4. 「后端没起来」排查顺序：端口 → 进程 → curl（**必须绕代理**）→ build → stderr → 计时桩。

### ★ 判据抓出的两个**真实生产 bug**（不报错的那种）

1. **哨兵溢出**：`CommitSuccess` 在 `NextTick` 仍是 `long.MaxValue` 时算下一跳 ⇒ `MaxValue + Period`
   **溢出成负数** ⇒ 命中兜底分支 ⇒ 下次到期是随机负数 ⇒ job 立刻被再收集 ⇒ 相位错乱（间隔出现
   8/12/46/342）。**修法**：`job.NextTick = nowTick + job.PeriodTicks`（复位哨兵 + 严格 += Period，**不读旧值**）。
2. **相位钥匙用错枚举名**：`PhaseHash` 用 `kind.ToString()`（`DemoHeartbeat`）派生相位，而 `TickJobStore`
   落库存**线上名**（`demoHeartbeat`）⇒ 对账/重建相位不同，**改个枚举成员名就让全世界相位漂移且不报错**。
   **修法**：改用 `KindNames.Of(kind)`。

### R11（推翻 v2 原文）

v2 写「`.NET PriorityQueue` 非线程安全 / 无 decrease-key ⇒ 调度器必须单线程独占」——**已推翻**。
自实现 `ConcurrentTickQueue`（`lock` + 二叉小顶堆 + `Dictionary<JobKey,int>` 键索引 +
`volatile int _countHint` 无锁空转快路径 + 吊销哨兵），**任意线程可投递**。理由：tick 泵不是唯一生产者
（`commitPlace`/对账/一次性事件都从 Kestrel 请求线程来）；临界区只是 O(log n) 指针交换、不做 I/O/不做 proto；
`lock` 纳秒级 vs V8 十毫秒级。**已用真 OS 线程压测证明**（8 线程 × 2000 job，零重复零丢失）。

**★ 侦察得出的三条决定性事实**：

1. **`growTownFootprint(id, type, cq, cr)`（`mapgen.js:936`）签名里没有时间维度**，且按 id 缓存
   ⇒ 同一座城永远长同一个样 ⇒ **城内演化能力为零**，必须新增。
2. **`tradeEdgesFor(i,j)`（`mapgen.js:1102-1149`）+ `townNet(st)`（`mapgen.js:1090-1100`）是现成纯函数**：
   已实现「±2 环邻域 + `hexDist ≤ TRADE_REACH(40)` + 每对只算一次(小 id 发起) + 按 `RES_ORDER` 八资源
   取缺口最大者」，产出 `{key, from, to, resource, amount, dist}`。
   ⇒ 用户要的「资源互换」**不需从零造**；它现在是死的**只因为 `pop` 是 `hash01` 常量**。
3. **载体已就位**：`TickJobKind.TownEvolve`/`TradeEdge` 已声明，`TickJobRegistry` 已写好 spec
   （L1/V8/90 与 L1/Cpu/30），`TickPump.ApplyOutcome`（`TickPump.cs:253`）就是唯一写世界入口。
   ⇒ 工作量在「引擎演化公式 + 决策脚本 + 接线」，不在框架。

**★ 一个必须拒绝的直觉改法**：把 `maxN = CFG.TOWN_BUILD_MAX[type]`（`mapgen.js:952`）改成依赖 `pop`。
理由（三条，不是偏好）：
- `growTownFootprint` 产物进 `townCache`，而 `townCache` **参与 `townNet` 计算**（`mapgen.js:1091`）
  ⇒ 一旦它依赖可变的 `pop`，`tradeEdgesFor` 变成 tick 可变 ⇒ `tradeCache` 失效条件不可判；
- `pop` 回退（灾荒）⇒ `maxN` 变小 ⇒ 建筑**消失**，而 `buildings[]` 是 `spreadPick` 空间均匀取的
  ⇒ 删一个建筑**级联改变其余建筑位置** = 视觉上「整座城重排」；
- `townCache` 被清 ⇒ 跨区域（±2 环 = 25 个区域格）的 `tradeEdgesFor` 全部重算。

**∴ 演进式生长必须做在覆盖层（`$base + evoIn`），不能改 `maxN`。**

### v2 方案核心设计

- **第一层（城内）**：新 `CityState`（`pop`/`tier`/`state`/`stock[8]`/`built[]`/`upg[]`/`bornTick`）
  作为**演化覆盖层**，`settlementsFor = $base.map(applyCityState).concat(extIn)`。
  动力学取真实城市模型：Verhulst 人口增长 `dP/dt = r·P·(1−P/K)`，承载力 `K` 由**库存余缺**反推
  ⇒ **这就是第二层反哺第一层的位置**。
- **第二层（城际）**：复用 `townNet` + `tradeEdgesFor`，**唯一实质扩展 = 加结算步**
  （`stock` 双方扣加）。人口一动 ⇒ 缺口变 ⇒ 边自动重排 ⇒ 闭环。
- **资源守恒取「半守恒」**（每城独立演化 + 交换只是搬运）而非全图守恒 —— 理由：全图守恒需要
  全局顺序，会**毁掉 `TickPartitioner` 的按实体并行**。
- **两类意图两条通道**：城内演化（绝大多数）走 `CityStateStore` 新独立表（微秒级）；
  改变世界实体（极少，如新城诞生）才走 `commitPlace`（405~443ms）。
  **这是全方案的取舍核心** —— 若城内演化也走 `commitPlace`，200 座城 × 每季 400ms 根本跑不动。
- **新表 `CityState` 必须独立**（`PruneExcept` 会静默删 `Data` 表的非活跃 seed 前缀）。
- **脚本契约**：`evolveDecide(snapshotJson) → intents[]`（稀有，喂分批快照）+
  `evolveStepBatch(statesJson[], dtTicks) → newStates[]`（高频热点，必须批量）。
  ⚠ 两个新出口都要挂 `JsEngineHost.Call` 的 switch。
- **沙箱**：`ScriptTimeout` 200ms 试 / `MaxHeapSize` 64MB 试 / VM 池独立于读路径（零门闩争用）/
  ⚠ **超时后该 VM 实例必须作废重建**。
- **12 条判据**（C1~C12）+ 8 条风险（R1~R8）+ 三级回退（L1 停演化 / L2 清演化层 / L3 卸覆盖层）。
  ⭐ **L3 是保险丝**：因为演化是纯叠加，卸载它零残留 ⇒ 零风险渐进上线。
  这也是选覆盖层而非改 `maxN` 的第三个硬理由（改 `maxN` 不可逆）。
- **落地顺序 E1~E8**，E1~E4 完成时**世界表现不变**（还没接 job）。

- **ClearScript 是 7.4.5**（`Zongmen.csproj`）⇒ `IArrayBuffer` 只有 `byte[]` 重载；**`ReadBytes/WriteBytes(Span<>)` 与 `InvokeWithDirectAccess` 是 7.5.1+**；`SharedArrayBuffer` 跨 runtime 共享 7.2+ 有。⇒ 「零拷贝」要升级（换原生 dll，须全量回归）。⚠ **宿主如何拿到 `IArrayBuffer` 句柄必须 spike 验证，不假设 API 名**。

### ★★ 四个真实 bug（都是「不报错但结果错」那一类）

1. **Δ 铁律：判据形式必须「连续累加」而非「重喂 s」**。v2 §七 C3 / line 450 原文写
   `evolveStep(s,90) ≡ 9 次 evolveStep(s,10)`，字面读像「每子步都从 s 出发」——**那样数学上必不相等**

2. **K 必须在批内冻结（Kf）**。Verhulst 闭式解 `K/(1+((K−P0)/P0)e^{−rt})` **只在 K 为常数时精确**。

   ⇒ 360 vs 12×30 的 Δpop 达 **337**。修法：K 在季首算一次存 `Kf`，批内 9 子步复用。
3. **⚠ 绝不逐子步 `round(pop)`** —— 最隐蔽的一个。单日增量可能 <0.5

   ⇒ 修后 360 vs 360×1 的 Δ = **4e-10**（机器精度）。**这是 Δ 铁律能抓出、而「跑一遍看看」抓不出的典型。**
4. **量纲错：骨架产出被多除一个 `T.Season`**。`plan.resources[].amount` 已是**日**产出，
   人口消耗 `pop/TRADE_DEMAND[r]` 也是日 ⇒ 直接相减。原式 `sup/T.Season − drain` 把产出缩小 90 倍
   ⇒ stock 恒为负 ⇒ 永远钉 0 ⇒ **贸易无货可运（结算 0 笔）**。修后：粮 137382 / 灵 104241 / 渔 66438 …
5. **`state=3` 判据自相矛盾**：`pop < kBase×0.35` 而 `kBase = popBase×4.0`

   修法：判据相对**自身基准 popBase**，跌破 70% 才灾荒、回升 90% 才解除。

### ⚠⚠ 但闭环只有**上半程** —— 这是下一步要解决的**设计**问题 (不是 bug)

`seed=city-evo-integration-1` 8 年逐季实测:

| 阶段 | 人口 | 建筑 |
|---|---|---|
| 0→1.5 年 | 987186 → **993479** (+0.6% 峰值) | 2480 → **4901** (+98%, 冲到 cap) |
| 1.5→8 年 | 993479 → **951237** (-4.3% **单调衰减**) | **4901 恒等** (6.5 年零变化) |

全程 `ev=0` (灾荒城恒 0), tier 只升不降。⇒ **涨得起来、跌不下去、更不会重建**。

**根因两条 (都在「口径」不在「系数」)**:

1. **量纲错位 —— 同一次供需判断挑了两半不同的口径**:
   - `resourcePrices` 用 `need = pop / DEMAND` (需求**随人口增长**);
   - `attractivenessOf` 的拉力用 `sup` = 骨架 `plan.resources` (与人口**无关的常数**)。
   ⇒ 价格算出来「缺」, 吸引力算出来「不缺」, 闭环自相矛盾。
   且张力 `(need-have)/need`: 若这是新城的满额缺口 ⇒ `tanh(1.5)=0.905`,
   人口再涨 100% 也只到 0.964 ⇒ **价格信号早已触顶饱和**(8000 人城与 80000 人城涨价只差 0.1%)。
2. **库存只能进不能出 —— 物理上封死了稳态** (这条更硬, 与口径无关):
   库存日变 = `sup - pop/DEMAND`; `sup` 是常数。
   设均衡 `pop* = sup × DEMAND`, 而骨架 `sup` ≈ `pop0/DEMAND` (骨架 own-pop 正好平衡)
   ⇒ **`pop* = pop0`**, 也就是说库存的「零增长点」恰好卡在**入口人口**。
   把 `hat = stock + (sup-drain)·dt` 代入价格: **人口 +1% ⇒ 库存日增 ≈ 6 (仅 +3%)**,
   而每日需求 ≈ 81 ⇒ 价格几乎**完全看不见**人口变化。
   ⇒ 涨价杀不死人口, **唯一在起作用的净负反馈只剩迁移** ⇒ 迁移极差驱动的单调衰减。
   ★ 含义: 「**多造田**」根本没有回路 —— `E.R0` 只有 **8.3e-5/日**, 1.25 年就撞 K,
   新田要 `FIELD_TRIGGER=0.25` 才开; **生产端增长天生比人口增长慢 2~3 个数量级**。
   ⇒ 若要让「种田 → 价格下降 → 人口迁入」真转起来, 只有两条路:
     ① 给人口增长加**承载力 K 的显式依赖**(让造田直接抬 K);
     ② 或让**库存以远高于 3% 的权重进入价格/吸引力**(把积累变成真信号)。
     这两条都是**设计决策**, 得用户拍板, 不宜自行调参。
