## 玩家放置宗门方案 · v3 修订（「附近城市重算」代价分账 + roadVer 归零坑）

### 用户追问与纠正

- 用户原话（09-23 凌晨）：「附近城市直接重新算太久了是吧？」
- 这是一个**提法本身需要纠正**的问题：贵的是**道路**，不是城市。

### 实测（`verify/check_place_road_recompute.mjs` 段 6，本轮新增）

| 项 | 实测 | 口径 |
|----|------|------|
| 道路重算 | **405 ~ 443 ms** | 热地形，只清 `roadCache`/`roadFail`/`demandCache`/`skeletonCache`，25 区域格 |
| 城市重算 | **31 ms**（纯城市 ≈ **23 ms**）| 热地形，只清城市链路缓存 |
| 城市重算（全命中）| 0.2 ms | 下界对照 |
| 全冷（含建地形）| 370 ms | 上界，只有重启/换 seed 才会遇到 |

⇒ **道路 ≈ 纯城市的 19 倍。**

### 关键结论：两笔账不能记成一笔

- `growTownFootprint` 只读 `fields` / `landuseOf` / `veinNear`（`mapgen.js:950~975`），**不读道路**。
- 玩家实体按方案 §2.4 **不进** `settlementsFor$base` 的抑制逻辑 ⇒ 既有聚落的中心 / 足迹 / 建筑**逐字节不变** ⇒ **既有城市根本不需要重算**。
- 用户说的「附近城市对应的道路重算」，要重算的是**路**。

### 新钉的红线（最易漏，症状是「用户觉得卡」而非报错）

**`roadVer` 只能 +1 增量，绝不能归零。**

- `resetRoads()` 把 `roadVer = 0`（`mapgen.js:1851`）；服务端 `ObserveRoadVer` 单调取大（`MapWorldService.cs:114~121`）。
- 两者相撞 ⇒ 服务端 known 保持旧值 N，而 tile 缓存条目 `TileEntry.RoadVer` 也是 N ⇒ 判据 `cached.RoadVer == known`（`:694`）**仍成立** ⇒ 路重建了却**永远送不出去**（"改了没反应"，无异常无日志）。
- 若客户端将来改成按值跳变重拉，归零则 ⇒ **全图 tile 一次失效** ⇒ 前端重拉视野内所有 tile —— 这才是真正的"太久"，与 405 ms 的引擎开销不是一个量级。
- ⇒ 实现口径：**只按边 `roadCache.delete(rkey)` / `roadFail.delete(rkey)` + 显式 `roadVer++`；绝不调 `resetRoads()`**。

### 判据改动

- `verify/check_place_road_recompute.mjs`：
  - 新增**段 6**（城市 vs 道路分账），为此加两个出口：`__clearCity`（只清城市链路、**保地形热**）/ `__cacheSizes`。
  - 把「warm 是否充分」做成**断言**（warm 覆盖率 ≥94%），并把漏 warm 的地形钱**单列**（419 格 ≈ 8 ms），避免把地形钱算进城市值。
  - 计时改**交替多轮取中位**：首测 85 ms（含 JIT）vs 中位 31 ms，差 2.7 倍。
  - 现 **4 PASS / 0 FAIL，约 25 s**。
- `verify/run_regression.mjs`：注册 `['check_place_road_recompute.mjs', ['seed-check','5','1','3'], 'off']`（在 `check_place_neighborhood.mjs` 之后）。
- `docs/玩家宗门放置与城市迭代方案.md`：新增 **§3.6**（两笔账 + 红线 4）；§3.5 数字统一为区间 **405~443 ms**；风险表新增 **#14**，并把 **#13 升级为 🔴 高**（roadVer 归零）。

### 方法论（值得复用）

- **测「重算代价」必须先 warm 掉上一层的缓存**，否则测出来的是「上一层 + 本层」的混合值。且 warm 是否充分要**做成断言**（本次用 field 缓存增量占比），不能只靠"我觉得热了"。
- 首测总含 JIT（本次 85 ms vs 中位 31 ms，2.7 倍）⇒ **必须交替多轮取中位**；单次计时能给出完全错误的结论（本判据第一版就栽过）。
- 用户问「X 是不是太久了」时，先确认**「X」的定义边界** —— 本次用户口中的"城市重算"实际是"道路重算"。边界不清就答，会把两笔账记成一笔。

## 玩家信息表设计（新文档 `docs/玩家信息表设计.md`）

用户要求：玩家信息放 SQLite **一张表**、**JSON 存储**（"后续字段可能会频繁改动，不用 protobuf 了"）。

### 关键决策

| 项 | 结论 |
|----|------|
| 表名 | **`PlayerSect`**（原方案叫 `PlayerPlace`，已全局改名 —— "Place" 名不副实）|
| 粒度 | 一账号 × 一世 = 一行。主键 `(Account, Round)` |
| 存储 | **混合式** —— 主键 + 热查询列提列，其余进 `Json TEXT` |
| 必须独立表 | 与 `World` 同理：写进 `Data(Key,Value)` 会被 `PruneExcept` 每 2 分钟静默删除 |
| 字段数 | P0 **25 个**（3 身份列 + 11 渲染必需 + 5 玩家特有 + 6 元数据）|

**为什么不能全 JSON**：引擎生成**每个区域包**都要问"这格有没有玩家宗门"（热查询）。全 JSON ⇒ 每包一次全表读 + 逐行 `JSON.parse`，且无法用索引。**提列判据**：字段第一次进 `WHERE`/`ORDER BY` 时提。

**为什么不能全列式**：用户明确说字段会频繁改 ⇒ 每个玩法字段都要 `ALTER TABLE` + 迁移。

### ⚠ 本轮最有价值的发现：修正上游一处会静默失效的错误

上游方案 §4.3 写 `EntId TEXT PRIMARY KEY -- p_{round}_{n}` —— **错**。

证据（`mapgen.js`）：
- `:1209` NPC 聚落 id = `i + '_' + j + '_' + k`
- `:1221` poi id = `i + '_' + j + '_p'`
- `:1651` `var pAp = pA.id.split('_'), spk = pAp[0] + ',' + pAp[1]; skeletonEdgesFor(+pAp[0], +pAp[1])`

⇒ 引擎**反解 id 前两段为区域格坐标**。`p_3_1` ⇒ `+pAp[0]` = **NaN** ⇒ `skeletonEdgesFor(NaN, 3)` ⇒ **不抛异常、静默扫出空池**（与方案 §3.2 坑 E 同型）。

⇒ 正确格式 **`{区域i}_{区域j}_u{n}`**：前两段必须是区域格数字串；后缀不能是纯数字（撞 NPC 序号 `k`），也不能是 `p`（poi 已占）。已在 `PlayerSectStore` 设计里加落库前断言。

### 关键纪律：不存派生量

- ✗ `x`/`y` —— `tileToWorld(q,r)` 的派生量。存了就有两处真相（"数据在东、画在西"，不崩溃）
- ✗ `styleName` —— `STYLE_NAME[style]` 查表派生
- ✗ 任何"产出速率" —— 由 `buildings` 派生。`buildings` 是真相，`stock` 只是当前值
- ✗ 自动聚落的一切 —— 按 seed 可复现

### 读路径必须内存镜像

`MapWorldService` 生成区域包时**绝不能查库** —— 每包一次 SQLite 往返会毁掉方案 §3.6 实测的 405 ms 预算。照 `WorldLedger` 惰性全量加载 + 落定/升阶/拆除时**同锁内**同步更新镜像（否则会出现"落定成功 → 立刻重拉 → 拿到不含自己宗门的包"竞态）。

### 待拍板（6 项）

① `stock` 走乙案（存净库存，因宗门经营必有消耗）② 离线收益 P0 不做但留 `tickAt` ③ `Account` 明文无鉴权 ⇒ 先只在局域网用 ④ 历史 `Round` 行保留全部 ⑤ `disciples`/`queue`/`chronicle` 先占位 ⑥ 已定表名 `PlayerSect`。
另**新增 `v`（JSON 结构版本号）到字段清单** —— 初稿把它列进"不做"，后判断错：它的价值只在于**先有**（一旦库里有没带 `v` 的行，之后任何结构变化都只能靠猜）。
