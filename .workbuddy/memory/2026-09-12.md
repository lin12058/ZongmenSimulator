## 灵脉预览页新增「聚落 / 道路」层

需求：预览页也要能查看城市建筑与道路。文件仍是自包含单文件 `灵脉预览.html`（引擎内联）。

### 接入的引擎接口
- `MapGen.settlementsFor(i,j)` → 区域格内聚落数组
  `{id, type:'sect'|'city'|'town'|'village'|'poi', q,r,x,y,name,pop,owner,tier,state}`
- `MapGen.roadsNear(i,j,budget)` → `{key, pts:[{x,y} 世界坐标], tiles:Set"q,r", x0,x1,y0,y1}`
  budget = 本次允许新算的 A* 条数；0 = 纯读缓存
- `MapGen.roadCache`（cap 4096）、`MapGen.REGION_M`

### 关键事实：**聚落网格 ≠ 群落晶格**
- 聚落按 `REGION_M = 18` 格的**区域格**排布；群落按 `CFG.COMM_CL` 格排布。两套独立网格，互不影响。
- `settlementsFor` 不读 COMM_CL，所以调 COMM_CL 不会改聚落分布；改 `SPIRIT_R_TILES/SPIRIT_CURVE` 会（密度公式 `h0 < 0.20 + 0.38*spiritAt`）。
- `init()` 与 `configure()` 都会清 `settleCache`/`roadCache`（mapgen.js:181、882-883）→ 换种子/换参数后聚落与道路都会重建。

### 实测代价（`verify/bench_preview_settle_road.mjs`）
1400×800 画布，初始 scale≈0.077（1 格≈1.07px），可见区域格 **101×53 = 5353**：
- 聚落扫描：冷 138ms；**但引擎 settleCache 只有 1024 容量 → 反复淘汰，热扫一度升到 294ms**
- 道路 A*：**单条约 40ms（个别最坏 380ms）**；可见范围全建 400 条 ≈ **16 秒**

### 因此本页做了三层保护
1. **本页再缓存一层聚落**（`settleLocal` Map，cap 30000）→ 只对抗引擎容量淘汰；缓存命中后拖动帧耗时 2ms。
2. **道路只在视野中心 ±N 区域格内渐进建造**（默认 8 区域格 ≈ ±144 格），每轮 1 条、间隔 24ms，逐轮让出主线程。实测 ±8 区域格 289 格 → 120 格有可建路聚落 → 104 条路 / 245ms / 单轮 max 75ms。
3. **队列跳过「无可建路聚落」的空区域格**（跳过约 58%），并加 `scanned<40` 上限压最坏帧。
4. 聚落绘制门控：区域格 < 2.5px 时不扫（否则区域格数量按平方增长，扫一遍可达 4 万格 ≈ 1s）。

### UI
- 显示开关：`cb_settle` 聚落 / `cb_sname` 聚落名称 / `cb_road` 道路
- 道路参数：`roadCells` 建造半径（2~20 区域格）、`roadBudget` 每条/轮（1~8）、`roadClear` 清空道路缓存
- 标记形状：城市=方、城镇=圆、宗门=角、村庄=小圆、秘境=菱；颜色见 `SETTLE_STYLE`
- 名称旁显示 `·N格`（`hexDist(q,r,0,0)`，与灵脉标注一致）
- **悬停聚落弹 tooltip**（名称/类型/人口/等级/距中枢格数/区域格/地块），数据来自 draw 时收集的 `pickList`
- 统计面板增加「聚落 N 个 · 区域格 18 格/格」+ 道路状态（关 / 建造中 x/y / 缓存 N 条）

### 顺带修的遗留
- draw() 内 `rr` 被灵气渐变半径与灵脉半径重复 `var` 声明（同名遮蔽）→ 灵脉那处改名为 `vrr`。

### 验证脚本
- `verify/bench_preview_settle_road.mjs` — 聚落/道路耗时基准（决定预算与门控）
- `verify/check_preview_settle_road.mjs` — 4 脚本块语法 + DOM id 一致性 + 引擎导出 + 真实跑一遍聚落扫描/道路泵送

## 灵脉预览页：新增「地形层」（逐格群系色）

### 关键实测（verify/bench_preview_terrain.mjs + bench_preview_terrain2.mjs）
- **`fields()` 单格 21~30µs 冷 / ~5µs 最优**；单块 `buildChunk` ≈ 441 格 / 16ms（36µs/格，同量级，交叉印证）。
- **默认视野（scale≈0.077，1000 格量级）覆盖 1313×866 = 1137k 格** → 逐格渲染 = **100 秒级**，绝不可行。
  实测：stepT=16 → 4.6k 采样 120ms；stepT=8 → 18k 采样 378ms；stepT=1 → 1138k 采样 102.6s。
- 引擎 `fieldCache` cap 30000 / `elevCache` 40000：**采样数一旦超过 cap 就抖动**（stepT=4 的 71k 采样单次 38µs→2.7s，热重建反而更慢）。
  ⇒ 采样上限必须与 cap 同量级（本页取 **24000**），这样整张光栅都在缓存里，**热重建十几 ms**。

### 方案：离屏光栅 + 整数分级降采样 + 分帧渐进
- **光栅几何（唯一真源）**：光栅列 `i ↔ 世界 x = i*HEX_W`，行 `j ↔ 世界 y = j*TILE_H`（`TILE_H=1.5*HEX_R`）。
  即 rectified 坐标 `dx = q + r/2`；**cell i = floor(dx)** ←→ 反解 `q = Math.round(i - r*0.5)`。
  该不变式已逐格断言 18515 个地块全通过（`check_preview_terrain.mjs` ②）——这是地形图与真实格网对齐的唯一依据。
- **stepT 取整数（不是 2 的幂！）**：`stepT = max(capStep, blockOK)`，其中
  `capStep` = 满足采样上限的最小步长（成本下界）；`blockOK` = 满足块宽 ≤6px 的最大步长（不失真上界）。
  ⚠️ 早期用 2 的幂跳档，默认视野被 16 一档拖到 17px 色块、且 12000→24000 完全无效。改整数后默认视野 stepT=11 → 11.7px。
- **分帧构建**：每帧 ≤22ms 后 `setTimeout(0)` 让出主线程，边建边显示（putImageData 未填像素透明）；
  另开一张 canvas 构建、完成才 swap → 构建期间旧图继续显示，不互相污染。
- **缓存 + 外扩 25%**：视野逃出缓存矩形才重建；`pointerdown` 直接 `terrainAbort()` 丢弃半成品（拖动零重算），
  `endDrag` 才 `terrainEnsure(true)`；wheel 靠 draw 内的 80ms 防抖。
- **放大到能看清单格且该范围已被光栅预热**（stepT==1 且 coversRect）→ 改逐格画真六边形（+0.35px 消细缝），更精细且不冷不贵。
- 块宽 ≥14px 时 `imageSmoothingEnabled=true`（缩略成软渐变），小块保持硬边（忠实逐格真值）。
- 海拔明暗：陆地 `0.72+0.56e`，水下 `0.56+0.90e`。**灵脉中心被 LIFT_CORE 抬成山地/雪峰 → 地形上直接看得到灵脉山**。
- 签名 `seed + 全部 CFG 控件值`，变更即重建；灵气底色在地形在场时 alpha ×0.5（否则糊成一片蓝）。

|---|---|---|---|---|
| 0.077（初始） | 11 | 180×119 | 21.4k | 11.7px |

### 验证
- `verify/check_preview_terrain.mjs`：4 脚本块语法 + DOM id + 定位不变式 + 覆盖不变式（光栅矩形 ⊇ 视口，5 档缩放 × 2 机位）+ 真实构建耗时 + 群系分布不得单一。全绿。

## 灵脉预览页：地形层重构为「多级 LOD」+ 修掉放大糊的两个真因

### 症状
放大后地形糊成一团色块。**两个独立成因，缺一不可修**：

1. **缓存复用判据缺"缩放维度"**（原始 bug）
   `terrainEnsure` 只判 `签名 + 几何覆盖`，而 `terrainHexes` 又要求 `stepT===1`。
   放大后旧粗级（stepT=11）依然"覆盖"视口 → 判为可用 → **永不重建**；
   同时块宽被拉到 152~609px 触发 `imageSmoothingEnabled` → 一坨模糊；
   且 `stepT!==1` 让逐格六边形永远进不去。
   ⇒ 判据必须含「当前需求级」：`terrainLv[want]` 存在且覆盖才复用。

2. **防抖被 `pumpRoads` 饿死**（第二层，不加计数器根本看不出来）
   `pumpRoads` 每 24ms 就调一次 `draw()`；`draw()` 每帧调 `terrainEnsure()`，
   而后者是「clearTimeout + setTimeout(80)」的纯 debounce →
   **每次 draw 都把 80ms 重置，terrainStart 一次都跑不到**（探针实测 tstart=0）。
   ⇒ 改成「同一需求级不重复排程」：`if (terrainTimer && terrainArmedWant===want && !immediate) return;`

### 实现
- **LOD 阶梯 = 几何级数 ×√2**：`[1,2,3,4,6,8,11,16,22,32,45,64,90,128,181,256]`（16 级，级差 ≤2）。
  为什么不用 2 的幂：默认视野需求 9 只能进到 16 → 17px 色块（比原来的 11 差）；
  √2 阶梯量化到 11 → 11.7px，**与重构前一致，无倒退**。
- `terrainLv[stepT]` 每级独立缓存（含 `img` ImageData）；`wantStepT()` 由
  `max(blockOK, capStep)` 夹逼后量化到阶梯；`pickTerrainLv` 取"覆盖视口的最细级"，
  `pickTerrainFallback` 取最接近需求的级作过渡。
- **逐格六边形改为读 LOD-1 的 ImageData 取色**（不再每格调 `fields()`）→ 拖动不卡。
- **插值阈值反转**：旧代码 `blockPx>=14px 才开平滑`（大色块反而插值 → 糊）；
  改为 `每光栅像素 <2.5px 才开`，大像素强制硬边。
- 起点对齐到本级 step 倍数；空闲 160ms 后**向更细一级预取**（放大前备好，受采样上限约束）。
- 统计行显示：当前 LOD / 缓存级列表 / 需求级 / px per pixel。

### 实测（verify/check_preview_terrain.mjs + probe_lod.mjs）
| 档位 | LOD | 块宽 | 模式 |
|---|---|---|---|
| 默认 0.077 | 11 | 11.7px | 光栅 |
| 0.25 | 3~4 | 10.4~13.9px | 光栅 |
| 0.5 | 2 | 13.9px | 光栅 |
| 1.0 | 1 | 13.9px | **逐格六边形** |
| 4.0 | 1 | 55.4px | **逐格六边形** |
单调性 0.01→4.0 全档 ✔；预取链 11→8→6→4→3→2→1；默认视野冷建 107ms / **热重建 3~6ms**。

### 验证工具（新增/改写）
- `verify/check_preview_terrain.mjs`：改为 LOD 不变式（覆盖/对齐/单调性/预算/最细/逐格可达）
  + **回归断言**：`terrainEnsure` 必须含 `terrainLv[want]`、`coversRect` 必须已消失、
  插值阈值必须 `<3px`。（不写这条就可能被后来的改动悄悄改回去）
- `verify/probe_lod.mjs`（新）：注入探针到 **IIFE 内部**，先等初始级建完 → 再改 scale
  → 等收敛，把 `want/mode/lv/blk/levels/各计数器` 写进 `document.title`，`--dump-dom` 读回。
  这是唯一能复现该 bug 的路径（开局即 scale=1 反而触发不了）。
- 截图：`lod_default.png`(8%) / `lod_zoom_50.png`(50% 硬边色块) / `lod_zoom_100.png`(逐格六边形)。

### 通用教训（戒条级）
- **「缓存判据必须包含所有影响产物形状的输入」**。这里漏了 `scale`（决定 stepT）→
  放大后永远吃旧图。凡是"按覆盖范围复用"的缓存，都要问一句：产出物的**精度**由谁决定？
- **周期性 `draw()` 会饿死任何纯 debounce**。多个子系统共用一条渲染管线时，
  要么"同参数不重排"，要么用 dirty flag 而不是 clearTimeout/setTimeout。
- 症状相同的两个 bug 可能叠在一起；**先加计数器确认"函数到底有没有被调用"**，
  比读代码猜快得多（本次 `tstart=0` 一眼定位）。

## 引擎新增「灵气边界衰减」：界外全海洋 + 无聚落

需求：灵气边界半径之外原本还有地形与聚落 → 要变成"外面都是海洋、没有城市"，各配一个衰减系数，参考灵气强度。

### 实现（`Server/Zongmen/Engine/js/mapgen.js` + `mapgen-config.js`）
- 新增 `edgeKeep(sp, band)` = `NL.smoothstep(0, band, sp)`：把灵气强度映射成 **0..1 的"保留"权重**（sp≥band→1 不衰减；sp=0→0 彻底衰减）。
  两个系数：`EDGE_SEA_SP`(默认 0.30, 地形) / `EDGE_SETTLE_SP`(默认 0.35, 聚落)。置 0 = 硬边界。
- ① 地形 `elevAtVN`：**在灵脉抬升之后**加沉海 `gSea = 1 - edgeKeep(spiritAt(q,r), EDGE_SEA_SP)`,
  下沉目标 `EDGE_SEA_FLOOR(0.30) + (e-0.5)*EDGE_SEA_VAR(0.12)` ∈ [0.24,0.36] **恒 < SEA_LEVEL** → 界外必为海。
- ② `fields()`：灵脉覆写加陆地守卫 `vn.d<=1 && e >= SEA_LEVEL`（否则沉海的灵脉仍会吐 disp≥8 → 海面无根灵脉峰）。
- ③ `settlementsFor()`：`pSpawn = (0.20 + 0.38*spLoc) * edgeKeep(spLoc, EDGE_SETTLE_SP)`（秘境在同一 if 内，一并被门控）。
- ④ `communityOf()`：概率乘 `edgeKeep(sp, EDGE_SEA_SP)`（灵脉属地形的立体产出，不门控会在水下留空壳群落）。
- ⑤ 新增导出 `spiritEdgeWorld()` = `SPIRIT_R_TILES * HEX_R * 2`（边界世界半径唯一真源）。

### ⚠ 踩到的真 bug：权重方向写反
`edgeFade` 我按"衰减权重"命名，却实现成"保留"（smoothstep 输出 1 表示不衰减），于是沉海直接乘了它 →
**灵气越浓越沉海**：内圈整片被淹（环带 k=0.3~0.85 陆地 0%）、边界附近反而露出陆地（k=1.0 仍有 78% 陆地）。
症状极怪但只由一行决定。**修法**：函数改名 `edgeKeep`（语义只有一个方向 = 保留），沉海写 `1 - edgeKeep(...)`；
导出名同步改。**教训**：给"衰减/保留"这种双向语义的函数命名时，名字必须体现方向，并且在注释里写死"要衰减请用 1-x"。

### 口径坑（用户抱怨的直接原因）
- 引擎真边界 = `SPIRIT_R_TILES × HEX_R × 2` = 500×16 = **8000 世界单位 ≈ 577 格**（每格邻距 HEX_W=13.856）。
- 预览页旧边界圈用的是 `SPIRIT_R_TILES × HEX_W` = 6928 → 只有真边界的 **86.6%** ⇒ **圈内看着是界外**（圈外还有山/城）。
- 已全部改用 `MapGen.spiritEdgeWorld()`：边界圈、灵气底色渐变、统计行、滑块下的"实际格数"提示。
  头部文案也改了（"视野半径 1000 格"只是浏览范围，不是灵气边界，原文写成"（灵气边界）"会误导）。

## 灵脉标记：六角形徽标 + 与聚落同一套「自动放大缩小」

用户诉求（两条其实是同一处）：①"我要的是六角形的灵泉，而不是六边形"
②"把自动放大缩小改成和城镇一样的机制，而不是只在地图的一点点位置"。

### 口径判读（重要，避免下次再猜）
用户说的"六角形"= **标记/徽标**（一个能认出来的六角形图标），"六边形"= **格/面积**（按占地铺开的六边形色块）。
"只在地图的一点点位置"= 旧公式下只有放大到某处才看得清 → 等于"只有一小片区域能看到灵脉"。
所以两条一起指向：**把灵脉标记的尺寸从"格×scale"改成聚落那样的夹逼式自动缩放**。

### 改法（只在预览页渲染层；引擎未动）
- 抽 `markBase = clamp(MapGen.REGION_M*HEX_W*scale*0.16, 2, 16)` 到 `draw()` 顶部作**唯一真源**；
  聚落层 `var mBase = markBase;`（原来是就地重算一遍，两套会各自漂移）。
- 灵脉 `vrr = Math.max(2.2, Math.max(markBase, 3.0) * vf)`，`vf` = 大1.5 / 中1.0 / 小0.65（与聚落 tier 系数同构）。
  `max(markBase,3.0)` 是必须的：低缩放时 markBase 会掉到下限 2px 把三级压平成同尺寸
  （校验脚本一开始就报"大/中/小 尺寸序被打乱"，才发现）。
- 删掉旧公式 `Math.max(0.8, rTiles*HEX_R*scale)` 与整层门控 `cellPx > 1.5`，改为逐标记视口裁剪。
- 名称标签阈值改为随标记尺寸：大 ≥7px、中 ≥12px（否则低缩放下所有大灵脉都标名 → 标签风暴）。
- 图例/统计/侧栏说明同步："占地 2/1.5/1 格"（占地≠屏幕尺寸）；统计行加"标记 x/y/z px"。

### 实测（scale → 标记半径 px）
| scale | markBase | 大 | 中 | 小 | 旧公式·大 |
|---|---|---|---|---|---|
| 0.005~0.038 | 2.00 | 4.5 | 3.0 | 2.2 | 0.1~0.6（看不见） |
| **0.077（默认）** | 3.07 | **4.6** | 3.1 | 2.2 | 1.2（看不见） |
| 0.2 | 7.98 | 12.0 | 8.0 | 5.2 | 3.2 |
| 0.4~4.0 | 16.00 | **24.0（封顶）** | 16.0 | 10.4 | 6.4→**64.0（巨块）** |
任何缩放：大>中>小、都 ≥2.2px、都 ≤24px、随 scale 单调不减且 2× 后封顶。

### 验证
- 新增 `verify/check_preview_vein_marker.mjs`：4 脚本块语法 + DOM id + 静态契约
  （markBase 公式 / 聚落复用 markBase / hexPath 而非 ctx.arc / 旧公式与旧门控必须消失 / 图例三行 hex）

  另用新工具裁 1:1 局部：`verify/crop_vein400.png`、`crop_vein_default.png`。
- **形状朝向坐实**（不是靠肉眼）：把 400% 图裁出来逐行量"白描边+蓝填充"的宽度剖面 →
  顶行 7px / 中部 67px（比 0.10）⇒ **尖顶(pointy-top)六角形**，与 `hexPath` 的 `60k-90°` 定义一致；
  数学上也闭合：`hexPath` 的邻居方向 = 60° 整数倍、邻居距 √3·R；地块晶格邻居正是
  (±HEX_W,0)/(±HEX_W/2,±1.5HEX_R) 且 |v| = √3·HEX_R ⇒ R = HEX_R 时严格平铺。地形六边形同用 hexPath ⇒ 天然同朝向。
