## 调研：NPC 行为 & 玩家行为（纯文档，未动代码）

产出 `docs/游戏设计/NPC与玩家行为-调研与候选库.md`（NPC 8 组 62 条 + 玩家 12 组动词 + 咬合矩阵 + 10 部作品拆解 + P0/P1/P2 候选）。

调研得到的三条硬结论（后续做「小队跑起来」直接照这个走）：
- 现有「行为」只有一种：**在宗门干活**。`crew-model.js:127` 的 `JOBS` = 10 个静态活计，`activity.kind` 实际只用 `idle`；`squads[].settle` 只有驻地，**没有「在路上」状态** ⇒ 地图上当然没小队。
- ⚠ **时间尺度不匹配是真问题**：1 tick=1 秒，1 游戏年=360 tick=6 分钟 ⇒ **1 现实秒 = 1 游戏天**（快 720 倍）。「小队沿路走 30 格」若逐格播要现实 30 秒 = 游戏 30 天，与「一趟外出几个月」对不上。**结论：外出应做成「出发 tick / 返回 tick 两数 + 进度条」的惰性任务**（同招募值结算姿势），地图光点只做视觉插值，遭遇用 `hash01(seed, squadId, departTick, k)` 注入。
- 修仙题材行为天生分两套尺度：低境界做经济（采药/坊市/押运，天天见），高境界只剩闭关/渡劫（一个计数器）。**境界越高行为越少、尺度越长**，这本身就是 LOD。

另记：`activity.kind` 扩枚举时前端 `crew-bridge` 只判 `idle`，未知 kind 必须能降级；小队任务字段若加到 `squads[]`，会重蹈 `settle` 覆辙（整表替换静默洗掉）⇒ 必做「旧值非空则保留」。


## 招募系统：上线后第一轮 bug 巡视（2026-11-26 01:0x，已修 + 判据）

用户点了 3 次招募后让我"巡视一下"。查出 7 个真问题（全部有判据守着）：

1. **编制上限 8 vs 9**（最影响手感）：`crew-bridge` 把 `squad.capacity` 的默认值写成了 `STASH_ROWS`（背包行数 = 8），服务端 `SquadsCap` 又照合同读 ⇒ 第 8 个人就回「目标小队已满」，界面却显示 8/9。修法：`SquadsCap` 恒返 `SquadCap`(9)，**不信** `contract.squad.capacity`（字段已被污染）；`crew-model.CFG.SQUAD_CAP=9` 供 bridge 用。
2. **Gate.allowed 与 Decide 各写一份判据** ⇒ 有队员的队一在别镇、一驻地为空时：红条不出现（allowed=true），点下去 `wrong-settle`。修法：抽 `AllowedHere()` 两处共用；`Decide` 选队加「驻地为空且有队员」一档；有队员的队全在别镇时**不许**退到空队。
3. **前端用 `!here` 判可进** ⇒ 空队（可改绑）与驻地为空（可补绑）两类合法目标全置灰，只剩「新建小队」能走。修法：服务端下发每队 `canEnter`/`full` + 顶层 `squadCap`/`maxSquads`，前端只读不推。
4. **并发抢招同一 slot**（多标签/多账号，池子内容与账号无关）⇒ 同 id 弟子与装备各写 N 份。修法：`Mutate` 闭包里先查成员 id 已存在 ⇒ `dupHired`，退 50 点并按 `duplicated:true` 回。
5. **`MarkTaken` 不校验批次**：招人的几百毫秒里另一标签页点了刷新 ⇒ 标到新批次的同一 slot（白瞎一个候选）。修法：`MarkTaken(..., rollNo)`，批次不符不标。
6. **`SettleLocked` 首次建档在 nowTick<=0 时落库**（State 端点不要求世界存在）⇒ LastTick=0，世界起来后一次性补满 300。修法：`nowTick<=0` 只回临时行不建档。
7. **`EnsureLoaded` 先置 `_loaded` 后读库** ⇒ 一次锁表异常就把"已加载"钉死成空缓存，下一轮 Settle 当新档发 50 并覆盖真实余额。修法：读成功后再置位（异常向上冒 500 更安全）。

附带修：`SettleLocked` 夹断后回写 `_points` 缓存（原来每次重复夹断+写库）；`Resolve` 对空/坏 JSON 归 `bad-settle`（别冒 500）。

判据增补：`check_recruit_pool` 22 / `check_recruit_api` **57**（新增第 7 组：一队在 A + 一队驻地为空 ⇒ 别镇可招且补绑）/ `check_recruit_race` **9**（新，5 账号并发抢同一 slot）/ `check_recruit_e2e` 18+17 / `check_recruit_ui` **36**。

## 17:59 Tick「超预算/顺延」日志诊断（只分析，未改代码）

用户贴了 5 组 `[tick] tick=NNN 超预算 ~400ms > 300ms，剩余批顺延` + `顺延 1 个未执行 job`，问是不是卡住了。

结论：**没卡死**。实测 `/api/clock/stats`：tick 63303→63308 在两秒内推进，`incompleteTicks` 恒 5（与日志 5 条一一对应，之后再没增长），`pending` 恒 50，`tickMsP50=1ms / P95=4ms`。

机制（代码级）：
- `TickOptions.ConcurrentExecution` 默认 false ⇒ `TickPartitioner.Partition` 走单元素批 ⇒ **每个 job 单独一批**。
- `TickPump.RunOneTick` 的预算闸在**批执行之前**检查 `elapsedMs > TickBudgetMs` ⇒ 第一个 job 吃掉 300ms+ 后，同 tick 剩下的批一律 break ⇒ `DeferUnapplied` 按 `nowTick+1` 顺延。所以「超预算 + 顺延 1」= 本 tick 到期 2 个 job，第一个慢，第二个被推一天。`DtTicks` 只算 1 天，不丢演化。
- 批的顺序 = `(Layer, Resource= V8:0 < Cpu:1, EntityId)` ⇒ TownEvolve(V8) 永远先于 TradeEdge(Cpu)，被顺延的恒是 tradeEdge。

成本结构（真因候选，按可能性）：
1. `CityTickExecutor.Execute` **每一批**都调 `EnsureInitialized`：扫 49 区域格 × `citySettlementsJson` × 每格聚落的 `growTownFootprint`（当前 25 城）。名字叫「初始化」，实际是「每批全窗口校验」，job 越多重复越多。TradeEdge 25 个 job 各自一批 ⇒ 各跑一次全城 `SettleTrade`（cityPriceLayerJson + cityTradeEdgesJson）。
2. 单次 300~400ms 的离群更像外部阻塞：SQLite 写锁（`CityStateStore.Open()` 每次新连接、`busy_timeout=8000` 会静默等待），`db/zongmen.sqlite-wal` 正好 4.0MB 顶在 auto-checkpoint 阈值；或 core/city V8 门闩被人类请求占住。
3. 数据规模：25 城 × {townEvolve:90, tradeEdge:30} = 50 job；`dispatched/advanceCalls = 69736/62759 = 1.111`，与理论 25/90+25/30 完全吻合 ⇒ 每 tick 平均 1.1 个 job 到期。

顺带发现的静默病（未修）：
- **`TickPerf` 表 0 行**，跑了 6.2 万 tick 一行没落（`TickMetrics.EndTick` 里 `_store.Write` 抛了被 `catch {}` 空吞）⇒ 没有分段耗时历史可查。
- `/stats` 的 `tickMsP50/P95` 只是**最近 512 tick** 的环形缓冲，回看不到 tick 44269 那一刻。
- 扩容临界点：城数涨到 ~300 时每 tick 都有多个 TownEvolve 到期，单 job 300ms ⇒ 每 tick 只能跑 1 个 ⇒ 会真的积压。25 城时安全。

## 每 tick 事件耗时行（`Engine/TickTrace.cs` + `TickMetrics.LogTick`）
格式（用户指定「日期：事件：xxxx」）：
```
2026-11-26 21:24:19.094 info: tick[0] #75650: 3.0ms: citySettlementsJson 1.5ms: cityPriceLayerJson 0.4ms: cityEvolveJson 0.2ms: cityTradeEdgesJson 0.1ms: cityMetaJson 0.0ms: other 0.8ms
```
- **`TickTrace` 用 `AsyncLocal<Dictionary<string,long>?>` 而不是静态字段**：HTTP 请求（tile/chargen）与 tick 并行，静态桶会把请求耗时记到 tick 头上（账面 tick 变慢而实际没干活）。请求线程拿到 null ⇒ 直接不记。桶在 `BeginTick` 重建、`EndTick.Take()` 取走并置 null；异常路径遗留的桶会被下个 Begin 覆盖，不跨 tick 串账。
- `JsCallStats.Hit` 里 `TickTrace.Hit(fn, execUs)` + `Hit("wait", waitUs)`；事件名 = **JS 出口名**（与 `JsvmModule.Invoke` 的 case 同名，可直接 grep 代码）。
- **只在有 JS 调用的 tick 打**（空 tick 只有调度开销，1 tick/s 全打 = 3600 行/小时会把超预算那行淹掉）。
- `other` = 总耗时 − 已归因，即 **init 的 49 格 C# 循环 + PutRange + BumpBlockRev + 调度**。实测 0.3~0.9ms（总 3ms），账基本对上；真要细分就在那几处加 `TickTrace.Hit`。
- `TickMetrics` 构造改为 `(opt, store, ILogger)`；DI 用 `CreateLogger("tick")`（类别名短，每行前缀更省）。
- `appsettings.json` 的 `TimestampFormat` 改成 `yyyy-MM-dd HH:mm:ss.fff `（完整日期在最前）。
- ⚠ 日志量：约 1 行/秒（有 job 的 tick）。嫌吵时只改 `TickMetrics.EndTick` 里那一句 `if (ev is not null) LogTick(...)` 即可（加采样/阈值）。
- 实测新数据：`citySettlementsJson` **每 tick 都有 1.4~1.6ms**（就是那 49 格扫描，现在单独可见）；`cityPriceLayerJson` 0.3~0.8ms（贸易结算的价格层）。

### 格式改 NDJSON（用户要求「方便程序解析」）

- 解析：`const i=l.indexOf('{"ts"'); JSON.parse(l.slice(i))`。前缀（`info: tick[0]`）来自 ASP.NET SimpleConsoleFormatter，**无法配置去掉**（`SimpleConsoleFormatterOptions` 没有 IncludeCategory/IncludeEventId）。
- 字段：`ts`(ISO) / `tick` / `ms`(总) / `ev`(事件→ms) / `other`(未归因)。数值统一 ms、2 位小数、不带单位后缀。
- ⚠★ **实证抓到最初 398ms 超预算的真身**：冷启动首个 tick `#76351 = 510ms`，其中 JS 仅 71.4ms（`citySettlementsJson` 41.55 + `cityPriceLayerJson` 15.1 + `setExternalSettlements` 13.09），**`other` 438.55ms** ⇒ 就是 `JsVm` 构造里的 `new V8ScriptEngine()` + `Evaluate(bundle)` 重编译 + 首次 JIT（这两步在 `Call` 之外，故落在 other）。**与演化算法无关，也不丢天**（`DeferUnapplied` 下 tick 补跑）。
- 推论：日志里那种「成簇出现 5 次、之后 1.9 万 tick 一次没有」= VM 被 LRU 淘汰后重建的节奏，不是性能退化。要给 other 细分只需在 `JsVm` 构造函数加 `TickTrace.Hit("vmBuild", us)`（但构造在 BeginTick 之外时会 no-op，需按 tick 边界处理）。

### other 拆干净（vmBuild / init / put / dirty）
新增事件名（都在 `TickTrace`，与 JS 出口名同级）：
- `vmBuild` —— `JsVm` 构造里 `new V8ScriptEngine()` + `Evaluate(bundle)` 全量重编译。实测冷启 96~282ms（波动取决于 OS 文件缓存与 .NET JIT 是否预热）。

## 23:40 字符串压缩（6 张表 / 8 处编码）+ 清库

**结论：除 `Data.Key` 坐标键外，其余字符串 45.6KB → 8.0KB（省 82.5%）。全库 66.4KB 里 33% 是 JSON 键名、20% 是 `Data.Key` 里重复 690 次的同一个 seed 前缀。**

- `TickJob`：删 `Seed` 列（整库单世界，`World.Seed` 才是真源）+ `Kind` TEXT → `KindCode INTEGER`。主键 `(Round,EntityId,KindCode)`；`DeleteWorld(seed,round)` 改为 `DeleteRound(round)`。

⚠ **三个新踩的坑**：
1. **`KindCode` 必须显式固定编号**（`KindNames.All` 里写死 1..8），**绝不能用 `(int)enum`** —— 枚举插一个成员在前头，整表历史行静默错读成另一个 kind。`Code()` 返回 0 = 保留无效码，载入时跳过并计数。
