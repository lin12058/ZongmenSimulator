## 道路网拓扑重构 —— 邻域全对 + 跳板剪枝 + 笛卡尔 A*

需求演进（用户三次拍板）：① 城镇别只连最近 1/2 个 → 邻域全对尽量囊括；② 重复并行路太多 → 跳板剪枝
（顺路中间聚落替代直达，绕行 ≤30% 不建直达）；③ A\* 启发必须用**笛卡尔实际位置**的欧氏距离，不开浮点平方。

### 实现（全在 `mapgen.js` 道路段）
- **`roadsNear` 拓扑**：删 `want = sect?2:1` 上限；每个聚落 × 3x3 邻域格内全部聚落，按距离升序逐对跑 A\*，
  预算内可达即建路。创建顺序按 `hubBefore`（pop 降序 → 离原点平方欧氏距升序 → id）排序，大城先建。
- **跳板剪枝 `hopPrune`**：∃m 严格介于两点之间（到两端都严格更近）且 `10×(dam+dmb) ≤ 13×dab`（直线绕行
  ≤30%，整数比）⇒ 不建直达路。跳板**不限规模**——初版加过「m 须比 (a,b) 较小端点大」的资格门槛，用户截图
  实测漏掉「大城-小镇直达 + 小村跳板」三角捆绑，第二版删掉门槛（规模只用于排序）。
- **连通性双保证**（严格介于条件的推论）：最近邻对永不被剪；MST 边永不被剪（环性质：m 到两端都严格更近
  ⇒ (a,b) 是环 a-m-b 最重边）⇒ 每聚落 ≥1 路且不碎裂。实测孤点率 3.1%→3.2% 不变（全是地形隔离）。
- **`cartDist(q1,r1,q2,r2)`**（新导出）：两端点**实际笛卡尔世界坐标**的直线距离（以格间距 HEX_W 为单位取整）。
  恒等式 `dx²+dy² = HEX_W²·(dq²+dq·dr+dr²)`（代入 tileToWorld: x=HEX_W(q+r/2), y=1.5·HEX_R·r, HEX_W=√3·HEX_R
  精确展开）+ `isqrt` 纯整数牛顿 ⇒ 无浮点开方。2 万对随机数值验证：对 tileToWorld 勾股参照 0 例上取整、
  取整误差 <1、恒等式噪声 2.8e-14。**hexDist 从此只用于步数预算语义**（ROAD_STEPS_MAX 数的是格步数）。
- **A\* 启发** `h = minW × cartDist(当前格,目标格)`：平地上 hexDist 分层会让全部单调格同 f（整片同桶→路形锯齿），
  欧氏让直线走廊 f 最低先展开 ⇒ 等代价路径向直线收敛。floor ⇒ 仍可采纳；h 一致 ⇒ 桶序即标准 A\* 序。
- **跳板池 = 3x3(a格) ∪ 3x3(b格)** 并集（b 格坐标从 id 前缀反解）：从 a 侧与从 b 侧评估同一对池子相同
  ⇒ 剪枝与访问顺序无关（跨会话确定）。剪枝纯几何全整数、不读缓存、不记 roadFail、不耗预算。

## 追加：用户三次反馈的迭代 + 独立 Dijkstra 对拍抓出真 bug

1. **权重表改版（用户拍板）**：ROAD_W = [8,6,4,3,4,5,8,8]（深海8/浅海6/沙岸4/草3/林4/沙5/山8/雪8）；
   新增 ROAD_W_ROAD=2（已铺路格寻路代价）与 ROAD_REUSE_CORRIDOR=3（复用走廊宽度）。
2. **路复用（并线）**：bfsRoad 增可选参数 roadTiles（会话内已建路格索引 roadTileIdx，add-only）；
   走廊内已铺路格每格 2 ⇒ 新路并线旧路廊。**路复用使可行性路径依赖**（先建路的形状改变
   可骑路格集合 ⇒ 后建对可能失效），路数在配置间 ±2% 波动属预期，±20 统计可复现。
3. **路复用必须加「直线走廊」约束**：无约束时远处干道会把新路垂直拽离直线（用户截图 S 弯）。
   走廊判定 = 点到线段垂距 ≤3 格（胶囊体，垂足越出按端点距离），全整数公式
   4·Q(u)·Qv − B² ≤ 4·D²·Qv（Q=cartDist 二次型，B=2u·v=2udqvdq+udqvdr+udrvdq+2udrvdr）。
   ⚠ **B 公式初版漏了 2·u.dr·v.dr 交叉项**（首个算例 v.dr=0 测不出）——20 万点 vs 浮点世界坐标
   勾股对拍 0 不一致后才可信。
4. **真 bug：ROAD_STEPS_MAX=40 步数透镜误杀骑路长径**。40 是「每格最低 3 费」时代的隐含
   总长上限（40×3=120）；路格 2 费后骑路最多 120÷2=60 步，按 40 剪 ⇒ 假不可达 + 次优路径
   （独立朴素 Dijkstra 对拍 148 对抓到 4 例：3 假不可达 + 1 次优 120vs117）。
   修复：复用模式步数上限自动放宽 = COST_MAX÷ROAD_W_ROAD = 60（纯地形模式 40 不变），
   直线下界剪枝同步改用 hMin。修复后 296 对对拍 0 不一致。
5. **对拍方法论**（值得复用）：① 独立朴素 Dijkstra（不共享引擎代码）逐对比代价/可达性；
   ② 不变量断言「复用模式代价 ≤ 纯地形模式」（复用只是多给便宜选项）；
   ③ 整数几何公式必须与浮点世界坐标真值做 ≥10 万点对拍。注意判定条件别写反
   （首轮把「复用更便宜」标成违例）。
6. 数字：seed42 ±20 → 953 路/平均度 2.33/共享率 27.2%/孤点 33（+7 来自新权重表沙5/水6,8
   令跨沙水更贵；如需缓解提 ROAD_COST_MAX 至 ~150）；w3 12 项全过；最慢单 region 127.4ms
   （透镜 60 后搜索扩大，预算 250ms 内）。

## 追加 2：路网优先 (Network-First) 重构 P0 落地 —— 成对寻路框架退役

用户第四张截图（谷中双平行路）确认成对框架无解，按 docs/道路网络重构方案.md 实施 P0：

  MST ⊆ RNG 连通保证继承）。⚠ 池从 3x3 扩到 **5x5** 是孤点排查的关键修复：
  真最近邻可能落在隔 1 个区域格的位置（3x3 看不见）——石桥集(-287,-335) 案例实测。
- 建网规范序 = 端点 hub 等级降序 → 距离升序 → rkey（干线先行，与访问顺序无关）。
- **全局折扣**：已建路格 ROAD_W_ROAD=2 **不限走廊**（ROAD_REUSE_CORRIDOR 已删）——
  分叉聚落自动共享干道（用户蓝线形态）。
- **绕行闸**：DI = 步数/六边距 > ROAD_DI_MAX10/10 (=1.4, 林道规划标准) ⇒ 先试无折扣
  直连，仍超限则骨架边(Kruskal over RNG 边)强制建、非骨架放弃。
- **DI 重试队列**（会话级 FIFO，每次 roadsNear 限量消化 8 条）：DI 拒绝/复用 null 失败
  **不进 roadFail** —— 路复用是路径依赖的，建网早期超限/不可达可能只是路网还稀；
  记 roadFail 会永久毒化（石桥集实测）。3 次重试仍失败才转终身不可达。
  ⚠ 队列消化只在有预算的调用发生（maxNew=0 渲染调用跳过）。

**验证**
- 独立朴素 Dijkstra（全局折扣模型）6566 对：0 不一致（引擎=精确最优）；
- w3 12 项全过：建成路 598/615 = **建路率 97.2%**；最慢单 region 195.8ms（预算 250）；
- seed42 ±20 双遍：850 路/平均度 2.07/孤点 39→**27**（全部为地形超预算，无逻辑残留）；
- 可视化 _road_vis7.png：树状路网（干线+分支），零平行冗余（对照 _road_vis3/5）；
- 预览页已同步，泵送回归通过（单轮 max 118ms —— 泵送期瞬时值，可接受）。

**调参旋钮**：ROAD_DI_MAX10（14=1.4；调小更直）、ROAD_W_ROAD（2=并线力度）、
ROAD_COST_MAX（120；提到 150 可救沙/水隔断的 27 个孤点）。
**遗留 (P1/P2)**：RoadNet 共享表示 + 干线加宽渲染；line-of-sight 平滑；严格全局成网模式。

## 追加 4：RNG 支配补回 30% 绕行条件（修复近距村不连通）+ 两段式镜头修性能

用户截图: 紧邻两村不连。原因 = 重构把 v2 跳板剪枝的「绕行 ≤30%」条件丢了:
纯 RNG 支配 (m 到两端都更近即剪) 对紧邻对过度 agresive —— dab 小, 稍偏的第三点
即支配, 绕行比可达 1.65× (seed42 实测: 840 近距对 239 对被此类误剪)。

(154 顺路跳板合理剪 + 19 地形超预算), 1.47×/1.65× 案例全部恢复直达。

**性能回退与修复**: 补回条件后需求边增多, 最慢单 region 444.8ms (超 250 预算)。
根因 = 复用模式弱启发 (hMin=2) × 60 步大镜头的单次 A* ~50ms。
修复 = **两段式镜头**: 先 40 步紧凑镜头 (多数对命中, 搜索小), null 再 60 步重搜
(骑路长径兜底) → 最慔回落 232.6ms 过预算; ⚠ 有界次优: 第一段命中时 41-60 步
的更便宜骑路路径不返回 (DI 闸兜底质量, 已注释)。另有 demandCache (i,j →

## 道路生成「慢」根因剖析（注入式计数 + CPU 采样，未改任何源文件）

- 新增可复用基准：`verify/bench_road_drain.mjs`（seed / 区域格半径 两个参数）。
  手法 = 读 mapgen.js 源码 → 内存副本字符串注入计数器 → vm 跑 pumpRoads 同序泵送。
  ⚠ 两个坑：① 加载序必须 noise + mapgen-config + mapgen；② 计数器**必须整段替换插进分支内部**，
  用「签名后追加」会落到 if 块之外 → 带 continue/return 的分支被数成反面（本次连踩两次，账目差 752）。
- 实测量级（seed-check，±8 区域格 = 141 格队列）：
  冷建 321 条路 / 11.1s = **34.6ms 每条**；单次 A* 均 6.7ms、p90 13.9、max 84ms；每次 A* ≈ 1583 次 fields()。
  CPU 采样自耗时：**hexDist 46%** / cacheSet 15% / search 15% / fields 8.5%（hexDist 冷建期 1352 万次，
  cartDist+isqrt 487 万次 —— 每格邻居 2 次 hexDist + 1 次 isqrt 牛顿迭代是主要内层开销）。
- **真正的病灶（新发现，比 review.md 记的更重）**：
  drain 循环（DI 重试队列）冷建 986 次 A* → 只建成 5 条（0.5%），其中 **757 次（77%）是「绕行闸回队」**；
  热态（路已全建好、本该零成本）单次 roadsNear(9999) 仍烧 8 次 A*、**1126/1128 = 100% 全是绕行闸回队，产出 0**，单次 32ms。
  死循环机理：这些边 `bfsRoad` **总能找到路**（骑已建路 2 费），但 `步数/六边距 > 1.4` 永远超闸 →
  `{ diRetryQueue.push(dq); continue; }` 原样回队；而 `roadFailTrials` 只在 `!qp` 时累加 →
  **永不转终身 roadFail，永不排空**。review.md P0「DI 拒绝边无负缓存」应升级为「DI 拒绝边无终止条件（无限循环）」。
- 排序确实「由内向外」（两级）：预览页 buildRoadQueue 按区域格到视野/修路中心六边距升序；
  引擎 demandEdgesFor(i,j,cq,cr) 按端点到中心 cartDist 升序。但优先权被三件事架空：
  ① drain 在主循环**之前**吃预算（每次最多 8 条，全是死循环边）→ 等于每次调用先交过路费；
  ② 预览页预算只按 roadCache 增量（建成）返还，A*/失败/被闸拒都不算建成 → 一 tick 最多扫 40 格、
     最坏烧 40 次 A*（预览页 UI 自己写的「最坏一条 380ms」即此）；
  ③ `cq/cr` 只参与排序，不带来任何剪枝或预算约束 —— 「当前视野」没有变成工作量约束。
- 次要根因：需求池 5x5 区域格允许端点相距 ~70 格，而预算 COST_MAX=120 ÷ 最小权重 3 = 40 步（复用模式 60 步）
  → 大量边物理上不可能达标：主循环 538 次 A* 里 143 次寻路失败（27%）。
- 未改任何代码。修复方向（待用户拍板）见回复：给闸拒边退避/终身化 + drain 让位主循环 + 需求池半径与预算对齐。
