## 1. 现状：三条数据通路

```
① 世界元信息   HTTP  /api/map/meta        → 1017 B 常量 (geo / 色板 / 海平面)
② 单格详情     HTTP  /api/map/tile        → 点击某格时的信息面板
③ 单块流式     WS    TileRequest/TileResponse
                      ├ chunk   (441 格 + 0~420 精灵)  ← 渲染主路径, 体量最大
                      ├ region  (区域名 + 道路)
                      ├ settle  (建筑足迹)
                      ├ poi     (秘境)
                      └ comm    (群落 + 灵脉)
```

**引擎脚本下发**（`R11`，`MapMessages.cs:215` 帧类型 `Script=4`）：

```
C→S  ScriptRequest{name}          name 空 = 要整包, 否则白名单单文件
S→C  ScriptPack{name, source}     source = gzip(UTF-8 js 源码); 帧本身不压缩
```

`MapWsHandler.cs:181-223` 的三个关键设计（都不是巧合，说明当时就为"前端自算"留了口子）：

1. **白名单拼接**而不是新增静态挂载 ⇒ 浏览器永远拿服务端**当前**的 bundle，不会与前端副本漂移（单真源）；
2. `Name` **只做白名单匹配，绝不拼路径** ⇒ 杜绝目录穿越；
3. **`mapgen-server.js` 不下发** —— 注释原文：*「服务端适配层 (落库/JSON 出口), 浏览器侧不需要, 故不下发」*。

> ⚠ 注意第 3 条：前端拿到的 `mapgen.js` 是**原封不动**的生成逻辑，缺的只是一个 291 行的「打包成 JSON/字节」的搬运层。**生成能力是完整的。**

### 1.1 现状：谁在自算？（**大地图不是**）

| 视图 | 图层 | 数据来源 | 接线点 |
|---|---|---|---|
| **大地图**（主视图 / WebGL） | 地形 chunk | ❌ **服务端** | `main.js:321` ← `MC.block()` (WS) |
| | 区域名 + 道路 | ❌ 服务端 | `main.js:357 regionCells.set` |
| | 建筑足迹 / 秘境 / 群落灵脉 | ❌ 服务端 | `main.js:373 / 383 / 393` |
| **小地图**（独立 2D canvas） | L1 地形 | ✅ **前端自算** | `minimap-vein.js:373 engine.fields()` |
| | L2 世界（灵脉/聚落/道路/区域名/POI） | ❌ 服务端（WS 快照） | 同上，模块只读快照 |

**判定依据**：`web/js/` 全目录 grep `MapGen` ⇒ **只有 `minimap-vein.js` 命中**（`bldg_ink.js:1749` 仅是一条注释）； / `renderer.js` / `mapclient.js` / `textures.js` 对引擎**零引用**。5 个图层的 `.set()` 全部落在 `applyBlock`（`main.js:345-393`）内部，而 `applyBlock` 只被 `MC.block()` 的响应驱动。

**两者需求量级差得很远** —— 小地图只要 `biome/e` 两三个标量抽样成位图（`putImageData`，`minimap-vein.js:423-452`）；大地图要 `tiles/elev/hash/neigh` 满格数据 + 每格精灵坐标，还要 `renderer.uploadChunk` 上 GPU。**所以改造顺序天然从 P1（大地图 chunk）开始** —— 它收益最大，也是 hybrid 档的第一步。

## 2. 算法支持度：逐条判定

### 2.1 引擎是「确定性纯函数 + 内存缓存」

`mapgen.js` 的全部状态是 14 个 `Map`/`Set` 缓存，容量写死（`mapgen.js:193-206`：`ELEV_CAP=40000`、`FIELD_CAP=30000`、`ROAD_CAP=4096`、`SETTLE_CAP=1024`…），并且源码注释反复自陈同一句话：

> *「淘汰只影响命中率，**不改变确定性结果**」*（`mapgen.js:191-192`）
> *「B 版起**无建路顺序依赖**：……扫描顺序 / 缓存冷热 / reload 都不改路形」*（`mapgen.js:168-171`）

⇒ **它是一张 (seed, 坐标) → 结果的纯映射表，缓存只是加速器。** 这是前端自算可行的根本前提。

### 2.2 外部依赖只有两个全局量，且都在下发清单里

| 依赖 | 来源 | 是否已下发 |
|---|---|---|
| `global.NoiseLib` | `noise.js:118` | ✅ |
| `global.MapGenConfig` | `mapgen-config.js` | ✅ |
| `global.window` | 宿主注入（服务端 `JsEngineHost.cs:125` 拼 `var window = globalThis;`） | ✅ 浏览器天然有 |

`mapgen.js:54` 甚至做了兜底：`var CFG = global.MapGenConfig || {...}`（带一份内嵌默认值），`mapgen.js:76-79` 还会 `console.warn` 报告配置漂移 —— **连"参数漏加载"都有自检**。

### 2.3 唯一带"进程状态"的东西是道路 —— 而它也是确定的

`roadsNear(i, j, maxNew, cq, cr)`（`mapgen.js:1604`）签名里有两个"看起来有状态"的参数：预算 `maxNew` 与修路中心 `cq/cr`。源码注释直接堵死了误读：

> *「⚠ 中心点/预算只决定「这一刻先算哪些边」，**不决定「算出来什么样」**：收敛后（预算够走完一遍）路网与是否传 cq/cr **完全一致**」*（`mapgen.js:1601-1602`）

`roadFail` 也从"状态"降级成了"派生量"（`mapgen.js:180-185`）：

> *「B 版起这是**派生量而非状态**：……一条边要么建、要么终身不建，与建路进度/扫描顺序无关」*

⇒ **道路同样可以前端自算。** 而且 `maxNew`/`cq`/`cr` 这两个参数的存在，恰恰意味着前端可以做到**服务端做不到的事**：以玩家为中心、小预算、渐进铺路（见 §5.4）。

### 2.4 铁证：A/B 逐字节一致

新增复跑脚本 `verify/chunk_selfcalc_ab.mjs`（A = 本地自算 → 按线上布局切段；B = 真实 WS `mask=CHUNK` → `gzip` 解包 → protobuf 解码）：

```
seed = abcalc-selfcalc   base = http://127.0.0.1:8140
块坐标          前端自算(ms)   服务端帧(bytes)  地块段  精灵段
(  0,  0)      14.20   n=441 pn=154    ✓ 全段逐字节一致
(  1, -1)       7.38   n=441 pn= 86    ✓ 全段逐字节一致
( -2,  3)       6.68   n=441 pn=418    ✓ 全段逐字节一致
(  4,  5)       7.39   n=441 pn= 46    ✓ 全段逐字节一致
( -7, -4)       5.63   n=441 pn= 18    ✓ 全段逐字节一致
( 12, -9)       4.05   n=441 pn= 18    ✓ 全段逐字节一致
结论: ✓ A/B 逐字节一致 —— 前端自算与下发等价, 可安全替换
```

比对覆盖 `chunkJson`（`mapgen-server.js:40`）声明的**全部 11 个定宽段**：
`cq | cr | tiles | elev | hash | neigh | pdx | pdy | psp | ph | pe`，外加 `count` / `pn` 元字段。

> 为什么一定能一致：服务端 `JsEngineHost.cs:126` 与前端 `MapWsHandler.cs:26` 拼的是**同一批文件**；只要 seed 与块坐标相同，`buildChunk` 的输出就是同一串字节。**这不是"近似复刻"，是"等价替换"。**

### 2.5 成本实测（Node 22 / V8 单线程 · 与浏览器同引擎）

`verify/chunk_selfcalc_bench.mjs`：

| 项目 | 实测 | 说明 |
|---|---|---|
| bundle `eval` 4 文件 | **8.42 ms** | 前端首屏一次性固定成本（`mapgen.js` 1.94 ms 为最大项） |
| `MapGen.init(seed)` | **0.76 ms** | 换 seed（"重铸世界"）也是这个量级 |
| `fields()` 冷 / 热 | **5.31 µs/格** / 0.17 µs/格 | 小地图 L1 已在这条路上 |
| `buildChunk` 单块冷 / 热 | **2.46 ms** / 0.62 ms | 441 格 + 0~420 精灵 |
| 首屏 25 块（冷） | **61.4 ms** | 均 2.46 ms/块，中位 1.96，p90 5.10 |
| 服务端同 25 块 `chunkJson` | **69.2 ms** | 含打包 + JSON + base64（**不含** gzip/落库/网络） |
| 线上这批需传输 | **0.20 MB** | b64 JSON，gzip 前；单块约 9.5 KB |
| `regionJson` ×25（含全预算 A*） | **69.4 ms** | 均 2.78 ms/区域 —— 见 §4.4，这是服务端最大瓶颈 |
| `settleJson` ×25 | **10.9 ms** | `growTownFootprint` 全量 |
| `commJson` ×25 | **0.45 ms** | 群落 + 灵脉，几乎免费 |
| 世界规模 | **3249 块** | `SPIRIT_R_TILES=500` → 归零半径 ≈577 格 → 块半径 R=28 |
| 全图 3249 块全量自算 | **≈20 s** | 一次性外推（中位 6.09 ms/块）；可分帧/后台摊掉 |

**反直觉但关键的结论**：前端自算（61.4 ms）**比服务端算完再发（69.2 ms，且不含 gzip/落库/网络）更快**。因为省掉了整整一条「打包 → JSON → base64 → gzip → 传输 → 解压 → protobuf 解码 → u16 还原」的往返链。前端还能进一步直产 `Float32Array`，跳过 `pb.js:148 chunkToArrays` 的量化还原。

## 3. 服务端现在存的到底是什么？

把这层问清楚，"接口怎么改"才有答案。

| 存储键 | 内容 | 性质 | 前端自算后 |
|---|---|---|---|
| `w:{seedHash16}:chunk:{ca}:{cb}` | 打包后的块字节 | **纯算力缓存** | ❌ 可弃 |
| `w:...:region:{i}:{j}` | 区域名 + 道路折线 | **纯算力缓存** | ❌ 可弃 |
| `w:...:settle:{i}:{j}` | 建筑足迹 `{style, buildings, resources}` | **纯算力缓存**（注释称"后续会演化"，但 `growTownFootprint` 当前是纯函数 + 按 id 缓存） | ⚠ 见 §4.6 |
| `w:...:comm:{ci}:{cj}` | 群落 + 灵脉 | **纯算力缓存** | ❌ 可弃 |
| `Region` 内存 LRU 512 | 同上 | 缓存 | ❌ 可弃 |
| `BlockRevs` + `BumpBlockRev` | 图层 rev 计数器 | **缓存失效通知**（`MapWorldService.cs:429` 注释：*「未来建筑事件只需 BumpBlockRev 后让客户端重拉该块」*） | ⚠ 只对世界层还有意义 |
| `_seenSeedPrefixes` / `Seeds` | 活跃 seed 登记 | 缓存清理用 | ⚠ 随之退化 |

另外两处"预留给演化"的字段，目前恒为默认值：

- `mapgen-server.js:93` — `settlementJson` 输出 `state: st.state || 0, expireTs: st.expireTs || 0`（引擎侧恒 `0`）；
- `MapMessages.cs:82` — `Owner` 字段（引擎恒空串，见同目录 `渔村贴图重画与归属势力底图-规划.md` §B）。

> **判定：服务端存储层 100% 是"算力缓存"，没有一处是世界真值。** 删掉它不影响任何输出的正确性 —— 这既是"可以前端自算"的理由，也说明它现在的唯一价值是**跨会话/跨客户端省算力**与**未来演化的载体**。

## 4. 那为什么还没这么做？—— 前端自算的真实代价

### 4.1 主线程阻塞（最硬的障碍）

25 块 61 ms 在桌面浏览器无感，但：
- 低端机 / 移动端可能 ×5~10；
- 全图 3249 块 ≈20 s，**绝不可能同步跑**；
- 现有 WS 路径之所以"不卡"，是因为 `NET_CFG.concChunk=4` 把算力摊到服务端，前端只做解码。

⇒ **必须分帧**：仿照小地图的 `SAMPLE_BUDGET_MS`（`dt*0.35` clamp 10~110ms）或更保守的每帧 8 ms 预算 + `requestIdleCallback`；正解是 **Web Worker**（见 §5.6）。

### 4.2 `window.NoiseLib` 命名冲突 ⚠

| 文件 | 导出 | 用途 |
|---|---|---|
| `web/js/noiselib.js:95` | `global.NoiseLib` | **前端视觉噪声原语**（贴图/纸纹） |
| `Server/Zongmen/Engine/js/noise.js:118` | `global.NoiseLib` | **引擎世界噪声**（SimplexNoise/mulberry32/hashSeed） |

同名不同物。小地图现在靠「eval 前存下 `g.NoiseLib` → `finally` 还原」（`minimap-vein.js:166-172`）规避，并因为 `textures.js:15` 是模块顶层捕获 `var NL = global.NoiseLib` 才没炸。

**这是时序脆弱点**：一旦主渲染流程也要用 `MapGen`，就不能再靠"谁先谁后"维持。⇒ 自算改造**必须先**把引擎加载收敛到单一入口（§5.5）。

### 4.3 双实例 / 双 `init(seed)` 会让缓存互相冲掉

`MapGen.init()` 会 `clear()` 全部 14 张缓存（`mapgen.js:266-272`）。当前小地图在 `syncEngineSeed`（`minimap-vein.js:198-201`）里按 seed 变化调 `init`。

⇒ 如果主渲染另起一个实例，**内存翻倍**；如果共用实例但两个模块各自 `init`，**每次切 seed 等于把对方的缓存全清**，性能退化到冷算（2.46 ms/块 vs 0.62 ms/块，4 倍差）。

⇒ **必须单实例 + 单一 seed 同步点。** 这是改造中**最容易踩、也最隐蔽**的坑。

### 4.4 服务端其实正在为这条路"流血"

`mapgen-server.js:98-103` 自陈的 A5 问题（P1 未闭环）：

> *「该调用在 V8 门闩内同步跑完整区域 A\*，实测首请求 **~195.8 ms**，阻塞同 VM 的其它请求」*

这是 `REGION_ROAD_BUDGET=9999`（"一次算全"）的代价。而 `JsWorldVm.Call` 是 `SemaphoreSlim` 串行（`JsEngineHost.cs:70-97`）—— **一个慢请求会卡住同 seed 的所有请求**。

⇒ 把道路搬到前端，不仅省算力，还**直接消灭服务端的一个已知 P1 阻塞点**。这是支持改造的最强动机之一。

### 4.5 其他

- **每客户端重复算**：服务端算一次 N 个客户端共享；前端各算一遍（浪费，但 61 ms 无所谓）。
- **内存**：浏览器端缓存上限固定（`ELEV_CAP 40000` / `FIELD_CAP 30000` / `ROAD_CAP 4096` 含 pts/tiles），需实测常驻占用。
- **降级**：无 JS / eval 被 CSP 拦 / 内存不足 的客户端需要回落到服务端路径 —— 必须保留整条老链路。

### 4.6 ⚠ 长期架构分叉点：世界一旦可写，前端自算立即失效

现在世界**不可变**（纯函数），所以谁算都一样。但代码里已经埋好了"要变"的伏笔：`settlementJson` 的 `state`/`expireTs`、`MapMessages.Owner`、`BumpBlockRev` 的注释。

**一旦出现下列任一需求，前端自算就不再成立**（或必须退化为"只算静态地形"）：

- 玩家/宗门建造、建筑演化、聚落兴衰；
- 势力归属随事件变化（见渔村规划 §B）；
- 任何服务端权威的持久化世界变更。

⇒ **建议：把"地形/静态世界 = 可自算"与"动态状态 = 必须服务端"在协议上分层**（§5.1 的 hybrid 档天然就是这个形态）。

## 5. 接口怎么改

### 5.1 核心抽象：加一个「块供给器」，三档开关

现状只有一个入口（这点非常有利）：

```js
// main.js:317
function applyBlock(job, resp) { ... }   // resp 来自 MC.block() (WS)
```

`applyBlock` 是**唯一**的数据分发点，5 个图层全部在这里落到 `chunkData / regionCells / settleCells / poiCells / commCells`。
⇒ 只要让 `resp` 有第二个来源，改造面就被压到最小：

```
                     ┌── ServerSource : MC.block()      (现状, 保留为降级通道)
applyBlock(job,resp) ┤
                     └── LocalSource  : EngineLocal.block(ca,cb)   ← 新增
                                        └ 产出与 TileResponse 同形对象
```

三档开关（`?calc=server|hybrid|client`，默认 **`hybrid`** 分批推进）：

| 档 | chunk | region | settle/poi/comm | 收益 | 风险 |
|---|---|---|---|---|---|
| `server` | WS | WS | WS | 现状基线 / 降级通道 | — |
| `hybrid` | **本地** | WS | WS | 省 ~0.2 MB/25块传输 + 干掉服务端最大头的 `chunkJson`；改动最小（`mask` 去掉 `CHUNK` 位即可）**协议零改动** | 4.1/4.2/4.3 |
| `client` | **本地** | **本地** | **本地** | 干掉服务端 195.8 ms V8 门闩阻塞；道路可渐进铺路 | 4.6 定位必须写清 |

### 5.2 协议层：几乎不用改，但有两处必须补

**（a）`mask` 已支持按层请求 —— hybrid 档协议零改动** ✅

`pb.js:342` 的 `MASK = { CHUNK:1, REGION:2, SETTLE:4, POI:8, COMM:16, ALL:31 }`，服务端 `MapWorldService.cs:491` 有对应的 `needChunk = Need(0)` 分支。
⇒ 前端自算 chunk 后，只要把 `mapclient.js:324` 的 `mask: PB.MASK.ALL` 改成 `MASK.ALL & ~MASK.CHUNK = 30`，**服务端不需要任何改动**。

**（b）必须新增「引擎版本握手」** ⚠

否则服务端升级引擎后：老客户端用旧引擎算地形、用新服务端下发的 settle 放建筑 ⇒ **建筑落海**。这是最容易导致"诡异 bug"的一类漂移。

建议（二选一）：

```protobuf
// 方案 A: 扩 ScriptPack (protobuf 加字段 3, 老客户端自动跳过 = 兼容)
message ScriptPack {
  string Name   = 1;
  bytes  Source = 2;
  string Hash   = 3;   // 新增: 服务端对拼接后 bundle 做 SHA1/SHA256
}
```
```js
// 方案 B: 独立 HTTP 端点, 前端启动时比对, 不一致则强制回落 calc=server
GET /api/map/enginever → { "hash": "...", "files": [{"name":"mapgen.js","bytes":108894}, ...] }
```

> 同步改动：前端 `pb.js:395 decodeScriptPack` 需读新字段；`minimap-vein.js:165` 的 `requestScript()` 复用点不需改。

**（c）`rev` 机制只保留给世界层**

`BlockRevs` / `lastRevs`（`mapclient.js:320`）在 hybrid/client 档里对 chunk 层失去意义（本地算的，不存在"服务端按 rev 缺省"）。
⇒ `main.js:321-336` 那段"chunk 缺省但本地未持有 ⇒ 清 rev 重拉"的兜底逻辑，在 client 档要走另一种分支（本地算失败 ⇒ 退避重试本地）。**别把两套逻辑混在一起。**

### 5.4 道路的"中心 + 预算"：前端还能做得更好

服务端现在传 `REGION_ROAD_BUDGET = 9999`（无上限，一次算全）⇒ 路网"整片突然出现"+ 195.8 ms 阻塞。
前端自算可以传 `roadsNear(i, j, maxNew, cq, cr)` 的完整参数：

- `cq/cr` = 主相机中心格 ⇒ 路网**以玩家为中心向外生长**；
- `maxNew` = 小预算（如每帧 1~2 条）⇒ 视觉上是"路慢慢修过来"。

这是 `mapgen.js:1599-1602` 注释里明确支持、而服务端因"权威快照要求一次算全"而**主动放弃**的能力。**前端自算是把这条路解锁，不是模仿。**

### 5.6 降级链（必须有）

```
启动 → 取 meta → 取 ScriptPack → Hash 比对
   ├ 一致 + calc=client/hybrid → 本地引擎 init(seed) → 自算
   └ 不一致 / eval 失败 / CSP 拦 / 内存不足 / hash 缺失
                                → 强制回落 calc=server，全量走 WS（老链路一行不改）
```

老链路必须**完整保留**：它同时是无 JS 客户端、SSR、未来"服务端权威演化"三者的唯一退路。

### 5.7 Worker 化（可选，解决 §4.1）

正解：把 `EngineLocal` 放进 `Web Worker`
- Worker 内单独 `eval` 一次引擎脚本（脚本需在 Worker 里再取一份，或主线程转发文本）；
- 产出 `Float32Array` 用 `postMessage` + **transferable** 零拷贝传回；
- 主线程只做 `renderer.uploadChunk`。

代价：Worker 里没有 `window`，需 `self.window = self`（引擎 IIFE 参数是 `window`）；`MapGen` 的缓存改为 Worker 独占（**天然解决 §4.3 的双实例问题**）。
