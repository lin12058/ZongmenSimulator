## 一、需求收敛与关键澄清

### 1.1 「随便放」与「不能太接近」如何共存

这两条不矛盾，但要划清各自的边界：

```
玩家坐标准入  → 随便放（任意格，无候选、无择优、无"服务端钦定"）
空间关系准入  → 只受「聚落间距 / 领地」这一条几何规则约束
```

即：**除领地/间距这一条几何规则外，不做任何地形择优**。玩家想在山顶、海边、荒漠建宗门都行，只要不与既有聚落相犯。

这一点与 v1 的「候选位」根本不同 —— v1 实质上是把「选址打分」的权力从玩家手里收走了，v2 把它还给玩家。

**因此有一条要明确放弃**：不再要求「玩家宗门只能落在 `siteScore` 高的地方」。`siteScore` 仍用于**自动生成**（NPC 聚落选址），但**不用于玩家**。这是「随便放」的语义必然。

### 1.2 「8 格」的解读

你的原话是「如果玩家 8 格附近的有城市的中心就不允许建造」。两处需要澄清，我先按最合理的解读实施，并在 §六 列出待拍板项：

- **「8 格」= 到城市中心的 `hexDist` 阈值** ⇒ 用**六边距离（格子数）**，与引擎既有口径一致（全工程所有距离判据都用 `hexDist`）；
- **只对「城市」用 8 格，还是所有聚落共用一个阈值** ⇒ 你前半句已给了答案：「**根据城镇的规模来设置属于的领地**」⇒ 按规模分层。**city = 8 格**只是其中最大的一档。

## 二、放置规则设计（核心）

### 2.1 规模 → 领地半径（真源映射）

引擎里「规模」有两个字段可用（`mapgen.js:1189~1205` 已核实）：

| 字段 | 取值 | 说明 |
|------|------|------|
| `tier` | sect: 1~3 / **city: 恒 3** / town: 恒 2 / village·fishing: 恒 1 | 离散档位，**这就是「规模」** |
| `pop` | sect 2000~6000 / city 40000~70000 / town 4000~10000 / fishing 150~850 / village 200~1100 | 连续值，用于展示与收益，**不用于间距判定** |

**用 `tier` 做间距映射**（不用 pop —— pop 是连续量，规则不可预期，且 `inVeinDomain` 时 pop 还会 ×1.3；tier 是稳定的离散档）：

| 规模（type / tier） | 领地半径 `DOMAIN_R` | 与「8 格」的对应 |
|------------------|--------------------|--------------------|
| `city` / tier 3 | **8** | ✅ 你明确给的值 |
| `town` / tier 2 | 6 | 按比例内插 |
| `sect` / tier 3 | 8 | 与大城同级（大修士的道场理应更阔） |
| `sect` / tier 2 | 7 | |
| `sect` / tier 1 | 6 | 与镇同级 |
| `village` / `fishing` / tier 1 | 4 | 最小（足迹半径是 3，留 1 格缝隙） |
| `poi`（秘境） | **0（不设领地）** | 秘境是荒僻地标，不占领地，玩家可建在旁边 |

> **口径说明（重要）**：这里的 `DOMAIN_R` 是「**中心距**」阈值，不是「半径重叠」判据。
> 判定统一为一句：`hexDist(新落点, 既有聚落中心) ≥ 既有聚落的 DOMAIN_R` ⇒ 允许。
> **是拿新落点去量既有聚落的领地，不是量半径之和。**

**与既有的 `SETTLE_MIN_DIST=7` 是什么关系？**

`SETTLE_MIN_DIST = 7` 是**自动生成聚落之间**的抑制阈值（`mapgen.js:1244~1265` 的 `settlementsFor`），注释原文写明了推导：「足迹半径 `TOWN_R=3` ⇒ 中心距 < 7 时两镇地盘**必然重叠**；取 7 恰好不重叠但贴边」。**它是单一常量，不看规模。**

你的新需求实质是：**把这个单一常量升级为「按规模分档」的规则，并且让它也管玩家**。落地方式见 §2.4 —— 这是本方案要动引擎的地方，也是风险最大的一处。

### 2.2 领地半径 vs 足迹半径 —— 两者必须分清

| 概念 | 来源 | 值 | 用途 |
|------|------|-----|------|
| **足迹半径** `TOWN_R` | `mapgen-config.js:90`，实际成长由 `growTownFootprint` 决定 | 3（hexDist ≤ 3 的 37 格候选盘） | 「这座城镇的建筑铺到哪」 |
| **领地半径** `DOMAIN_R`（新增） | 本方案 §2.1 的规模映射 | 4 ~ 8 | 「这座城镇不许别人插足的势力范围」 |

两者关系：**领地必然 ≥ 足迹**（否则领地内已经有别人的建筑）。校验必须**两者都查**：

```
拒绝落点的条件（几何部分）:
  ∃ 既有聚落 P:
    (a) hexDist(落点, P中心) < DOMAIN_R(P)      // 侵入 P 的领地
 或 (b) 落点 ∈ P 的建筑足迹格集合               // 踩在别人的房子上（双保险）
```

> (a) 已蕴含 (b)（因为 `DOMAIN_R ≥ TOWN_R`），但 (b) 保留为**显式双检**：
> 足迹是「实际生成的建筑格」，领地是「规则上的势力范围」。万一 `growTownFootprint`
> 生出超出 `TOWN_R` 的地皮（它有三段式生长与 `spreadPick` 配额），(b) 能兜住。
> 这与既有 `check_no_build_on_vein.mjs` 的风格一致 —— 该脚本同时断言「判定层」与「足迹层」两层。

### 2.3 落点校验链（服务端唯一实现）

严格按「便宜 → 贵」排序，早退：

| # | 判据 | 真源 | 失败 err |
|---|------|------|---------|
| 1 | seed == 当前世 | `_ledger.Current()` | `world_stale` |
| 2 | 已登录 | `session.Authed` | `need_login` |
| 3 | 配额（该世玩家宗门数 < `PlayerSectMax`，建议 1） | `PlayerSect` count | `quota_exceeded` |
| 4 | 坐标在合法范围内（防越界整数） | 常量夹取 | `bad_coord` |
| 5 | 非深海 `f.biome !== BIOME.DEEP` | `MG.fields(q,r)` | `deep_water` |
| 6 | 非灵脉格 `!f.vein`，且距灵脉中心 ≥ `SETTLE_VEIN_FOOT_PAD`(=2) | `MG.fields` / `veinFootKeep` | `on_vein` |
| 7 | **领地/间距（§2.2 的 (a)+(b)）** | 邻域 2 环内的 `settlementsFor`（§2.7）+ `growTownFootprint` + `PlayerSect` | `too_close` |
| 8 | 灵气 `spiritAt(q,r) ≥ SEA_SETTLE_MIN_SPIRIT`(=0.20) | `MG.spiritAt` | `spirit_too_low` |
| 9 | 名字合法（1~12 字，去首尾空白，无控制字符/换行） | 服务端 | `bad_name` |

**⚠ 判据 7 的扫描范围有严格的数学要求 —— 见 §2.7，1 环不够，必须 2 环。**

其余两点：

```
· 用 settlementsFor 而非 rawSettlementsFor —— 一致对外口径。
  settlementsFor 是"抑制后"的结果，抑制只发生在「字典序更小的 1 环邻格」之间，
  且**不包含玩家实体**（§2.4）⇒ 玩家永远不会挤掉一个 NPC 聚落。
· 判据 7 附带的 too_close 响应必须给出「最近聚落 + 距离 + 它要求的半径」
  （PlaceCheckResponse 的 NearName/NearDist/NearDomainR），
  前端才能把「为什么不行」讲清楚 —— 这是「随便放」体验的关键（不能只弹一个红叉）。
```

### 2.4 引擎侧必须做的改动（本方案唯一动引擎的地方）

**问题**：`settlementsFor(i,j)` 是**纯函数 + 按区域格缓存**（`settleCache`），而玩家实体是**可变的**（会新增、会被拆）。若直接把 ext 塞进 `settlementsFor` 本体：

1. `settleCache` 里就**无法区分**「这条缓存含不含 ext」⇒ 缓存管理失控；
2. 但——**不把 ext 放进 `settlementsFor` 更糟**：需求边生成（`scanDemandEdges`）与骨架（`skeletonEdgesFor`）都只认 `settlementsFor`，看不见玩家 ⇒ **玩家接不上路、也挤不掉该挤的边**（§3.1 已用实测证明这些"挤掉"必须发生）。

⚠ v2 曾想用「双通道」（玩家边走独立通道、不进 `demandCache`）绕开问题 1，**但那样就绕掉了问题 2 的全部效果** ⇒ 双通道方案已废弃（§3.2）。

**决策：ext **必须**进 `settlementsFor`，但只在「缓存之外」叠加 —— 把"纯的部分"和"可变的部分"在缓存边界上切开。**

```js
/* 改动 1: 原函数改名, 由包装函数对外提供 (函数体与缓存逻辑原样搬入) */
function settlementsFor$base(i, j) { ... }

/* 改动 2: ext 叠加层 —— 这是「池是 5×5」的第二处依赖 (§2.7 的另一个 25) */
var extSettlements = [];               // 宿主注入的外部聚落 (玩家实体), 只读
function extIn(i, j) {                 // 按区域格取 ext —— 靠 id 的 "i_j_k" 前缀反解
  var out = [];
  for (var z = 0; z < extSettlements.length; z++) {
    var sp = extSettlements[z].id.split('_');
    if ((+sp[0]) === i && (+sp[1]) === j) out.push(extSettlements[z]);
  }
  return out;
}
function settlementsFor(i, j) {
  var ex = extIn(i, j);
  return ex.length ? settlementsFor$base(i, j).concat(ex) : settlementsFor$base(i, j);
}

/* 改动 3: 落库出口 —— 区域格由**引擎自己**算, 不接受 C# 传入 id (见 §九 风险 #6) */
function placeSettlement(q, r, opts) { ... }   // 返回 { id: i+'_'+j+'_p'+seq, type, q, r, ... }

/* 改动 4: 让 C# 能显式推进 roadVer (坑 C) */
function bumpRoadVer() { roadVer++; }

/* 改动 5: 让 C# 能按范围精确清 ext 侧派生缓存 (坑 A/B/E) */
function clearRoadSideFor(ci, cj, ring) { ... }

/* 改动 6: 注入入口 */
function setExternalSettlements(list) { extSettlements = Array.isArray(list) ? list.slice() : []; }
```

> ⚠ **`settleCache` / `townCache` / `siteScoreCache` 为什么可以不清？** 因为 `settlementsFor$base` 保持纯函数（ext 在缓存**之外**叠加）⇒ 这三个缓存里永远只存「与 ext 无关」的结果。**这是这套形状的唯一理由** —— 代价是必须显式管好 `demandCache`/`skeletonCache`/`roadCache`/`roadFail` 四个**含 ext 影响**的缓存（§3.2 坑 E 就是它们中最危险的一个）。
>
> ⚠ **玩家实体 id 必须伪装成 `"<区域格i>_<区域格j>_p<seq>"`**：`rngDominated`（`mapgen.js:1359~1360`）用 `id.split('_')` 反解两端区域格再去扫 5×5 池，`roadsNear`（`:1651`）也用它取「小 id 端所属格」。若 id 写成 UUID 或 `p_xxx`，`+ap[0]` = NaN ⇒ `settlementsFor(NaN, NaN)` ⇒ **静默扫出空池、漏判支配**（不崩，更危险）。后缀用 `p1/p2/...` 可确保不与自动聚落（`k ∈ {0,1}`）和 poi（`'p'`）冲突。

配套只需两个只读出口（不缓存、纯查询）：

```js
/* 供 C# 侧做落点校验: { ok, near:{id,name,q,r,dist,domainR}, err } */
function domainCheck(q, r, excludeId) { ... }

/* 某聚落（含玩家实体）的领地半径 —— 规模映射的唯一出口 */
function domainRadiusOf(settlement) { ... }
```

> **新增 JS 出口共 6 个**（`setExternalSettlements` / `placeSettlement` / `bumpRoadVer` / `clearRoadSideFor` / `domainCheck` / `domainRadiusOf`），
> 都必须在 `JsEngineHost.Call` 的 switch 白名单里加 case（`JsEngineHost.cs:78~91`）——
> 漏了就是 `InvalidOperationException: 未知 JS 函数`。
> 且都必须在 `mapgen-server.js` 的 `global.MapGenServer` 出口上挂透传。
>
> ⚠ `domainRadiusOf` 建议**同时**在 C# 侧保留一份镜像常量表（理由：C# 需要在不进 V8 门闩的
> 路径上算领地，例如快速拒绝明显非法的落点）。镜像一致性由判据脚本跨源逐值钉死 —— 这是
> `vein-skin.js` 的 `FOOT_MIRROR` 已用过的成熟做法（引擎就绪时问引擎，引擎缺席时用镜像兜底）。

### 2.5 `DOMAIN_R` 表放哪 —— 真源归属

**放 `mapgen-config.js`**（引擎真源），C# 侧镜像。理由：

- 工程纪律是「生成参数真源 `mapgen-config.js`」；
- `DOMAIN_R` 与 `SETTLE_MIN_DIST`、`TOWN_R` 是同一族的空间参数，放一起才好对账；
- 前端要画领地环（§四.4），走「引擎就绪时问引擎」的既有姿势（同 `vein-skin.js` 的地盘彩环）。

```js
/* mapgen-config.js 新增 */
DOMAIN_R: { city: 8, town: 6, sect3: 8, sect2: 7, sect1: 6, village: 4, fishing: 4, poi: 0 },
/* 说明: 「中心距」阈值（拿新落点去量既有聚落的领地），不是半径之和。
   city = 8 来自用户口径「8 格附近有城市中心就不允许建造」。
   poi 不设领地（秘境是荒僻地标）。*/
```

### 2.6 一个要写清楚的语义选择

「8 格附近有城市中心就不允许建造」有两种理解，结果差别很大：

| 解读 | 判定 | 后果 |
|------|------|------|
| **(甲)** `hexDist(落点, 城市中心) < 8` ⇒ 拒绝 | 「城市中心 8 格内是禁区」 | 城市周边 8 格半径（约 217 格）不能建。**采纳此解** |
| (乙) `hexDist(落点, 城市中心) < 8 + 玩家宗门领地半径` | 「两个领地不重叠」 | 禁区随玩家宗门规模变化 ⇒ 想建大点就得离城更远 |

(甲) 更简单、更可预期，且与你字面表述最贴。**采纳 (甲)**：判定只看**既有聚落**的 `DOMAIN_R`，与玩家自己的规模无关。

> 这引出一个不对称：玩家宗门自己的 `DOMAIN_R` **只对"之后要建的东西"生效**，对既有聚落不生效。
> 即 `DOMAIN_R` 是**单向**准入规则：「我不能侵入别人，但别人（自动生成的）已经在那儿了」。
> 这在自动生成的世界里是必然的 —— NPC 不会因为玩家来了就搬家。

### 2.7 ⚠ 关键结论：校验必须扫描 **2 环邻域（25 个区域格）**，1 环不够

这是本轮**通过计算发现的一个真问题**，不是保守取大值。推导如下（真源值已核实）：

| 参数 | 值 | 来源 |
|------|-----|------|
| 区域格间距 `REGION_M` | **18** | `mapgen.js:45` |
| 聚落锚点抖动半径 | `0.35 × 18 = 6.3` 格 | `mapgen.js:1166~1167`：`(hash01(...) - 0.5) * REGION_M * 0.7` |
| 锚点后再选址的半径 | `PROSPECT_R = 4` 格 | `mapgen-config.js:88`；`pickSettlementCenter(锚点)` 在锚点周围 4 格内重选 |
| **单侧最大偏移** | **6.3 + 4 = 10.3 格** | 二者串联 |

于是「第 n 环邻格里的聚落，最近可能距我多远」= `n × 18 − 10.3`：

| 环 | 该环聚落最近可能距离 | 能否覆盖 8 格禁区的校验 |
|----|-------------------|---------------------|
| **1 环** | `18 − 10.3 = **7.7 格**` | ❌ **不安全** —— 一个距我 7.7 格的聚落（在 8 格禁区内！）藏在 1 环里，若只扫 1 环就**查不到它** |
| 2 环 | `36 − 10.3 = 25.7 格` | ✅ 安全（> 8） |

**⇒ 所需环数 = `ceil((DOMAIN_R_MAX + 10.3) / 18) = ceil(1.017) = 2`，即 25 个区域格。**

**为什么这个坑很危险**：如果按直觉写成 1 环（9 格），实现不会报错、不会抛异常，只是**偶尔**允许玩家在两个城市之间建房 —— 而且只在「两格中心恰好错位到 7.7~8 格」时才发生（约 20/296 ≈ 7% 的邻近对落在这个带里，见下）。这种「偶发、无日志、部分场景才错」的 bug 极难定位。

**已把这条推导钉成判据**：`verify/check_place_neighborhood.mjs`（本轮新增，已跑通）：

```
== B/C. 邻域环数推导 ==
  区域格间距 REGION_M = 18
  单侧最大偏移 = 10.30 格
  第 1 环最近可能 = 7.7 格  => 不安全
  第 2 环最近可能 = 25.7 格 => 安全
  PASS 1 环不足以覆盖 DOMAIN_R_MAX=8 的校验 (即: 必须扫 >=2 环)
  PASS 所需环数 2 与公式 ceil((8+10.3)/18)=2 一致
  ⇒ 校验必须扫描 2 环邻域 (共 25 个区域格)

== D. 真实世界抽样 ==
  抽样聚落 296 个, 落在 8 格内的邻近对 20 对 (其中 20 对落在 [7, 8) 带内)
  PASS 样本非空真: 至少存在 1 对落在 8 格内的邻近聚落
  PASS 所有 8 格内的邻近聚落都落在 2 环邻域内
```

> ⚠ D 段的「样本非空真」断言是**刻意加的**：第一版脚本只在 `< 8` 格里找样本，
> 而 `SETTLE_MIN_DIST=7` 已把自动聚落推开，导致命中数恒为 0 ⇒ 断言**空真**、没有鉴别力。
> 改成探针半径 8（跨过抑制阈值那一带）后拿到 **20 对**真实样本，断言才有牙齿。
> 这条对应工程纪律「参照系不能自证 / 空真不可接受」（skill §32）。

**性能影响**：25 个区域格 × `settlementsFor`（有 `settleCache` 命中，便宜）× `growTownFootprint`（有 `townCache`）。这比 9 格多约 2.8 倍，但都是缓存命中路径。**注意**：`PlaceCheck` 是悬停高频调用 ⇒ §四.4 的节流更必须做。

## 三、道路重算（本次改动最难的一条）

### 3.1 现状：道路是「纯函数 + 顺序无关」，这是全链路确定性的地基

必须先理解既有道路设计，否则会做出一个把它推翻的改动。已核实的事实：

| 事实 | 位置 | 含义 |
|------|------|------|
| **生产路径恒不传 `roadTiles`**（纯地形 A*） | `mapgen.js:~1570` | 一条边的折线**只由「该边 + 静态地形」决定** ⇒ 与建路顺序、缓存冷热、页面 reload 全都无关 |
| **骑路折扣已删除** | `mapgen.js:165~172` 注释 | 历史上「已铺路格当 2 费高速路」是顺序依赖的根源，B 版起彻底移除 |
| `roadFail` 是**派生量而非状态** | `mapgen.js:176~183` 注释 | 「一条边要么建、要么终身不建」，与进度无关 |
| `roadVersion` 计数器 | `mapgen.js:1666` | 每新增一条路 `roadVer++`；宿主拿它做 tile 缓存新鲜度校验 |
| `resetRoads()` | `mapgen.js:1848` | 清 `roadCache` + `roadFail`，`roadVer = 0` |

**⚠⚠ 修正在此 —— v2 由此推出「旧边一条都不用重算」，该结论经实测**已被推翻**。**

原文的错误推理是：「新增聚落 P ⇒ 只有含 P 作为端点的边是新的，旧边只依赖两端聚落 + 地形 ⇒ 不变」。

错在**漏看了两步"三方"运算** —— `rngDominated` 会拿第三点来剪边，`skeletonEdgesFor` 用 Kruskal 重算骨架：

| 机制 | 位置 | 为什么新实体能改**旧边** |
|------|------|----------------------|
| `rngDominated(a,b,dab)` 三方支配 | `mapgen.js:1352~1381` | 池 = `5x5(a格) ∪ 5x5(b格)`。新聚落 P 若到 a、b 都严格更近且 `10*(d_am+d_mb) ≤ 13*d_ab`（绕行 ≤30%）⇒ **(a,b) 被判冗余、从需求图剔除** |
| `skeletonEdgesFor(i,j)` Kruskal | `mapgen.js:1386~1431` | 池同为 `i±2` 的 5×5。新 P 加入会**改变 MST 结构**：原骨架边 A—B 可能被 A—P、P—B 取代 ⇒ **骨架资格翻转** |

所以正确的说法是：**折线本身仍是纯函数（这部分没错），但"有哪些边"不是** —— 边集依赖 `settlementsFor` 的**全体成员**，多一个成员就变。

**实测（`verify/check_place_road_recompute.mjs`，seed=`seed-check`，±5 区域格内 56 个合法落点）**：

| 指标 | 实测结果 | 样本 |
|------|---------|------|
| 需求边被挤掉 | **23/24 个落点命中，累计消失 39 条**（另新增 81 条）| 取前 24 个落点 |
| 骨架集翻转 | **24/24 个落点命中，累计 281 个区域格**（均 11.7 格/落点）| 同上 |
| `roadFail` 集翻转 | **3/6 个落点命中，累计 7 条边** | 同上取前 6（A* 贵，限量）|

⇒ **你说的「这些城市对应的道路直接全部重新算」是必要且正确的**，不是保守取大 —— 旧边真的会消失。

### 3.2 ⚠ 五个必须一起处置的坑（本方案最容易反复踩的一区）

v2 的「双通道（玩家边走独立通道，不进 `demandCache`）」设计**必须放弃**。它的前提是「玩家实体不参与需求边生成」，但 §3.1 已证：**不参与就改不了支配与骨架 ⇒ 玩家既接不上干道、也挤不掉该挤的边**。

正确形状：**玩家实体必须进 `settlementsFor`，但只能「读时叠加」，不进纯函数缓存**（§2.4 的 `settlementsFor$base` + `extIn` 包装）。代价是必须显式管好下面五个坑 —— 它们全部**静默**，不崩溃、不报错。

| # | 坑 | 机制 | 症状 | 处置 |
|---|----|------|------|------|
| **A** | **旧边会被删除** | `rngDominated` 三方支配 + Kruskal 骨架翻转（§3.1）| 「只新增不修改」的实现会残留幽灵边：路画在已经不存在的边位上 | 受影响边的 `roadCache` 条目**必须删**，不能只增 |
| **B** | **`roadFail` 把「终身不建」锁死** | `roadFail` 注释自称「派生量」，其前提是「(该边, 静态地形) 的纯函数」——**骨架判定依赖 `settlementsFor`，注入 ext 后前提破裂** | 一条边原本「绕行超限 + 非骨架」进了 `roadFail`，P 加入后**变成骨架边（应建）**，但 `roadFail` 仍说终身不建 ⇒ **该建的路永远建不出来**（实测 7 条）| 受影响边的 `roadFail` 条目**必须删** |
| **C** | **`roadVer` 不前进 ⇒ tile 缓存不失效** | `roadVer++` 只在**新路落成**时发生（`mapgen.js:1666`）；而服务端 tile 判据是 `cached.RoadVer == known ⇒ return`（`MapWorldService.cs:694`）| 删边、或重算后条数不变 ⇒ roadVer 不变 ⇒ **旧路的 `onRoad` 永远画在 tile 上**（删边更是永远不可检测）| 放置流程**显式 `roadVer++`**。⚠ 只能 +1 增量，**绝不能归零**（服务端 `ObserveRoadVer` 单调取大，`:114~121`）|
| **D** | **一条边进两个区域包** | `demandEdgesFor(i,j)` 取「本格聚落 × 5×5 池」，**两端各自扫** ⇒ (a,b) 同时进 `demandCache[a格]` 与 `[b格]` ⇒ `regionJson(a格)`、`regionJson(b格)` **都含它** | 只 Bump「范围内 25 格」⇒ 远端 region 包不重拉、仍持有含同一条边的旧包 ⇒ **可能把新数据覆盖回去** | 脏块集合 = 范围内格 ∪ **跨界边另一端所在格**（实测 9 个）|
| **E** | **缓存不失效 ⇒ 注入静默无效** | `demandCache`/`skeletonCache` 的 key 是区域格、内容是"纯几何"（注释如此声明）—— ext 注入后几何**不再纯** | **实测 24/24 个落点**：不清这两个缓存就注入，得到与基线**完全相同**的几何 ⇒ 不崩溃、不报错、**无声无息地什么都不发生** | 注入前必须清 `demandCache` + `skeletonCache`（`settleCache`/`townCache`/`siteScoreCache` **不动**）|

> **坑 E 是本方案最危险的一条**：100% 命中且完全静默。任何「服务端说成功、客户端什么都没变」的现象，第一嫌疑就是它。
>
> **为什么 `settleCache` 可以不清？** 因为 §2.4 的包装让 `settlementsFor$base` 保持纯函数（ext 在缓存**之外**叠加）⇒ `settleCache` 里存的永远是 ext 无关的 base 结果。若图省事直接把 ext 塞进 `settlementsFor` 本体，`settleCache` 就会被污染，且**无法区分「缓存里的结果是否含 ext」** ⇒ 缓存管理失控（这正是 v2 想用双通道绕开的问题，绕不开，只能靠"缓存外叠加"）。

### 3.3 落定后的**同步**重算序列（你的口径：放下去 → 附近重算 → 直接发前端）

你的原话：「**放下去的时候附近的直接重修算然后直接发给前端，这些城市对应的道路直接全部重新算啊**」

三点解读，都照做：

| 你的要求 | 落地 |
|---------|------|
| 「放下去的时候」 | **同步** —— 在同一个 `PlaceCommit` 请求内跑完，**不分两拍**（§六 #5 就此定案）|
| 「附近的直接重算」 | 范围 = 落点 **±2 环（25 个区域格）**，与 §2.7 的校验范围同源 |
| 「这些城市对应的道路**直接全部**重新算」 | **不做「这条边会不会变」的预判**（预判不了 —— §3.1 的支配/骨架是三方运算，要问遍 5×5 池）。受影响边一律清掉重算 |

```
PlaceCommit 校验通过后，**在同一个请求内**依次做（全程持有 V8 门闩）：

【第 1 步·清 ext 侧派生状态】            ← 坑 A/B/E 的唯一解
  · 按「边」清: 任一端所在区域格 ∈ 落点 ±2 环 的 rkey
      → roadCache.delete(rkey) + roadFail.delete(rkey)
  · 按「格」清: 落点 ±2 环内 25 个区域格
      → demandCache.delete("i,j") + skeletonCache.delete("i,j")
  ⚠ 必须**按边/按格精确清**, 不能用 resetRoads() —— 后者清全表 (ROAD_CAP=4096),
     等于整张地图重算, 与"这些城市对应的"范围不符 (且实测全冷要 2.4 秒, §3.5)
  ⚠ settleCache / townCache / siteScoreCache **不动** (ext 在缓存之外叠加, §2.4)

【第 2 步·引擎侧·注入 + 重算】
  vm.Call("setExternalSettlements", playerEntitiesJson)     // 引擎持有, 只读
  对「落点 ±2 环内有聚落的格」+「跨界边另一端格」调 roadsNear(i, j, 9999)
  ⇒ 内部重扫 demandEdges / skeleton (已清缓存) ⇒ 重跑 A*
  ⇒ 新边落 roadCache; 被支配的边**不再出现** (= 旧边消失, 坑 A 的正确行为)

【第 3 步·引擎侧·显式推进 roadVer】       ← 坑 C 的一半
  bumpRoadVer()   (只 +1, 绝不复位)
  ⇒ 服务端 tile 缓存的 RoadVer 校验才会判陈旧

【第 4 步·C# 侧·清区域包缓存】
  · _regionPackCache / _regionHot / _rawCache : 删受影响的区域格
  · _settlePackCache : 删玩家实体所在区域格 (Settle 层多了玩家实体)
  · _tileCache       : **不必逐个清** —— 带 RoadVer 校验, 第 3 步推进后自动判陈旧
  · _blockLayersCache: 不需要 (块归属只依赖 region/comm 映射, 与道路无关)

【第 5 步·C# 侧·更新 roadVer 观测】       ← 坑 C 的另一半
  ObserveRoadVer(prefix, vm.RoadVersion())
  ⚠ 必须**主动取一次**, 不能等下次区域包生成时"顺带"观测 ——
     否则 _roadVerCache 停留旧值 ⇒ tile 命中路径拿旧 roadVer 判「新鲜」⇒ 路画不出来

【第 6 步·C# 侧·BumpBlockRev】           ← 坑 D
  BumpBlockRev(seed, i, j, TileMask.Region | TileMask.Settle)
  覆盖 = 落点 ±2 环 25 格 ∪ 跨界边另一端格 (实测 9 格) ∪ 路点包围盒覆盖到的块
  ⚠ 脏块集合由**引擎返回的路点包围盒 + 跨界边端点**推出, 不能由客户端猜

【第 7 步·直接回响应】                    ← 这就是"直接发给前端"
  PlaceCommitResponse 里带 DirtyBlocks[] ⇒ 前端按块 blockForget + 重拉 (§四.4)
  ⇒ 前端拿到的是**已经重算完**的路网, 不需要等第二拍
```

**与 v2 的三个差别**：① 同步，不分两拍（v2 建议「异步 + 二次 Bump」）；② 不做「新边 / 旧边」区分，受影响边一律重算；③ 显式 `bumpRoadVer`（v2 漏了 —— 坑 C）。

### 3.4 ⚠ 第 3 步的关键：`BlockRevs.Region` 不随 `roadVer` 前进

这是本方案里**最隐蔽的坑**，`mapgen-server.js:101` 的注释原文已经预警了：

> 「BlockRevs.Region 只在显式 BumpBlockRev 时变化, 不随 roadVer 前进, 客户端不会自动重拉。」

结合 `REGION_ROAD_BUDGET = 9999` 那段注释（A5 条目）：

> 「单纯调小本预算会让区域包永久少路 —— 因为 BlockRevs.Region 只在显式 BumpBlockRev 时变化,
> 不随 roadVer 前进, 客户端不会自动重拉。」

**所以第 3 步的「失效区域包」必须同时做三件事，缺一不可**：

1. `_regionPackCache` / `_regionHot` / `_rawCache` 里删掉受影响的区域格；
2. `BumpBlockRev(..., TileMask.Region)` 让客户端知道要重拉 region 层；
3. `ObserveRoadVer` 更新 service 层 roadVer 观测值（否则 tile 层的 `onRoad` 不会重算）。

> **教训（写进文档以防反复踩）**：本工程存在**两套独立的"新鲜度"系统** ——
> ① `rev` 系统（`BumpBlockRev` ⇒ 客户端缓存有效性）；
> ② `roadVer` 系统（⇒ tile 的 `onRoad` 是否正确）。
> **它们互不相通。** 任何「内容变了」的改动都必须**两套都通知**，否则症状是
> 「改了没反应」（无异常、无日志），这类 bug 极难定位。

### 3.5 实测代价（不是估算 —— `verify/check_place_road_recompute.mjs` 的输出）

决定性的一问：**同步重算要多久？会不会把 V8 门闩钉死？**

先纠正一个此前的误算：我曾按「25 格 × `regionJson` 首请求 195.8ms ≈ 5 秒」推断同步不可行。**这个推断是错的** —— 195.8ms 是**全冷**（`init` 后连地形缓存都空）。真实场景中玩家在看的区域地形缓存必然是热的。

实测（seed=`seed-check`，最坏落点 `(-4,5)`：范围内 16 格有聚落 + 跨界远端 9 格 = 25 格；交替 3 轮取中位）：

| 口径 | 基线 | 注入玩家实体后 | 说明 |
|------|------|--------------|------|
| **全冷**（`MG.init` 后，地形缓存也空）| 2241 ms | **2358 ms** | 最坏；3 轮 2391/2312/2358 |
| **仅清道路**（地形热，只重跑 A*）| 396 ms | **405 ms** | ✅ **真实场景**；3 轮 405/401/406 |

> 本表是**首次运行**。此后三次复跑同口径给 405 / 426 / 443 ms ⇒ 该口径的区间记作 **405 ~ 443 ms**（引擎无随机性，差异全在 JIT 与机器负载）。下文凡"405 ms"处均指此区间。

| 指标 | 值 |
|------|-----|
| **同步重算（真实口径）** | **405 ms** / 25 格 = 16.2 ms/格 |
| 同步重算（全冷，最坏） | 2358 ms |

**结论：你要的同步方案可行。** 405 ~ 443 ms 的 V8 门闩占用，用户感知是"点下去稍微一顿"，可接受。

⚠ **三条必须写进实现的红线**：

1. **地形缓存绝不能清**。清了就从 405 ms 变 2358 ms（**5.8 倍**）。第 1 步只清道路侧（`roadCache`/`roadFail`）+ `demandCache`/`skeletonCache`，**不碰** `elevCache`/`fieldCache`/`settleCache`/`townCache`。
2. **计时必须交替多轮取中位**。单次计时有 JIT 预热偏差，**实测后跑的一遍能快 ~17%** —— 本判据第一版就栽在这：A 段 1939ms、B 段 1598ms，看起来像"加了玩家实体反而更快"，纯属假象。
3. **脏块集合必须含跨界边另一端格**（坑 D）。只按落点算会漏。

### 3.6 ⚠「附近城市重算」与「附近道路重算」是**两笔账**（你 09-23 追问后补测）

你问「附近城市直接重新算太久了是吧？」—— 实测后我要先纠正这个提法本身：**贵的是道路，不是城市。**

同一脚本段 6 实测（seed=`seed-check`；25 区域格 / 28 座城镇村落；交替 3 轮取中位）：

| 项 | 实测 | 归因 |
|----|------|------|
| **道路重算**（热地形，只清 `roadCache`/`roadFail`/`demandCache`/`skeletonCache`）| **405 ~ 443 ms** | 每条边一次纯地形 A*（`ROAD_CAP=4096` 张表全要过）|
| **城市重算**（热地形，只清 `settleCache`/`settleRawCache`/`siteScoreCache`/`prospectCache`/`centerCache`/`townCache`/`tradeCache`）| **31 ms** | 扣掉 warm 未覆盖的 419 格地形 ⇒ **纯城市 ≈ 23 ms** |
| 城市重算（缓存全命中，下界对照）| 0.2 ms | — |
| 全冷（连地形也现建，上界）| 370 ms | 只有重启/换 seed 才会遇到 |

⇒ **道路 ≈ 纯城市的 19 倍。**

而且那 23 ms 是**白花的**：

- `growTownFootprint`（足迹/建筑/产出/风格）只读 `fields` / `landuseOf` / `veinNear`（`mapgen.js:950~975`），**完全不读道路** ⇒ 它与路网是两条独立链路；
- 按 §2.4 决策，玩家实体**不参与** `settlementsFor$base` 的抑制逻辑 ⇒ 既有聚落的中心、足迹、建筑**逐字节不变**；
- ⇒ **既有城市根本不需要重算**。所谓"附近城市对应的道路重算"，要重算的是**路**。

**为什么必须把这两笔账分开写**：记成一笔的后果是实现在落地时顺手 `resetRoads()` 或清整片城市缓存 —— 前者把 `roadVer` 归零（下面红线 4），后者白花 23 ms 并放大不必要的失效面。

#### 红线 4 —— ⚠ `roadVer` 只能 **+1 增量**，**绝不能归零**

这是最容易被漏、且症状表现为「用户觉得卡」而不是「报错」的一条。

`resetRoads()` 内部把 `roadVer = 0`（`mapgen.js:1851`），而服务端 `ObserveRoadVer` 是**单调取大**（`MapWorldService.cs:114~121`）。两者撞在一起会产生一个很坏的组合：

- **服务端视角**：归零后 `ObserveRoadVer(prefix, 0)` 取大保持旧值 N ⇒ 而 tile 缓存条目里的 `TileEntry.RoadVer` 也正是 N ⇒ 判据 `cached.RoadVer == known`（`:694`）**仍然成立** ⇒ 一路命中缓存、**返回含旧 `onRoad` 的 tile**。引擎侧路网已重建，却永远送不出去（"改了没反应"）；
- **客户端视角**：若将来改成"按值跳变重拉"，归零会让**全图 tile 一次失效**，前端重拉视野内所有 tile —— 这才是真正的"太久"，且与 405 ms 的引擎开销根本不是同一个量级。

⇒ 实现口径：**只按边清 `roadCache.delete(rkey)` / `roadFail.delete(rkey)`**，然后**显式 `roadVer++`**。**绝不调用 `resetRoads()`。**

**仍然需要的缓解措施**：

- 前端 `PlaceCheck`（悬停校验）≥150ms 节流 —— 它要扫 25 格（§2.7），悬停是高频调用，不节流会钉死门闩；
- `PlaceCommit` 加服务端令牌桶（⚠ `ApiRateLimitMiddleware` **对 WS 帧无效**，只拦 `/api/map/tile|fields`）；
- 在线判据盯 `PlaceCommit` P99 与 `roadVer` 是否确实前进。

## 五、城市迭代（P2）

### 5.1 推进模型：服务端 tick + 客户端拉取

**保持** `MapWsHandler`「服务器不主动推送」不变。演化在后台任务推进（与 `MaintenanceLoopAsync` 同款），客户端按需拉帧 7。

- **不选客户端驱动**：同一世界在不同玩家机器上进度会不同 ⇒ 世界不权威。
- **不做服务端推送**：要一整套订阅/背压/断线重放基建，收益为零。

### 5.2 演化规则

复用已预留的 `State` 四态（`0活跃 1被毁 2刷新中 3事件态`）：

```
每拍:
  资源产出: 建筑按 kindsOf → 累加 Resources
  人口:     Pop += floor(粮产出 × 系数), 受 Tier 上限约束
  升阶:     Pop 与资源同时达阈值 ⇒ Tier+1, 按 TOWN_BUILD_MAX[type] 上限追加建筑
            (sect=16 / city=25 / town=16 / village=8 — 复用引擎同口径, mapgen-config.js:97)
  ⚠ 升阶改变 DomainR ⇒ 必须重新校验「新领地内是否已有其他聚落/玩家实体」
     若冲突则本次升阶暂缓（否则会出现「两个聚落的领地重叠」的不变量破坏）
```

**建筑追加的确定性来源必须是 `(EntId, Tier)` 纯函数 hash**，不能用随机数 —— tick 可能因服务端重启重跑同一拍，随机数会让建筑「跳变」。
