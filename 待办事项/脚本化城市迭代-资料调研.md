## 〇、一页纸

你描述的形态，剥开有三件事：

1. **一个脚本**（JS，可在引擎里跑、可热改、可复现）；
2. **代替玩家做决策**（在哪里立宗、往哪拓土、什么时候升阶、遇到冲突怎么退让）；
3. **驱动世界逐轮推进**（V8 里迭代，产出可被服务端接受的世界变化）。

对照现状：**"能改世界"的入口已经存在**（`commitPlace`）；**"逐轮推进"的挂载点已存在**（`MaintenanceLoopAsync`）；**"城市内部演化"是零**（`growTownFootprint` 是纯函数，同一座城永远长同一个样）。所以这不是从零造，而是"给已有骨头接上关节"。

三句话结论，先说在前面（第 6 节展开）：

- 最值得照搬的是 **Screeps 的 runner/processor 分离 + CPU limit/bucket**：脚本**只产出意图，不直接改世界**。
- 最需要你拍板的是 **"迭代"到底指哪一层**：单座城内部进化（人口/建筑/升阶）还是聚落数量扩张（建新城）——两者的工程量差一个数量级。
- 最大的隐藏成本不是脚本，是 **`commitPlace` 单次同步重算道路 405~443ms**：脚本一轮想建 10 座城就是 4 秒级的门闩占用，这条决定了整个架构。

**三条必须写下来的硬结论：**

1. **"城市内部迭代"目前能力为零，且不是加个字段能解决的。** `growTownFootprint` 的签名里没有"时间"这个维度——它是 `(id, type, q, r)` 的纯函数。要让一座城"长大"，只有两条路：**(a) 把时间维度塞进纯函数**（`(id, type, q, r, tier)` → 结果随 tier 变化，天然确定性、天然可复现），或 **(b) 加一层"演化覆盖层"**（照抄 `ext` 层的零拷贝思路：引擎永远是"出生态"，演化结果叠在缓存之外）。这是整个方案的分水岭。

2. **`commitPlace` 的 405~443ms 是同步的、在门闩内的。** 现有实测（方案 §3.5/§3.6）：单个玩家放一座宗门 = 同步重算 25 个区域格的道路 = 405~443ms，期间同 VM 的其它请求**全部阻塞**。当前"一个玩家一世放一座宗门"这个量级完全可接受；但脚本一轮想建 3~10 座城，就会把门闩占满 1.2~4.4 秒。**这是方案的一号约束，任何路线都要正面回答它。**

3. **脚本重放必须幂等。** 已有两条红线：幂等键 `(Account, Round, Type, IdemKey)`；`roadVer` **只能 +1，绝不归零**（归零后 tile 判"新鲜"⇒ 路永远送不出去）。脚本一旦可以重跑（tick 重试、服务端重启、回放校验），重复的建城请求必须被幂等吸收，而不是建出第二座城。

## 二、参考资料 A：城市增长的经典模型（学界，可参数化）

### A-1 SLEUTH（Clarke 城市增长元胞自动机）—— 最成熟、最可参数化

- **输入 5~6 层**：Slope（坡度）、Land-use、**Exclusion（排除层：水体/保护区）**、Urban（城市化范围）、Transportation（道路）、Hillshade（仅背景）。模型名就是首字母缩写。
- **5 个系数**：Diffusion（扩散，总体分散性）、Breed（繁衍，新增长中心能否自己开始增长周期）、Spread（蔓延，自组织繁衍）、Slope Resistance（坡度阻力）、Road Gravity（道路引力）。
- **4 类增长规则**，每个增长周期依次跑一遍（一个周期 = 现实中 1 年）：
  1. **Spontaneous（自发）**：随机点落在已有城市格旁边 ⇒ 城市化；
  2. **New spreading center（新增长中心 / 扩散）**：足够平坦的格，即使不挨着城市也可以变成新中心；
  3. **Organic（边缘 / 有机）**：从城市边缘向外铺开 —— 最常见的"城市长大"；
  4. **Road influenced（道路影响）**：沿路网生长（SLEUTH 特有，把临时格沿路"搬到"最终位置）。
- **自修改规则**：模型能读取历史状态自我修正（这是它比普通 CA 强的地方）。
- **标定**：暴力枚举 0~100 的系数组合，每组跑多次 Monte-Carlo 迭代取平均，用 MRV（多分辨率验证）而非逐格比对评分。

**迁移到本项目**：
| SLEUTH | 本项目对应物 | 状态 |
|---|---|---|
| Slope | `elevAt` / biome 8 档（山地8/雪峰8 权重最高） | 已有 |
| Exclusion | 深海(DEEP)、雪峰、灵脉占地(d<=1)、`veinFootKeep` | 已有 |
| Transportation | `bfsRoad` 路网 + `roadCache` | 已有 |
| Urban extent | `settlementsFor` + `ext` 层 | 已有 |
| 5 系数 | **五个可调数字** ⇒ 这就是"脚本"最自然的参数面 | 待定 |
| 4 类增长规则 | 需要新写"聚落生成器"（当前聚落是一次性 Voronoi+抑制产生） | 缺口 |

**价值**：SLEUTH 给了一个"**用 5 个数字 + 4 条规则描述城市怎么长**"的现成骨架，且**天生确定性**（规则固定、随机只来自显式概率校验）。这正好是"脚本参数化"的天然接口。

### A-2 ABM / CA-MAS 耦合 —— 把"决策者"显式建模

- 常见的三类 agent：**政府/规划当局、开发商、居民**（北京案例）；**开发商、政府、居民**（德黑兰案例）；**区域当局、地产商、居民、环保主义者**（凤凰城案例，用 **BDI = Beliefs–Desires–Intentions** 结构建模）。
- 范式：**CA 负责"邻域效应"（地块怎么被带动），MAS 负责"人的决策"**，两者耦合（MAS 决策 → 改 CA 的转换概率 → CA 演化 → 反馈给 MAS）。
- 常配 Markov Chain（预测扩张**总量**）+ MCA（多准则分析给**倾向面**）+ 空间回归。

**迁移到本项目**：三类 agent 可直接对应 **宗门 / 附属城镇 / 散修（或凡人聚落）**。BDI 结构是脚本的自然骨架：**Beliefs**（脚本能读到的世界快照）→ **Desires**（目标：人口/灵机/声望）→ **Intentions**（这一轮要落子在哪）。这套结构能直接变成脚本里 `decide(state) → intent` 的函数签名。

### A-3 路网生长 —— 四条流派，对"新增道路"用处不同

| 流派 | 代表 | 机制 | 对本项目 |
|---|---|---|---|
| 自敏感 L-system | Parish & Müller 2001（**开山之作**，"街道网络是大地形的关键"） | 从一段路开始像树枝一样生长，遇到已有路段即停；目标函数=人口密度 + 道路模式（栅格/放射） | 我们是 A* + Kruskal 骨架，换 L-system 成本高，**不建议** |
| 模板法 | Sun et al. 2002 | 观察真实路网的高频模式，做成模板（Voronoi 人口中心 / 栅格 / 放射 / 混合） | 可作为"新区"的图案库，低优先 |
| **Agent 式** | Lechner et al. 2003/2006 | **extender**（找未连通区域）+ **connector**（去连接它）；扩展版还有"主干道 agent"和"小街 agent" | ⭐ 最契合：我们已有 `bfsRoad` + 骨架，**新增道路用两个 agent 增量补路**比全量重算便宜得多（正好绕开 405ms 约束） |
| 张量场 | Esch/Wonka/Müller/Zhang 2007 | 用张量场引导街图生成，支持交互编辑 | 过度工程，跳过 |

⚠ 需注意：Lechner 式的 agent 路网"结果可信但运行时间极长"（文献里提到 agent 方案生成小城市网络要 30 分钟；Galin 法 15 分钟）。**所以 agent 只能用于"增量补几条路"，不能用于"重建一张图"**。

### A-4 层次化细分 + 城市年轮

- **层次化**（Lyu 2015）：人口密度 → 定高速/主干道 → 围合地块分"区"→ 按 land use 分配 → 二级路网 → 街区 → 街巷 → 地块。可作为"城市升阶时解锁的细分层级"。
- **城市年轮（urban annual rings）**：以老城为中心一圈圈向外，配 **扩展强度 R = (Uj−Ui)/Ui × 1/T**。
- 这两条最适合直接映射到 **`tier` 升阶**：tier 1→2→3 就是"多长一圈 / 多一层细分"。

## 三、参考资料 B：游戏工业的可借鉴实现（工程，比学界更硬）

### B-1 Screeps —— ⭐ 与本项目形态最接近

Screeps 是"玩家写 JS 控制单位"的多人持久世界。其架构文档公开，几条可直接照搬：

- **tick 语义（关键）**：下一 tick 只有在**所有玩家的 main 模块全部执行完**之后才开始。tick 内分三段：**开始**（确立不可变局面）→ **中段**（执行脚本，脚本看到的永远是 tick 开始时的状态）→ **结束**（把脚本排的"意图"一次性、独立地应用）。**同一 tick 内先 move 后 attack，attack 仍用旧坐标**——因为属性下一 tick 才变。
- **intent / runner-processor 分离（最值得抄的一条）**：
  - `Runner Worker`：加载玩家代码 → 建沙箱 → 执行（带 CPU 限额与超时）→ **收集 intents**（合法意图，不改状态）；
  - `Processor Worker`：**校验 intents** → 应用游戏规则 → 更新世界 → 持久化。
  - 官方理由：安全、性能、并行。**玩家脚本永远不能直接写世界。**
- **CPU 限额 + Bucket 桶（可直接搬的"迭代预算"模型）**：
  - 每 tick 执行时长上限（默认 20ms，可解锁到 100+）；
  - 省下没用完的额度进 **bucket**（上限 10000），允许在后续 tick **透支**，单 tick 最多取 500；
  - `Game.cpu.tickLimit` = 本 tick 实际可用额度。
  - ⇒ 这就等价于"脚本平时省着用，攒够了就一次性做大动作（比如批量建城）"。
- **超时的代价**：`vm.runInContext` 带超时，但某些负载无法优雅中断 ⇒ **直接杀掉整个 fork**（该进程里所有玩家上下文一起消失、重建）。⇒ 教训：**限额要留余量，别指望能优雅杀脚本**。
- **上下文与缓存**：全局作用域**每 tick 清空**；但 context 与 `require` 缓存跨 tick 复用；编译产物有 code cache。

### B-2 确定性模拟（OpenRA / Klotho / TickForge）

- **OpenRA（RTS 帧同步）**：定点数（**模拟路径里零浮点**）+ **自研 seeded PRNG**（xorshift，明确"不用 `System.Random`/`Math.random()`"）+ 只传输入不传状态。理由："浮点在不同 CPU 上结果不同，HashMap 遍历顺序也会破坏确定性"。
- **Klotho（Godot .NET）**：32.32 定点 + seeded RNG（Xorshift128+）+ **snapshot/rollback ring buffer** + replay（LZ4）+ **frame-perfect 可复现**。
- **TickForge（Unity）**：**固定 tick 调度器 + 有序系统执行** + seeded RNG + **deterministic serialization & replay hashing**；验收方式叫 **replay parity**——同一 seed 在两个 build 上必须逐 tick 产出相同日志。
- **一个纯函数式引擎的极简做法**（值得抄的洁癖）：`applyAction(state, action) → newState`，纯函数、不改输入；**所有随机来自 state 里的 seed（mulberry32，32 位状态）**；于是"整局游戏 = seed + 动作列表"，replay 免费、多人几乎免费。
  - 文中唯一踩的坑值得记：**动作规范化（canonicalisation）必须与引擎一致**——客户端省略可选字段时若服务端 default 解析不一致，合法动作会被判非法。

**对本项目的直接映射**：引擎已用 `hash01(i,j,salt)` 这类**纯函数哈希**做全部随机（聚落 pop/tier、建筑、名称）——**已经满足确定性要求**。要做的是：新增的迭代代码**不得引入 `Math.random()` / `Date.now()`**（方案 §5.2 已明确"建筑追加的确定性来源必须是 `(EntId,Tier)` 纯函数 hash"）。

### B-3 离线推进（idle game）—— "没人在线时世界要不要长"

这是本项目会立刻撞上的问题（服务端权威 + 客户端拉取，玩家不在线时 tick 还跑不跑）。

两种工业实现：

| 方案 | 机制 | 适合 |
|---|---|---|
| **闭式公式** | `gained = floor((now − lastSaved) / tickMs) × rate`，不动模拟，直接结算 | 产出是线性的、无分支的 |
| **分批补跑** | 把离线时段塞进 N 个虚拟 tick 逐个跑（Antimatter Dimensions：N 可调 1000 ~ 100 万；50ms 为最小 tick 粒度；有"加速"按钮改成 1000 tick 快速结算） | 有状态机/自动化（autobuyer）必须"发生很多次"的情形 |

⚠ Antimatter Dimensions 的实测教训：**补跑 tick 数 = 精度 vs 加载时间的旋钮**；且**"离线时 tick 被拉长"会让依赖"每 tick 触发一次"的系统失真**（autobuyer 从每秒 20 次变成每 3.6 秒 1 次）。⇒ 若我们的城市迭代里有"每 tick 检查一次阈值"的逻辑，离线补跑会改变结果。

**另一条**：离线推进的天然漏洞是**设备时钟作弊**。本项目**已经是服务端权威**（进度、时间戳都在服务端），所以这一条对我们不成立——但反过来，**"服务端时间"必须成为脚本唯一的时间源**（不能用 `Date.now()` 在脚本里算）。

## 四、参考资料 C：迭代质量的判定指标（给"判据"用，不是给"评分"用）

城市形态学里有一组成熟的定量指标，直接可用作**"脚本是不是真在生长"的客观断言**：

| 指标 | 公式 | 语义 | 取值范围 |
|---|---|---|---|
| 扩展强度 | `R = (Uj − Ui) / Ui × 1/T` | 单位时间用地面积变化幅度 | — |
| 紧凑度 | `C = 2√(πA) / P`（或 `√(πA)/P`） | 边界紧凑程度，圆=1 | 0~1 |
| 分形维数 | `D = 2·ln(P/4) / ln(A)` | 边界曲折度；D<1.5 趋简单，=1.5 类布朗随机，>1.5 越复杂 | 1~2 |
| 形状指数 | `LS = 0.25P / √A` | 与同面积圆的偏离度（斑块破碎度） | — |
| 土地利用多样化 | 辛普森：`GM = 1 − Σfi²/(Σfi)²` | 功能单一性（蔓延的特征是功能单一） | 0~1 |
| 地均产出 | 产值 / 建成区面积 | 效率维 | — |

⚠ **按本项目既有的判据纪律使用**（见 MEMORY「判据三防」）：这类指标**不能当绝对值阈值**（"紧凑度必须 > 0.6"必然假红），正确用法是做 **A/B 归因**与**跨轮趋势断言**：

- 「脚本跑 100 轮后，聚落总足迹面积**单调不减**」；
- 「同一 seed 下，脚本 A 与脚本 B 的最终分形维数**有显著差异**」⇒ 证明参数真的起作用了；
- 「紧凑度**不出现剧烈跳变**」⇒ 证明生长是渐进的而不是一次性爆开。

## 五、参考资料 D：修仙宗门经营类作品的迭代机制（可玩性参考）

《了不起的修仙模拟器》（Amazing Cultivation Simulator）的机制里，有三条**能直接对应到我们的数据结构**：

| 该作的机制 | 机制细节 | 本项目对应物 |
|---|---|---|
| **声望阈值 → 扩规模** | 门派声望达 **500 / 2000** 时"扩大门派规模"：**新增建筑种类 + 提高弟子上限** | ⭐ 就是 `tier` 升阶 + `TOWN_BUILD_MAX[type]` 分档（village 8 / town 16 / city 25）。阈值驱动、离散跃迁，天然确定性 |
| **品质达标 → 晋"洞天"** | 高品质建筑数量达标 ⇒ 门派晋升"洞天"，获得显著修炼加成 | 可作 tier 3（city）的达成条件：不是"人口到了就行"，而是"建筑种类/品质达标" |
| **建筑被毁留"废墟"** | 建筑摧毁后**不完全消失，留下废墟可直接重建** | ⭐ 与已有的 `state = 1（被毁）` 字段严丝合缝：被毁 ⇒ 留废墟 ⇒ 可原地重建（`excludeId` 豁免已支持"原地重建"） |
| 风水 / 五行 | 建筑材料的五行属性影响建成品属性与风水；风水影响修炼效率 | 本项目有五行（`ELEMENTS`/`ELEMENT_RGB`）+ 灵脉域，是现成的"加成来源" |
| 分工（外门劳作 / 内门修炼） | 弟子分内门外门，职能不同 | 可作"建筑种类配额"的叙事包装 |

其他同类（《鬼谷八荒》《觅长生》）：偏个人修行 + 势力关系，城市/门派建设的**迭代粒度没有该作细**，参考价值次之；但其"势力范围随境界扩张"可作为扩张档的叙事参考。

## 六、三条候选路线（供讨论，含我的倾向）

三条路线的分歧点只有两个：**脚本改不改世界**、**迭代发生在哪一层**。

### 路线 A：意图—执行分离（Screeps 式）

- 脚本每轮只读世界快照 → 产出 **intent 列表**（`{action:'found_sect'|'expand', q, r, type}`）→ 服务端**校验并执行**（复用 `placeCheckJson` + `commitPlace`）→ 结果写入台账。
- 脚本**没有任何写权限**。世界永远只被 `commitPlace` 这一条链改。
- **优点**：确定性天然（意图 = 输入，世界 = 纯函数产物）；可回放（seed + 意图列表）；沙箱边界干净；**与现有代码接缝最少**（`commitPlace` 一行不改）。
- **缺点**：表达力受限——脚本想让"城市内部长大"就得新增对应的 intent 类型（即仍需实现 P2 演化规则）。
- **迭代预算**：可直接照搬 limit + bucket；单轮超标即拒（拒绝也要确定性，不能"跑到一半杀掉"）。

### 路线 B：演化规则内联（CA 式）

- 把规则本身写成 JS（SLEUTH 式的 5 系数 + 4 规则），脚本**直接参与计算**聚落/建筑/道路的下一步状态，只在最后一步把结果交给服务端落库。
- **优点**：表达力最强，能实现 SLEUTH/ABM 那套完整玩法；参数即脚本，调参就是热改脚本，适合"当玩法实验台"。
- **缺点**：**必须严格确定性**——引擎里已有的 `hash01` 纯函数哈希纪律要被脚本继承，一旦脚本里混入 `Math.random()`/`Date.now()`，整个世界的可复现性就废了；且**缓存污染风险高**（`settleCache`/`townCache`/`siteScoreCache` 逐字节不变的约束会被脚本绕过）。
- 与既有红线冲突最大：MEMORY 里"ext 只在缓存外叠加（零拷贝）"的纪律，在路线 B 下要重讲一遍。

### 路线 C：混合分层（我的倾向）

三层职责分明：

| 层 | 负责 | 谁实现 | 确定性来源 |
|---|---|---|---|
| **决策层** | 判断"该做什么"（立宗/拓土/升阶/放弃） | **JS 脚本**（玩家可写、可热改） | 脚本 + 世界快照（脚本内禁 `Math.random`/`Date.now`） |
| **校验层** | 判断"能不能做" | 引擎（`placeCheckJson` / `domainCheck` / `expandCheck`） | 已有，纯函数 |
| **执行层** | "改了之后重算/落库/通知" | C# + `commitPlace` 七步 | 已有，幂等键 + 单调 `roadVer` |

理由三条：

1. **它把"最有价值但最没把握"的部分（玩法决策）隔离在脚本里**，改玩法不用碰引擎；而"最容易出事"的部分（改世界）留在已经过验证的链路上。
2. **它正面回答一号约束**：执行层天然是**异步/分批**的——脚本一轮产出 N 个 intent，执行层按预算逐个落（每落一个 405ms 就在 `MaintenanceLoopAsync` 里让出一次），门闩不会长时间独占。
3. **它兼容"先做小的"**：可以先只支持 `found_sect`/`expand` 两种 intent（P2-α 已具备），跑通"脚本自动拓土"；城市内部演化（P2）作为第二批 intent 类型（`upgrade`/`build`）再接进来。

### 三条路线对比表

| 维度 | A 意图-执行分离 | B 演化规则内联 | C 混合分层 |
|---|---|---|---|
| 脚本能改世界吗 | 不能，只能提意图 | 能（计算结果） | 不能，只能提意图 |
| 表达力 | 中（受 intent 类型限制） | 强 | 中→强（随 intent 类型扩容） |
| 确定性风险 | 低 | **高** | 低 |
| 与现有代码接缝 | 最小 | 最大（缓存纪律要重讲） | 小 |
| 能否复用 `commitPlace` | 全部复用 | 部分/绕过 | 全部复用 |
| 一号约束（405ms/次） | 天然分批 | 需自己设计 | 天然分批 |
| 拉出"城市内部演化" | 需扩 intent | 天然支持 | 需扩 intent |
| 适合阶段 | 先跑通 | 玩法实验台 | 先跑通 → 再扩 |

## 七、必须由你拍板的问题

| # | 问题 | 我的建议（仅建议） |
|---|---|---|
| 1 | **脚本扮演谁？** (a) 单个玩家的客户端脚本（"帮你自动玩"）(b) 服务端"世界 AI"（"没人在线世界也活"）(c) 两者都要（同一份脚本两个宿主） | (b) 先做。它不依赖前端改动，可纯离线验证 |
| 2 | **"城市迭代"指哪一层？** (a) 单座城内部演变（人口/资源/建筑/升阶）(b) 聚落数量扩张（建附属城镇）(c) 两层都要 | (b) 先做——基础设施（`commitPlace`/`expandCheck`）**已经就位**，见效能最快；(a) 是真正的缺口，工程量最大 |
| 3 | **推进模型**：tick 驱动 / 事件驱动 / 离线补齐？tick 多长（现实秒 or 服务器时间）？ | tick 驱动 + **只在服务端在线时推进**（先不做离线补齐，避开 §B-3 的精度陷阱） |

| 5 | **迭代预算模型**：照搬 Screeps 的 limit + bucket（省下的攒、可透支），还是简单的"每轮最多 N 次提交"？ | 先用"每轮最多 N 次 + 全局冷却"（简单、可断言），bucket 留作 P3 |
| 6 | **是否要求严格可复现**（同 seed + 同脚本 ⇒ 逐 tick 状态哈希一致，即 replay parity）？ | **要求**。它是回归判据的唯一抓手（否则只能靠人眼看图） |
