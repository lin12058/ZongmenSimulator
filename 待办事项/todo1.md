## 1. 热跑回退 +23%

### 1.1 旧归因（错，已证伪）

原记录：「需求池 5×5 允许端点相距约 **70 格**，远超复用模式可达上限 60 步 ⇒ 冷建 617 次主循环 A* 里
226 次(37%)注定失败」→ 建议「需求边按 hexDist 预筛」。

**实测反证**（seed-check，±8 区域格 = 141 格冷扫，统计每条失败主循环 A* 的端点 hexDist）：

- 226 条失败边 hexDist **min 16 / p50 36 / p90 47 / max 55**，**>60 的 0 条**；
- 按 60 步预筛只减少 **4 次** A*（617→613，-0.7%）。

⇒ 失败**不是距离超预算**，而是**地形/代价不可达**（跨沙/水/山）。且**失败的那批 A* 恰好是最贵的一批**
（单次 p50 28ms / p90 130~166ms / max 347~675ms）—— 热跑贵的根源在此，不在次数。

### 1.2 已落地（`Server/Zongmen/Engine/js/mapgen.js`，输出不变）

1. `roadFailVer: Map<rkey, roadVer>` 负缓存 + `failMark()`（容量 ROADFAIL_CAP，淘汰只丢命中率）；
2. 主循环 / 延迟重试轮 / drain 三处失败统一记戳；
3. 需求边按复用模式步数上限 `COST_MAX ÷ min(ROAD_W_ROAD, 最低地形权重)`(=60) 预筛
   （与 `bfsRoad` 的 `d0 > cap → null` 硬早退**等价**，纯几何、与 cq/cr 无关 ⇒ 缓存安全）；
4. `starved` 标记：主循环因预算耗尽中断时，drain 让位（② 的引擎侧一半）；
5. init / configure 同步清 `roadFailVer`。

### 1.3 待拍板：强策略（失败边不再由「扫描」重算）

现落在工作区的是**强策略**：`if (roadFailVer.has(rkey)) continue;` —— 失败边只在 drain
（按 roadVer 增量节流）里重试。效果与代价（paired 同进程 A/B，PRE = git HEAD）：

| 指标 | PRE | 强策略 |
|---|---|---|
| 热重扫耗时 | 38.1 s（单跑 28~38 s） | **3 ms** |
| 热重扫 A* | 223 | 0 |
| 热重扫新建 | +6 条 | 0 条 |
| 冷扫建成 | 323 | ~303~316（**-2%~-6%**） |

**代价来源**：同一条需求边会被**两个端点所在的格各扫一次**，强策略下只剩一次机会
（第二个格不再补救）。⇒ 这是覆盖率 vs 热跑成本的取舍，需拍板。

**⚠ 上表「303~316」区间混入了并发会话的 A2/A4 改动（见下），必须在干净树上重测。**

**顺带修掉一个隐性不确定性**：旧行为下「同一格扫几遍」会改变路网（323→**329**，热扫 +6 条），
即输出依赖缓存冷热；强策略下路网只由「扫了哪些格」决定，对外可复现。

**回退方式**：把 `if (roadFailVer.has(rkey)) continue;` 换回
`if (roadFailVer.get(rkey) === roadVer) continue;`（中间档：同版本跳过，热跑只省 ~30% A*）。
