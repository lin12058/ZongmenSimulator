## 〇. 一页纸

### 0.1 用户口径（本轮已拍板，不可再改）

| 项 | 结论 |
|---|---|
| 「城市迭代」指哪一层 | **第一层 = 单座城内部演化**；**第二层 = 城市之间的资源互换 + 人口变化** |
| 变化粒度 | 单个城市的变化 |
| 可复现性 | **不需要可复现**（determinism NOT required） |
| 运行位置 | **服务端运算** |
| 总目标 | **尽量模拟真实世界的城市推演：资源交换与内部迭代同时进行** |
| 交付形态 | **只出方案，不写代码** |

### 0.2 三句话结论

1. **第一层（城内演化）= 全新能力，必须新增。** 现状 `growTownFootprint(id, type, cq, cr)`（`mapgen.js:936`）签名里**没有任何时间维度**，且按 `id` 缓存（`townCache`，`TOWN_CAP=4096`）⇒ **同一座城永远长同一个样**。要让它随时间变，只有两条路：**(a) 给纯函数加时间维度**，或 **(b) 加演化覆盖层 `$base + evoIn`**（照抄已有 ext 层的零拷贝范式）。**本方案选 (b)。**

2. **第二层（资源互换）= 已有现成纯函数，直接复用，不重造。** `tradeEdgesFor(i,j)`（`mapgen.js:1102-1149`）+ `townNet(st)`（`mapgen.js:1090-1100`）已经完成「产出聚合 → 供需缺口 → 配对成边」的完整计算，`TRADE_REACH=40`、扫 ±2 环、按 `RES_ORDER` 八资源取缺口最大者。**缺的只是「让它动起来」**：现在它是 `settlementsFor` 的纯函数输出，人口 `pop` 是 `hash01` 常量，所以缺口恒定、边恒定。**人口一动，贸易网络自己就动了。**

3. **载体已经就位，不需要新建任何调度设施。** `TickJobKind.TownEvolve` / `TradeEdge` 已声明，`TickJobRegistry` 已写好 spec（`TownEvolve` = L1/V8/周期 90；`TradeEdge` = L1/Cpu/周期 30），`TickPump.ApplyOutcome`（`TickPump.cs:253`）就是**唯一写世界的入口**。**本方案的工作量集中在「写引擎侧演化公式 + 一个决策脚本 + 接线」，不在框架。**

### 0.3 四条铁律（贯穿全篇，违反任一条静默出错）

| # | 铁律 | 违反后果 |
|---|---|---|
| **红线 1** | tick 只许写**可变派生层**（`pop`/`tier`/`state`/`owner`、`townCache`、`tradeCache`、落库 settle 包）；**绝不写 seed 纯函数层**（`chunk`/`settleCache`/`settleRawCache`/`siteScoreCache`/`prospectCache`/`regionCache`） | 前端自算地形契约崩、世界不可重建、`settleCache` 污染后**不可逆** |
| **红线 2** | 道路重算（L2 / `RoadRework`）**永不进 tick VM 池** —— `roadCache` 依赖建路顺序、不可从 seed 重建，只能走既有 `Lease(seed) + commitPlace` 串行序列 | 道路与地形错位且不报错 |
| **Δ 铁律** | 任何演化公式必须写成 `f(state, dt)`，**绝不写「+1 步」** | L0 摊批时演化速度随机快慢 M 倍（`dt` 被丢弃） |
| **帧铁律** | 新增 V8 出口必须在 `JsEngineHost.Call` 的 switch 加 case | 运行期 `未知 JS 函数`（编译期不报） |

### 0.4 「不需可复现」放宽了什么、没放宽什么

用户答「不需要可复现」，**只放宽一件事**：演化公式里**允许用 `Math.random()` / 真实时钟抖动**，不必强行用 `PhaseHash` 派生确定性 RNG。

**没有放宽的**（因为它们的理由是别的）：
- **红线 1** —— 理由是「前端自算地形契约」，与可复现无关。`settleCache` 一旦被写，前端按 seed 算出的地形与后端就对不上。
- **幂等键** —— 理由是「服务重启 / 重放不漏不重」，与可复现无关。
- **`roadVer` 绝不归零** —— 理由是宿主 `ObserveRoadVer` 单调取大，与可复现无关。
- **Δ 铁律** —— 理由是 L0 摊批的正确性。

> ⚠ 这一条必须写进代码注释里，否则半年后会有人拿「用户说不用可复现」当借口去写 `settleCache`。

### 1.2 缺口（本方案要补的）

| # | 缺口 | 影响 |
|---|---|---|
| G1 | **城内无时间维度**：`growTownFootprint` 是 `(id,type,cq,cr)` 纯函数 + 按 id 缓存 | 城市永远静态，第一层演化能力为零 |
| G2 | **`pop` 是常量**：`rawSettlementsFor` 里 `pop = hash01(i,j,9x)*RANGE+BASE`（如 city `40000~70000`），生成后不再变 | 贸易网络 = 静态快照；第二层「资源互换 + 人口变化」动不起来 |
| G3 | **`tier` 恒定**（sect 1~3 / city 3 / town 2 / village 1） | 城市无法「长大成城」，缺成长叙事 |
| G4 | **无决策脚本宿主**：现有 V8 出口全是「查询/提交」型（`chunkJson`/`commitPlace`…），**没有「喂快照 → 收意图」这种批处理型出口** | 脚本无处挂 |
| G5 | **`ExpectedJobs` 还是空集合**（`TickPump.cs:340`，P1 只给演示心跳） | 没有任何 `TownEvolve`/`TradeEdge` job 会被真正投递 |

### 1.3 一条现成但**不能直接改**的路

`growTownFootprint` 里 `maxN = CFG.TOWN_BUILD_MAX[type]`（`mapgen.js:952`；`village:8 / town:16 / city:25 / sect:16 / fishing:8`）—— 这是**唯一**的建筑数上限旋钮。

**直观想法**：把 `maxN` 改成 `maxN * (pop / pop0)` 就能让城市「长大」。**这个改法必须拒绝**，原因：

- `growTownFootprint` 的产物进 `townCache`，而 `townCache` 是**参与 `townNet` 计算**的（`mapgen.js:1091`）—— 一旦它变得依赖 `pop`（一个 tick 可变量），`townNet`/`tradeEdgesFor` 就**变成 tick 可变**，于是 `tradeCache` 的失效条件变得极其难判。
- 更致命：如果 `pop` 回退（灾荒、战争），`maxN` 变小 ⇒ 建筑**消失**。而 `buildings[]` 是按 `spreadPick` 空间均匀取的 ⇒ 删一个建筑会**级联改变其余建筑的位置**。视觉上是「整座城重排」，不是「几间房子塌了」。
- 且 `townCache` 被清 ⇒ 全部依赖它的东西重算，包括**跨区域**的 `tradeEdgesFor`（±2 环）⇒ 一座城变化引发 25 个区域格重算。

**结论**：演进式生长**必须做在覆盖层**，不能改 `maxN`。这是本方案选路线 (b) 的硬理由，不是偏好。

## 二、两层演化的模型设计

### 2.1 第一层：单座城内部演化（城内）

**核心对象**：每座城一个「城市状态」（CityState），作为**演化覆盖层**叠在 `growTownFootprint` 的静态骨架上。

```
CityState (每座城一份，落库，tick 可变)
├─ id            聚落 id（关联键）
├─ pop           当前人口        ← 演化主变量（可变）
├─ tier          当前规模等级    ← 随 pop 跨阈值升级（可变）
├─ state         0活跃/1被毁/2刷新中/3事件态（已有字段，第二轮启用）
├─ stock[8]      八资源库存（粮木矿渔炭灵丹器） ← 资源交换的落点（可变）
├─ built[]       演化新增建筑（在骨架 maxN 之外叠加）  ← 城"长大"的表现（可变）
├─ upg[]         建筑升级记录（骨架建筑 kind → 升级后 kind）
└─ bornTick      生成 tick（算年龄用）
```

**现状的 `settlementsFor` 骨架 + `$base + evoIn` 叠加**（与 ext 层同构）：

```
settlementsFor(i,j)
  = settlementsFor$base(i,j)                     ← 逐字节不变（红线 1）
      .map(st => applyCityState(st))              ← ★ 第 1 层：贴上级别/人口/新增建筑
      .concat(extIn)                              ← 已有：玩家放置实体
```

> ⚠ **顺序**：`applyCityState` 必须**在 `$base` 之后、`concat(extIn)` 之前**（或并列），
> 理由是 `$base` 的逐字节不变是前端契约；`extIn` 不参与城内演化。

**城内演化的动力学（照真实城市推演取）：**

| 机制 | 真实世界对应 | 公式要点 |
|---|---|---|
| **Malthus / Verhulst 人口增长** | 人口随资源承载力增长，有上限 | `dP/dt = r·P·(1 − P/K)`，`K` = 承载力（由**库存余缺**反推：缺粮则 K 下调） |
| **承载力耦合** | 城市饿死 / 因贸易吃饱 | `K = K_base(siteScore) × (1 + tanh(净粮盈余 / 500))` —— **这就是第二层反哺第一层的位置** |
| **规模升级** | 村镇 → 城镇 → 城市 | `pop` 跨 `TIER_POP_UP[*]` 阈值 ⇒ `tier++`（只升不降；降级单独走 `state=1` 被毁分支） |
| **建筑生长** | 人口多了要盖房 | 每 tick `built` 增长，速率 ∝ `max(0, pop − 骨架容量)`，受地皮上限约束 |
| **灾荒 / 衰减** | 缺粮、战乱 | 净粮长期为负 ⇒ `dP/dt < 0`；`pop < TIER_POP_DOWN` ⇒ `state=3`（事件态），**不自杀**，等外部救援 |
| **年龄效应** | 城市有兴衰 | 新城市增长率高、老城市趋稳：`r_eff = r0 × decay(age)` |

**为什么这比「改 maxN」好**：

- 骨架逐字节不变 ⇒ 前端契约安全；
- 建筑**只增不删**（`built` 是追加数组），不存在「空间重排」问题；
- `pop` 变成平滑微分量 ⇒ 不会跳变；
- 灾荒表现为「新增停滞 + 人口下滑」，而非「建筑凭空消失」。

### 2.2 第二层：城市之间资源互换 + 人口变化（城际）

**现成链路**（一行不改）：

```
settlementsFor(±2环) → 各城 townNet(st) → 各资源净余额 net[r]
   → tradeEdgesFor(i,j) → 配对边 {from, to, resource, amount}
```

**现状为什么是死的**：`net[r] = 供给(const) − 需求(pop / TRADE_DEMAND[r])`，而 `pop` 是 `hash01` 常量 ⇒ **边恒定**。

**接上第一层后就活了**：

1. `TownEvolve`（周期 90）改 `CityState.pop` / `stock`；
2. `TradeEdge`（周期 30）每次重算时，`townNet` 读到**新 `pop`** ⇒ 供需缺口变 ⇒ **边的集合、方向、流量自动重排**；
3. 贸易边产生**实际资源流**：`stock[from][r] -= amount`、`stock[to][r] += amount` ⇒ 回到步骤 1 影响 `K` ⇒ 人口变 ⇒ **闭环**。

> ⚠ **这里有一步必须显式做**：现状 `tradeEdgesFor` 只**产边**，不结算流量。
> 要让「资源真的换过去了」，须在 `TradeEdge` job 里加**结算步**：把 `amount` 扣加进双方 `CityState.stock`。
> **这是本方案对 `tradeEdgesFor` 唯一的实质扩展**，且扩展点在 `CityState`（可变层），不碰 `settleCache`。

**资源守恒与「凭空资源」的处置**（重要设计决策）：

| 方案 | 说明 | 取舍 |
|---|---|---|
| 严格守恒 | 全世界的 `stock[r]` 总量恒定，交换只是搬运 | 真实，但需要全图锁 + 汇总，代价高 |
| **半守恒（推荐）** | 每座城的 `stock` 独立演化，交换只是**在两城之间搬运**；`stock` 有**产出的自然增量**（来自 `resources[]`，即城镇自己的产出）和**人口消耗** | 无需全图锁，天然并行；「凭空」的量等于本地产出 − 消耗，是有来源的 |

**选半守恒**。理由：全图守恒需要「谁先谁后」的全局顺序（每次交换都改双方库存 ⇒ 不能并行批处理），
而 `TickPartitioner` 存在的意义就是**按实体分批并行**。半守恒保住并行度。

### 2.3 两层耦合的完整闭环

```
                  ┌──────────────────────────────┐
                  │  CityState.stock[8]（库存）   │
                  └───────┬──────────────┬───────┘
             产出增量 ↑    │              │   ↓ 人口消耗
        (growTownFootprint │              │  (pop/TRADE_DEMAND)
         .resources[])     │              │
                           │              ▼
                  ┌────────┴──────────────────────┐
                  │  净余额 net[r] = 供给 − 需求   │ ← townNet(st) 已有
                  └────────┬──────────────────────┘
                           │
        ┌──────────────────┴──────────────────┐
        │                                     │
        ▼ 第一层（城内）                        ▼ 第二层（城际）
   K = K_base × f(net[粮])              tradeEdgesFor：缺↔余配对
   dP/dt = r·P·(1 − P/K)                结算：stock 双方扣加
   pop 跨阈值 ⇒ tier++ / built++                │
        │                                       │
        └──────────────► pop 变化 ◄─────────────┘
                          （回到 townNet 的输入）
```

**闭环的三个落点**（都是可变层，红线 1 安全）：
`CityState.stock` → `CityState.pop` → `townNet` 读到的 `st.pop`。

## 三、脚本契约：`decide(worldSnapshot) → intents[]`

### 3.1 为什么需要脚本，而不是全用 C# 公式

- 用户原始需求是「**创建城市迭代过程的 js 脚本放在 v8 引擎中迭代**」——脚本形态是需求本身，不是实现偏好。
- 脚本可**热改**：调参、改策略不必重编译、不必重启（只要重新 `ScriptHost.Update`）。
- 与项目既有惯例一致：世界规则（地形/选址/道路）都在 JS 里，演化规则也该在 JS 里。

### 3.2 分层职责（路线 C：混合分层，见资料调研 §六）

| 层 | 载体 | 职责 | 权限 |
|---|---|---|---|
| **决策层** | **JS 脚本**（本方案新增） | 读快照 → 产出意图 | **无写权限**（纯函数） |
| **校验层** | 引擎既有纯函数（`domainCheck`/`expandCheck`/`isExpandType`） | 判「这个意图合法吗」 | 只读 |
| **执行层** | `commitPlace` / `CityStateStore` | 真正改世界 | 唯一写入口 |

### 3.3 出口签名（新增 V8 出口，必须挂 `Call` switch）

```js
// 演化决策脚本入口 —— 纯函数，无副作用，返回意图数组
function evolveDecide(snapshotJson /* string */) → string /* JSON: intents[] */

// 城内演化公式 —— 纯函数，逐城调用（也可在 evolveDecide 内联）
function evolveStep(stateJson, dtTicks) → string /* JSON: newState */
```

**两个出口而非一个**，理由：
- `evolveDecide` 是**稀有调用**（每 30/90 tick 一次），可整体喂大地图快照；
- `evolveStep` 是**高频调用**（每 tick 每城一次，城多时是热点），入参必须极小（单城 `state` + `dt`），
  且**必须能批量**（一次调用喂 N 座城，避免 N 次跨 V8 边界）。

> ⚠ 批量签名的建议形态：`evolveStepBatch(statesJson[], dtTicks)` → `newStatesJson[]`。
> 单城版保留作为判据的隔离断言入口（能逐条定位错误）。

### 3.4 脚本能读到什么（世界快照字段清单）

**`evolveDecide` 的快照**（避免过大，按**区域格**组织，只喂已激活区域）：

| 字段 | 来源 | 说明 |
|---|---|---|
| `seed`, `tick` | `TickPump.CurrentTick` | 时间坐标 |
| `dtTicks` | `job.DtTicks` | 距上次演化过了多少 tick |
| `regions[]` | 遍历区域格 | `{i, j, biome, spirit}` |
| `settlements[]` | `settlementsFor(i,j)` 全量 | 每城的 `{id, type, q, r, x, y, pop, tier, state, owner}` + **`CityState` 覆盖后的值** |
| `tradeEdges[]` | `tradeEdgesFor(i,j)` | `{key, from, to, resource, amount, dist}` |
| `stocks[]` | `CityState.stock` | 每城八资源库存 |
| `domainR` / `expandR` / `expandTypes` | `metaJson()` | 校验层常量，供脚本预判（**最终以服务端二次校验为准**） |
| `roadsVer` | `roadVersion()` | 只读，供脚本判断「近期道路有变」 |

**绝不下发**（红线 1 的输入面）：`chunk` / `settleCache` / `settleRawCache` / `siteScoreCache` / `prospectCache` / `regionCache` 等 seed 纯函数层任何内容。

> ⚠ **快照规模控制**：全世界区域格数量大时，全量快照会撑爆 V8 堆。
> **按区域格分批**：`TownEvolve`/`TradeEdge` 本来就按实体分片（`TickPartitioner` + `JobSpec.Reads/Writes` 的 `Region:i,j`），
> 所以每次都只喂「本批涉及的 2 环邻域」。这既是性能需要，也是 `JobSpec` 已声明的契约。

## 四、迭代循环：挂在哪里、怎么调度

### 4.1 挂载点：**不新建任何东西**，全部走 Tick 框架 L1

| job kind | 层 | 资源 | 周期 | 现有 spec（`TickJobRegistry.cs`） | 本方案需要做的 |
|---|---|---|---|---|---|
| `TownEvolve` | L1 | **V8** | 90（季） | `Reads=["Settle:{id}","Region:i,j"]`, `Writes=["Settle:{id}"]`, `EngineCaches=["townCache:{id}"]` | 补：`Writes` 加 `CityState:{id}`；执行器里接 `evolveStepBatch` |
| `TradeEdge` | L1 | Cpu | 30（月） | `Reads/Writes=["Edge:{id}"]`, `EngineCaches=["tradeCache:{id}"]` | 补：结算步（`stock` 双方扣加）；`Writes` 加 `CityState:{from}`/`{to}` |
| `RoadRework` | L2 | V8 | 360 | `Parallelizable=false` | **不动**（红线 2） |

> ⚠ `TownEvolve` 标 `EngineCaches=["townCache:{id}"]` 说明注册者本意是「它会改 townCache」。
> **但红线 1 + §1.3 的论证要求它不能改 `townCache`**（那是 seed 派生缓存）。
> **修正建议**：把 `EngineCaches` 改为 `["cityState:{id}"]`，或**留空**（演化层缓存由 `CityStateStore` 自己管）。
> 这是一个**方案级修正**，实施时必须同步改 `TickJobRegistry.cs` 的 spec（否则脏标记指向错误目标）。

### 4.2 `ExpectedJobs` 从空集合变成「遍历聚落」（G5 的修法）

现状（`TickPump.cs:340`）只保底一个 `DemoHeartbeat`。要改成：

```
ExpectedJobs(seed, round, tick):
  for 每个已激活区域格 (i,j):
    for st in settlementsFor(i,j):
      if st.type === 'poi' or st.type === 'fishing': continue   // 渔村不演化（可选）
      yield NewJob(seed, round, st.id, TownEvolve, tick)
      for e in tradeEdgesFor(i,j) 中 from/to 涉及 st 的边:
        yield NewJob(seed, round, e.key, TradeEdge, tick)
```

**⚠ 三个必须注意的点**：

1. **对账只增删不重置**（`TickPump.cs:307` 注释已明确）：已有行的 `NextTick`/`Phase` **绝不被覆盖**，
   否则每年一次的兜底会把相位抖动推平回同一天。
2. **新补上的 job 必须回灌进堆**（`TickPump.cs:319-324` 已做），否则「只落库不调度 = 永久漏事件」。
3. **`settlementsFor` 是含 `extIn` 的** ⇒ 玩家放置的宗门也会进演化。**这是有意的**（玩家城也该演化），
   但要确认 `CityState` 能容纳 `{区域i}_{区域j}_u{n}` 形态的 id（前两段必须是区域格十进制整数，见 MEMORY）。

### 4.3 预算、冷却、超时

| 旋钮 | 现有值 | 本方案的处置 |
|---|---|---|
| `TickBudgetMs` | 300 | **不动**。城内演化是轻量纯函数，单车批量应在 ms 级 |
| `MaxCatchUpTicks` | 4 | **不动**。⚠ 超预算宁可世界慢，不雪崩式追补 |
| `L0SpreadTicks` | 30 | 沿用（`TownEvolve` 是 L1，不摊批；但 `dt` 必须正确传入） |
| `V8 ScriptTimeout` | 待设 | **新增**：单次脚本调用硬超时（见 §六） |
| 脚本侧 CPU 预算 | 无 | **新增**：Screeps 式 CPU 上限（见 §六）。**用户答「不需要可复现」，但 CPU 限额与确定性无关，仍需** |

**批量策略**：`TownEvolve` 周期 90 意味着每城每 90 tick 演一次。假设全世界 200 座城、
相位抖动把它们摊到 90 天里 ⇒ **平均每天 2.2 座城** ⇒ 单 tick 的 `evolveStepBatch` 只喂 2~3 个 state。
**这个量级完全不需要异步**，同步跑即可满足 300ms 预算。

> ⚠ 但**首次激活**时要小心：所有人从 tick 0 起相位分散，若某 tick 恰好聚集，可能一次喂几十座城。
> 处置：**`PhaseHash` 抖动已解决**（`Phase = mix32(fnv1a(seed|entityId|kind)) % PeriodTicks`），
> 且有 `TickPartitioner.Partition` 分批 + 预算闸顺延兜底。**不需要额外机制。**

### 4.4 `dt` 的正确来源（Δ 铁律的具体落地）

`job.DtTicks` 是**瞬态字段**（`TickJob.cs` 注释），由 `CommitSuccess` 时按 `nowTick − LastRunTick` 填充。

**服务重启后第一次演化必须正确**：
- `NewJob` 设 `LastRunTick = fromTick`（首次 `Δt=0`）—— 正确，首次不演化（避免「凭空长一季」）。
- `Load` 从库读回 `LastRunTick` ⇒ 重启后 `Δt = now − lastSavedTick` ⇒ **正确的离线补齐**。
- ⚠ 若 `OfflineCatchUp=false`（当前值），重启后**不补跑**中间那些 tick，但 `Δt` 仍然是真实间隔 ⇒
  **演化公式会一次性吃掉这段时间**。这是**正确行为**（闭式积分，等价于分批补跑的终态），
  前提是公式写成 `f(state, dt)` 而非「+1 步」。**这就是 Δ 铁律的根因。**

## 五、intent → 执行层的映射

### 5.1 两类意图，两条通道（**关键分野**）

| 意图 | 例子 | 通道 | 代价 |
|---|---|---|---|
| **城内演化**（绝大多数） | 人口变、tier 升、建筑增、库存变 | **直接写 `CityStateStore`**（新表） | 微秒级 |
| **改变世界实体**（极少） | 新城诞生、聚落升级为城、聚落被毁 | **`commitPlace` 序列** | **405~443ms**（一号约束） |

> **一号约束回顾**：`commitPlace` 单次同步重算道路 405~443ms，且在 V8 门闩内达到。
> 一轮脚本若产 3~10 个「改变世界实体」意图 ⇒ 1.2~4.4 秒门闩独占 ⇒ **必须分批 + 异步**。

**本方案的核心取舍**：**让城内演化走轻通道，把重通道留给极少数事件。**
这也是为什么 §二要把第一层做成 `CityState` 覆盖层 —— 一旦城内演化走 `commitPlace`，
每城每季都要付 400ms，全世界 200 座城根本跑不动。

### 5.2 `CityStateStore`（新表，独立于 `Data` 表）

> ⚠ **必须独立成表**：`PruneExcept` 会**静默删** `Data` 表非活跃 seed 前缀的行（MEMORY 明确）。
> 玩家资产/演化台账一律独立表（`WorldLedger`/`PlayerSectStore` 即此例）。

```
表 CityState (
  Seed TEXT, Round INT, EntityId TEXT,      -- PK 三元组
  Pop REAL, Tier INT, State INT,
  StockJson TEXT,        -- 八资源库存 {粮:...,木:...}
  BuiltJson TEXT,        -- 新增建筑 [{q,r,kind,tier}]
  UpgJson TEXT,          -- 建筑升级记录
  BornTick INT,
  LastEvoTick INT,       -- 上次演化 tick（供 Δt 与审计）
  Ver INT,               -- 单调版本号（供前端失效判断，见 §5.4）
  PRIMARY KEY (Seed, Round, EntityId)
)
```

**写纪律**：
- 只在 `ApplyOutcome`（唯一写入口）里写；
- 攒批 flush（沿用 `FlushEveryTicks=10` 的节奏，或由 `CityStateStore` 自管脏集）；
- 换世（`UnbindWorld`）**强制 flush**（`TickPump.cs:134` 已有此纪律）。

### 5.3 失败回退

沿用 `TickPump.ApplyOutcome` 既有逻辑（`TickPump.cs:253-280`），**不新增机制**：

- `commitPlace` 失败 ⇒ `CommitFailure` ⇒ 退避 `FailBackoffTicks=5` ⇒ 连续 `MaxFails=5` 次 ⇒ 停用并 `LogError`。
- **「失败也推进」是静默病**（注释已明确），本方案不得引入。
- 城内演化（`CityState` 写入）理论上不会失败；若失败（脚本超时），退避后**下次用累积的 `dt` 重算** ⇒ 自愈。

### 5.4 脏区块累积与 rev 契约

⚠ **块级 rev 显式契约**（MEMORY 铁律）：任何改变某块某图层内容的服务端改动**必须** `BumpBlockRev`，
否则客户端带旧 `lastRevs` 重拉被判「未变化」⇒ **永久陈旧**（不报错）。

**本方案涉及的可变图层**：

| 变化 | 图层 | 处理 |
|---|---|---|
| `pop` / `tier` / `state`（骨架字段） | 聚落层（Region/Settle 包） | **必须** `BumpBlockRev` + `forceStaticDirty()` |
| `built[]` 新增建筑（足迹层） | 足迹层（`settleJson` 包） | **必须** `BumpBlockRev` + `forceStaticDirty()` |
| `stock[]` 库存 | **不渲染** ⇒ 无需 Bump | 无 |
| `tradeEdges` | **不落库、不进 chunk/settle 包**（`mapgen.js:1113` 注释）⇒ 无需 Bump | 无 |

**批量 Bump 的量化**：一季全世界若有 50 座城 `pop` 变 ⇒ 50 次 `BumpBlockRev`。
若这 50 座城挤在少数块里 ⇒ 同一块 Bump 多次 ⇒ **应做「按块聚合，同块只 Bump 一次」**。
`dirtyBlocksFor(tiles)`（`commitPlace` 步 6）就是现成的聚合工具，复用它。

**前端失效**：`CityState.Ver` 单调递增，前端凭 `st._popVer` 失效其 `spriteOf`/`factionOf` 派生缓存
（照 `st._fac` 靠 `settleVer` 失效的既有模式）。

## 六、沙箱与限额

### 6.1 ClearScript 侧（C# 宿主）

| 项 | 设定 | 理由 |
|---|---|---|
| `V8ScriptEngine.ScriptTimeout` | 建议 **200ms**（单次调用） | Screeps 经验：`vm.runInContext` 超时是**唯一**能杀死死循环的手段 |
| `V8RuntimeConstraints.MaxHeapSize` | 需实测定（先给 64MB 试） | 防脚本递归/大数组撑爆。⚠ 快照是主要内存消费者 ⇒ **靠 §3.4 的分批控制规模，而不是靠加大堆** |
| `V8RuntimeViolationPolicy` | 沿用现有实例的设定 | 与读路径 VM 一致 |
| **VM 实例** | 用 `TickVmPool`（**独立于读路径** `JsEngineHost`） | 设计文档 §6.7：两套独立 VM ⇒ tick 与人类请求**零门闩争用**（V8 单线程，门闩是全局的） |

> ⚠ **超时后的处置**：ClearScript 超时会让引擎进入「不稳定」状态，**该 VM 实例必须作废重建**，
> 不能继续复用。这需要在 `TickVmPoolExecutor` 里做「实例重建」逻辑（P2 落地时注意）。

### 6.2 脚本侧（JS）配额（Screeps 式）

```
每 tick 给脚本一个 CPU 预算（如 50ms），可跨 tick 累积到 bucket（上限 ~10000）
- 预算耗尽 ⇒ 脚本必须优雅退出（返回已算出的 intents），不许死循环
- bucket 允许单 tick 透支（Screeps 是 500），但连续透支 ⇒ 强制下限
```

⚠ **「不需要可复现」不豁免 CPU 限额**：限额防的是**卡死整个服务器**，与确定性无关。

### 6.3 静态守卫（防脚本写出红线 1 违规）

在脚本入口做**轻量 AST 检查或黑名单扫描**，拒绝出现：

- `MapGenServer.` 的任何 seed 纯函数层出口（`settleCache`/`settleRawCache`/`siteScoreCache`/…）；
- `commitPlace` / `bumpRoadVer` / `forceStaticDirty`；
- 任何写 `mapgen.js` 闭包内变量的路径。

**更彻底的做法**：脚本 VM 里**根本不暴露**这些出口（`MapGenServer` 对演化 VM 只挂只读子集）。
⭐ **推荐这一条** —— 「不给权限」比「检查他有没有用权限」可靠得多。

## 八、风险与回退

| 风险 | 触发条件 | 后果 | 处置 |
|---|---|---|---|
| **R1 快照过大** | 全世界聚落数 × 字段数超过 V8 堆 | 脚本超时 / 堆溢出 / 泵卡顿 | §3.4 按区域格分批；§6.1 实测堆上限；判据 C8 |
| **R2 演化引发连锁重算** | `CityState` 变化误触发 `townCache`/`settleCache` 失效 | `tradeEdgesFor` ±2 环级联 ⇒ 一次演化引发 25 格重算 ⇒ 卡顿 | 红线 1 + 判据 C1；`clearRoadSideFor` 只清该清的 |
| **R3 `CityState` 与骨架脱节** | `settlementsFor` 骨架变了但 `CityState` 没跟上（或反之） | 城市显示与数据不一致 | 对账步（`MaybeReconcile`）增补：骨架里消失的城 ⇒ 清其 `CityState`（或标 `state=1`） |
| **R4 灾荒死锁** | `pop` 下滑到 0，`K` 也归零 ⇒ 永不恢复 | 死城占位 | 设 `POP_FLOOR`（如 50），`pop` 不低于它；判据 C2 覆盖 |
| **R5 脚本人为改坏** | 热改脚本写错 | 全图演化异常 | 脚本版本化 + 加载时校验 + 出错退回上一版（graceful degradation） |
| **R6 相位聚集** | 首次激活时大量 job 同 tick 到期 | 单 tick 超预算 | 已有 `PhaseHash` 抖动 + `TickPartitioner` 分批 + 预算闸顺延（§4.3） |
| **R7 与 P0/P2-α 冲突** | `待办事项/玩家宗门放置与城市迭代方案.md` §十/§10.4 曾列「✗ NPC 城市迭代」为不做 | 范围冲突 | **本方案正在推翻该条**（用户本轮明确要求）。实施前须在方案 §十 标注「已由 v2 实施方案取代」 |
| **R8 `EngineCaches` spec 错误** | `TownEvolve` 现标明 `townCache:{id}` | 脏标记指向错误目标 ⇒ 该清的没清 / 不该清的清了 | §4.1 的修正建议必须落实（改为 `cityState:{id}` 或留空） |

### 回退方案（三级）

| 级别 | 动作 | 恢复时间 |
|---|---|---|
| **L1 停演化** | `TickOptions.TickEnabled=false`（或只停 `TownEvolve`/`TradeEdge` 两个 kind） | 立即，世界回到静态（P0 状态） |
| **L2 清演化层** | 清空 `CityState` 表 + 清 `townCache`/`tradeCache` | 秒级，回到「骨架 + ext」纯净态 |
| **L3 卸覆盖层** | 关掉 `applyCityState` 开关（一个 flag）⇒ `settlementsFor` 退化为 `$base + extIn` | 立即，**逐字节等于现在** |

**L3 是本方案的保险丝**：因为演化是**纯叠加**的，卸载它不会留下任何残留 ⇒ **零风险的渐进上线**。
这也是选「覆盖层」而非「改 `maxN`」的又一个硬理由（改 `maxN` 是不可逆的）。
