# 人物系统（修士个体建模）—— 资料调研

> 目的：为「在这个世界里建模**一个个修士**」这件事，把修仙类作品怎么做「人」、个体模拟能有多深、程序化生成怎么保证确定性、以及**本项目已有的地基与缺口**一次摊开，供选型讨论。
> 边界：**本文不含实施方案**。§六 只给候选路线与倾向，§七 列必须拍板的问题。定案后再写《人物系统-实施方案》。
> 相关已有档：`docs/设定.md`（化身系统 §四、天命者/借宿体）、`docs/玩家信息表设计.md`（`disciples` 字段）、`待办事项/脚本化城市迭代-资料调研.md`（ABM/BDI、以及「弟子分内外门」的叙事参考）、`docs/游戏时钟与Tick演化框架方案.md`(v2.1)、`.workbuddy/memory/DETAILS-引擎与表现层.md`。

## 〇、一页纸

你想要的「修士个体建模」，剥开是三件事：

1. **一个人是一份数据**（属性 / 境界 / 灵根 / 性格 / 寿元 / 关系）；
2. **他会随时间变化**（修炼、突破、衰老、死亡、结交与结仇）；
3. **他要能被看见**（画在地图上 / 出现在宗门面板与详情卡里）。

对照本项目现状：**"随时间变化"的挂载点已经有了**（Tick 框架里 `SectCultivation`＝弟子修炼、`Lifespan`＝寿元倒计时**两类 job 已注册**，只是空壳）;**"五行/灵脉/资源"这些加成来源也在**（`ELEMENTS=['金','木','水','火','土']`、灵脉域、`RES_ORDER` 八资源）；但**"一个人"这个实体在本项目里不存在**——世界里只有聚落、宗门、秘境，没有任何个体。

三句话结论，先说在前面（§六展开）：

- 最值得照搬的是 **Dwarf Fortress / RimWorld 的「个体不可替代」+ 需求/情绪驱动**，但要照搬的是**机制骨架**，不是它的逐器官深度。
- 最需要你拍板的是 **"人物"是聚合统计还是独立实体**——这决定工程量差一个数量级，也决定这张表能不能撑住 N 上万的规模。
- 最大的隐藏成本不是数值，是 **N 个独立实体的每 tick 调度与落库**：本项目已被「`commitPlace` 同步 405ms 占满门闩」教训过，人物系统会以更大的 N 撞同一堵墙。**而解药本工程已经用过一次：LOD（分级模拟）+ 覆盖层。**

**三条必须写下来的硬结论：**

1. **"人"是本项目唯一缺失的实体层级。** 聚落有 `pop`（一个数），但没有"这 pop 是谁"。——人物系统不是加字段能解决的，是**加一个新的实体类型**（以及它的 id、存储、渲染、调度）。

2. **Tick 框架已经替你把人物系统的"时间维度"预留好了。** `SectCultivation`/`Lifespan` 两类 job 的存在说明：设计意图本来就是「**每个修士一个 L0 job，按 dt 积分修炼进度 / 扣寿元**」。当前是空壳，但**接缝已经留好了**——这是本系统最大的现成红利。⚠ 但要注意 Tick 的红线：L0 只能写"可变派生层"，**绝不碰 chunk/settleCache 等引擎缓存**；同 `stId` 的 job 会被 `TickPartitioner.CanJoin` 拆成串行批（引擎缓存键重叠）。

3. **一号约束仍是"同步门闩"。** `commitPlace` 单次同步 405~443ms 的教训意味着：**若让 N 个修士各自触发一次同步重算，人物系统会比城市迭代更快撞墙**。任何路线都要正面回答"N 有多大、每 tick 谁在算、算不动怎么办"。

## 二、参考资料 A：修仙经营类怎么建模「人」

### A-1 《了不起的修仙模拟器》—— 最完整、且本工程已引用过

| 维度 | 该作的做法 | 对本项目的价值 |
|---|---|---|
| 属性 | 角色**五维**：根骨 / 机缘 / 悟性 / 神念 / 潜力 | 五维比"三属性"更有修仙味，且**每维都有明确去处**（根骨→炼体、悟性→修炼效率、机缘→事件气运） |
| 内外门 | 弟子分**外门（生产生存）/ 内门（专修炼）**，晋升内门解锁"精元/灵气/心境/修炼目标" | ⭐ 天然对应本项目的 `tier` 与"建筑配额"叙事（见城市迭代调研 §五） |
| 境界 | 练气 → 筑基 → 金丹 → 元婴 → 化神 → 炼虚 → 合体 → 大乘（8 阶），每阶有**天劫** | 境界链可直接做状态机；天劫=突破时的确定性判定 |
| 生存/心理 | 跟踪**饥饿/饮水/精力/娱乐**需求 + **情绪值**；情绪崩溃→**执念**→**心魔**→走火入魔 | ⭐ 这是"人味"的来源；但在本项目里**不能全盘照搬**（见 §三 的深度取舍） |
| 寿元 | 寿元结束即死；需在寿元耗尽前提升境界/收集延寿宝物 | ⭐ 与 `Lifespan` job 严丝合缝 |
| 社会关系 | 从亲人朋友到**师徒恋人** | 最深的一层，工程量最大 |
| 定义方式 | 5 维 + 背景故事 + 特性（道士/和尚/夺命神医…）**>200 种组合** | 组合式生成，天然可复现 |
| 工作 | **数十个职位**（猎户/农工/木客…）可分配给每个角色 | 可映射到"建筑 → 岗位" |

### A-2 《最强祖师》（手机）—— 最"游戏化"的一套词条结构

- **六维**：潜力 / 资质 / 根骨 / 机缘 / **聪慧** / **魅力**（后两维是本作特色：聪慧→技能经验、魅力→与修真者关系）。
- **特质四件套**：**天命**（橙色以上专属彩色词条）/ **灵根**（金木水火土 + 天金天木…）/ **天赋**（生产、学习、六维增减）/ **体质**（五行灵体…）/ **怪癖**（多数负面，可用丹药消除）。
- **一条关键设计**：**"灵根并不是越多越好，单一灵根修对应属性功法加成更高"**——即**多灵根 = 泛而不精**，这是有取舍的设计，不是纯堆数值。
- **招募**：引仙台招募令（8h 一次免费，最多累计 3 次）+ 家族招募（家族人口越多，出高品质弟子概率越大）。

### A-3 《鬼谷八荒》—— 属性分层与"资质卡门槛"最清晰

- **三大类 18 种资质**：功法 6（刀枪剑拳掌指）/ 灵根 6（火水雷风土木）/ 技艺 6（炼丹炼器风水画符药材矿材）。
- **个人属性**（状态值）：寿命 / 心情 / 健康 / 精力 / 体力 / 灵力 / 念力 / 幸运 / 悟性 / **声望** / **魅力**。
- **性格**：**1 内 + 2 外**，性格直接改变交互结果（"义气"更易结交、"正直/仁善"强化正道属性）。
- **先天气运**：roll 点生成，词条品质分**红橙紫蓝绿白**六档，品质越高初始加成越多。
- ⭐ **最值得抄的一条**：**资质是"硬门槛"不是"软加成"**——"剑法资质 20 才能学某剑法"，不到就是学不了。这条把"数值"变成了"选择"，比纯 +% 更有策略性。

**三作共同点（可直接固化为本项目的属性骨架）**：
> 属性 = **先天根骨类**（灵气亲和/资质，决定上限） + **后天成长类**（修为/境界，随时间涨） + **技艺类**（炼丹/炼器等，决定能干什么） + **心性类**（性格/心境，决定怎么干/干不干）。

## 三、参考资料 B：个体模拟能有多深（宁少勿滥 vs 深度）

### B-1 Dwarf Fortress —— 深度的天花板（但不要照抄）

- **50+ 人格轴**（焦虑倾向/愤怒倾向/抑郁倾向/合群性/爱自然…）。
- **100+ 技能**，逐个体成长。
- **关系网**：友谊/敌意/恋爱/亲缘，基于交互与共享价值观形成看法。
- **记忆**：记住死亡、骇人景象、美器、好饭/难吃的饭、下雨、被袭击——**影响 mood 数周到数月**。
- **需求**：食物/饮水/睡眠/社交/创作/信仰/接触自然。
- **逐器官身体**：断左臂、右肺撕裂、肝淤血…各有功能后果。
- **世界历史预生成**：文明兴衰、战争、英雄、神器，**不是风味文本，是有后果的模拟**。
- **涌现叙事（tantrum spiral）**：宠物猫被杀 → 高焦虑侏儒悲伤 → 拒绝工作 → 他人压力上升 → 食堂斗殴 → 旁观者受伤 → 其友愤怒 → 拉帮结派 → 孩子目击创伤 → 家长暴怒 → 整个堡垒在几天内被暴力与哀恸吞没。**没有设计师写这段，是系统碰撞出来的。**

### B-2 RimWorld —— 深度的"甜点区"（机制骨架最该抄）

- **Mood meter**：由 needs + traits + backstories 共同决定；needs 不满足会 **mental break**（发呆/暴走/攻击他人）。
- **Traits**：多数人 **1~3 条**；**成年人不能再获得新 trait，也不能移除**；孩子每过一个 birthday（7/10/13）才多一条；生成时按"pawn kind 要求 → 任务要求 → backstory 授予 → 随机补齐（按词条 commonality 加权）"的顺序确定，且**随机补齐会排除与已有 trait 冲突的、会禁用必需工种的、会把精神崩溃阈值抬高过 50% 的**。
- **Backstory 决定能力**：贵族出身→社交强但拒干体力活；农民→会种地不能研究。**"背景"不是文本，是能力约束。**
- **Opinion / 关系**：每个殖民者对他人有独立看法（爱/恨/漠然）；亲密度到阈值自动恋爱、结婚、生子；过低会争吵甚至互杀。
- **永久死亡 = 个体不可替代**：RimWorld 作者 Tynan 的设计论核心是「**让每个 NPC 不可替代，才能产生真情绪**」，单个殖民者的死亡是**永久损失**（Ironman 模式不可撤销）。这正是"人味"的来源。
- **"极简美术 + 丰富人格"**：屏幕上的殖民者只是无脸无腿的小色块，靠 **apophenia（人脑在随机中找模式的本能）** 让玩家自己脑补出故事——**对美术投入有限的项目是极重要的启示**。

### B-3 深度取舍表（给本项目用）

| 机制 | 照搬？ | 理由 |
|---|---|---|
| 情绪 / 需求驱动的"崩溃" | ⭐ **取骨架** | 人味核心；但只保留 2~3 个需求（如"心境"），不做饥饿/饮水/娱乐全套 |
| Traits 1~3 条 + 生成顺序 + 冲突规则 | ⭐ **照抄** | RimWorld 的生成算法本身**就是确定性的**，与本项目纪律一致，拿来即可 |
| Backstory 决定能力 | ⭐ **照抄** | "背景是约束不是文本"，低成本高收益 |
| 永久死亡 | ⭐ **照抄** | 与 `Lifespan` job 天然契合；呼应"个体不可替代" |
| 逐器官身体 | ❌ **不抄** | 本项目非战斗向；成本极高、收益低 |
| 50+ 人格轴 / 100+ 技能 | ❌ **不抄** | 量级失控；用"五行/流派"这类**少量正交维度**替代 |
| 世界历史预生成 | ⚠ **部分** | 可用 `hash01(seed)` 生成"某宗某代祖师"的编年，不做全文明史 |
| 社会关系网 | ⚠ **P3 再说** | 最贵的一层，见 §六 路线取舍 |

## 四、参考资料 C：程序化角色生成（确定性 > 花哨）

### C-1 五层生成管线（工业通用范式）

```
Core Seed（确定性起点，一个整数/字符串）
   ↓ 伪随机算法（同输入 ⇒ 同输出）
Stat Matrix（把种子变成数值：正态分布 / 点买，防止"破格"角色）
   ↓
Persona（性格/动机/说话方式：规则库 或 trait banks）
   ↓
Visual（属性 → 外观：贴图/颜色/立绘）
   ↓
Manifest（序列化成 JSON / protobuf，可跨引擎实例化）
```

- **Core Seed 是"基因源"**：本项目已有完全等价物——`hash01(...)`。**"整局游戏 = seed + 操作列表"**，replay 免费。
- **Stat Matrix 防破格**：用**正态分布或点买**保证"角色独特但都可玩"。⚠ 本项目的坑：**别用 `Math.random()` 生成属性**，一律 `hash01(seed, entityId, 'attr', k)`。

### C-2 一个必须警惕的坑：**行为同质化**

- 《PersonaWeaver》(arXiv 2026) 的发现：**LLM 生成的角色"传记多样但行为同质"**——不论设定成硬汉侦探还是精灵，行为都偏向礼貌、配合、乐于助人（RLHF 的副产物）。
- 解法：**把「世界设定属性」与「行为特质」解耦**，各行其是地采样，最后做一次"一致性修补"。
- ⭐ **对本项目的启示**：若本项目的人物也用本地 LLM 生成"性格/台词"，**必须有独立的"行为维度"来源**（如五行属性/宗门立场/境界），否则会出现"所有修士说话都一个样"。

### C-3 一个开源参考骨架

- `rbledsaw3/CharGen`（RPG 角色生成框架）：骰子机制（校验+无偏随机）→ 属性(ST/DE/CO/IN/WI/CH) → 性别/名字（**按种族×性别选名字库**）→ 种族加成 → 职业（含最低属性要求）→ 阵营。
- ⭐ **命名依赖前置变量**（"女性精灵"才知道用哪个名字库）——这是程序化生成里最容易被忽略的**生成顺序依赖**。本项目若做人物姓名，需注意**先生成"性别/来源地"再生成"名字"**。

## 五、参考资料 D：本项目既有的"接缝"（决定成本的部分）

| 接缝 | 现状 | 人物系统要怎么接 |
|---|---|---|
| **Tick 调度** | `SectCultivation`/`Lifespan` 已注册（L0/Cpu），空壳 | ⭐ 直接实现这两类 executor；新增 job（如 `SectRecruit`/`RelationTick`）须同时进 `TickJobKind`+`KindNames`+`TickJobRegistry` |

| **前端** | 实体来自 `settleCells`；本宗面板读 `PlayerSect` | 人物"画在图上"复用实体通路；"看某人的详情"复用 `infocard.js` |

| **五行** | `ELEMENTS` 已存在 | 灵根可直接复用五行（或扩到鬼谷式 6 行） |
| **ID 格式** | 引擎会反解 id 前两段为区域格（`skeletonEdgesFor`） | ⚠ 人物 id **不要复用** `{i}_{j}_{k}` 格式（会撞 NPC 序号 / 被路网误读）；建议独立前缀（如 `c{序号}`）或用 `(Round, Id)` 主键、id 不进路网 |

## 六、三条候选路线（含我的倾向）

分歧点只有两个：**人物是独立实体还是聚合统计**、**模拟发生在哪一层**。

### 路线 A：聚合统计流（最轻）

- 人物**不是实体**，只是宗门/聚落上的统计量：`disciples`（数量）+ **境界直方图** + **灵根分布**。
- 修炼/寿元在**宗门层**积分（`SectCultivation` 直接改宗门的境界分布）。
- **优点**：成本最低，复用现有 `pop` 模型与 `PlayerSect.disciples`；**N 无上限**（因为根本没有 N）。
- **缺点**：**没有"个体"**——谈不上姓名、师徒、不可替代感。与你想做的"个体建模"名不副实。

### 路线 B：全个体实体流（最重，DF/RimWorld 式）

- **每个修士 = 一行数据 + 每 tick 一个 job**；属性/境界/灵根/性格/寿元/关系全建。
- **优点**：表达力最强，能做出真正的"人味"与涌现叙事。
- **缺点**：**N 爆炸**——一个世界若几千宗门 × 几十弟子 = 十万级实体，每人每 tick 一个 job ⇒ 调度、存储、前端全要新建，且会直接撞 §一 结论 3 的同步门闩。
- 与既有红线冲突最大（L0 不可写引擎缓存、`PruneExcept`、确定性）。

### 路线 C：LOD 分层模拟（我的倾向）—— "名录 + 聚焦个体"

一句话：**大多数修士是统计量，少数修士是活人。**

| 层 | 谁 | 存什么 | 谁在算 |
|---|---|---|---|
| **L-agg（名录层）** | 全部普通弟子 | 只存"数量 + 境界直方图 + 灵根分布"（就是路线 A） | 宗门级一个 job（摊销，N=宗门数） |
| **L-focus（聚焦层）** | **重要个体**：玩家宗门核心弟子 / **天命者** / 各宗掌门 / 被通缉/被记录的人 | 完整个体数据（属性/境界/寿元/性格/关系） | 每人一个 L0 job（N=聚焦人数，可控） |
| **L-render（呈现层）** | 前端 | 地图上只画 L-focus（徽记/色块）；面板里两层都能看 | 复用现有实体会话 |

理由三条：

1. **它把"最有价值"的部分（个体不可替代感、天命的叙事）隔离在少数实体上**，而"人手规模"用聚合摊销——**既不放弃人味，也不让 N 爆炸**。
2. **它正面回答一号约束**：每 tick 的 job 数 = 宗门数 + 聚焦人数，**与总人口无关**；不会像 `commitPlace` 那样被 N 拖死。
3. **它复用本工程已验证的两个模式**：`ext` 覆盖层（"引擎出生态 + 派生叠加"）与 LOD（小地图 L1/L2/L3）。**不是新范式，是把已有范式用到人物上。**

⚠ 路线 C 的关键设计问题：**"晋升聚焦层"的判据必须确定性且单向**（否则同一修士在不同时刻一会儿是统计量一会儿是实体，会出现"数据对不上"的静默 bug——本工程已在 `domainR` 上栽过一次同类）。建议：**聚焦名单由 seed/事件纯函数决定，一旦晋升不降级**。

### 三条路线对比表

| 维度 | A 聚合统计 | B 全个体 | C LOD 分层 |
|---|---|---|---|
| 有"个体"吗 | 无 | 有 | 部分（重要个体） |
| 表达力 | 低 | 高 | 中→高 |
| N 上限 | ∞ | 万级即崩 | 可控（宗门数+聚焦数） |
| 与 Tick 接缝 | 复用（改宗门 job） | 大量新 job | 新增 1~2 类聚焦 job |
| 存储成本 | 极低（进 `PlayerSect`） | 新建，N×大 | 新建，聚焦才落库 |
| 个体不可替代感 | 无 | 强 | 强（但只对重要个体） |
| 前端改动 | 面板加字段 | 大量 | 中（徽记/详情卡） |
| 适合阶段 | 先跑通 | 玩法实验台 | **先跑通 → 再扩** |

## 七、必须由你拍板的问题

| # | 问题 | 我的建议（仅建议） |
|---|---|---|
| 1 | **人物是独立实体还是聚合统计？**（决定路线 A/B/C） | **C（LOD 分层）**——先跑通"名录层"，聚焦层按需长 |
| 2 | **模拟深度对标谁？**（RimWorld 的情感/需求深度 vs 修仙模拟器的境界/功法广 度） | 取**两者骨架**：境界链（修仙味）+ 情绪/需求 1~2 项（人味），不做逐器官 |
| 3 | **谁是"聚焦个体"？判据是什么？** | 玩家宗门核心弟子 + **天命者**（设定已有）+ 各宗掌门；判据走 `hash01`/事件纯函数，单向不降级 |
| 4 | **境界体系取值？** | 建议**压缩**到 5~6 阶（如 练气/筑基/金丹/元婴/化神+大乘），8 阶对 demo 偏长 |
| 5 | **灵根用几行？** | 复用已有 **五行 `ELEMENTS`**；⚠ 若照抄鬼谷 6 行（加风/雷）需改引擎常量，影响面大 |
| 6 | **要不要"个体死亡"（不可逆）？** | **要**——这是"人味"与 `Lifespan` job 的核心；触发=寿元尽/天劫失败/事件 |
| 7 | **社会关系（师徒/好友/仇敌）做不做？** | P0 **不做**，但**字段先占位**（同 `PlayerSect.disciples` 的"占位不花钱"原则） |
| 8 | **是否要求严格可复现**（同 seed 逐 tick 逐个体状态哈希一致）？ | **要** —— 本工程铁律，也是回归判据的唯一抓手 |
| 9 | **前端怎么呈现人物？** | 先**面板/详情卡**（复用 `infocard.js`），地图上暂用徽记/色块（学 RimWorld"极简美术"） |

## 八、你确认后，下一份文档会写什么

拿到 §七 的答复后，我会出《人物系统-实施方案》，目录预览如下（方便你提前否掉不想看的部分）：

1. **数据模型**：`Cultivator` 字段清单（属性/境界/灵根/性格/寿元/关系），哪些提列、哪些进 JSON、`v` 版本号
2. **生成管线**：`hash01(seed, entityId, 维度)` 的确定性属性/姓名/性格生成（含生成顺序依赖）
3. **Tick 接线**：实现 `SectCultivation`/`Lifespan` 两类 executor；LOD 聚焦层的新 job 与预算
4. **存储**：`CultivatorStore` 独立表（避开 `PruneExcept`）、主键与索引、迁移策略
5. **协议/前端**：并进 `settle` 包还是新帧；人物在面板/地图上的呈现与帧位
6. **判据**：离线可直调的断言清单（确定性哈希、Δ 不变性、聚焦层单向性、寿元单调）
7. **风险与回退**：N 上限、门闩占用、与城市迭代/Tick 的耦合
